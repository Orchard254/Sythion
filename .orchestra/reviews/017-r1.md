## What changed
`backend/runtime/events.py` (17 insertions / 3 deletions): replaced the one-time `_counter_table_checked` boolean guard at the top of `append_event` with a transaction-resident existence check:
- `if not self._session.in_transaction(): self._session.execute(text("BEGIN IMMEDIATE"))` ensures the append participates in a rollback-capable transaction when the caller has not started one.
- `SELECT 1 FROM sqlite_master WHERE type = 'table' AND name = 'task_event_sequences'` is evaluated in the append's transaction.
- Absent -> idempotent `CREATE TABLE IF NOT EXISTS task_event_sequences (task_id VARCHAR NOT NULL PRIMARY KEY, next_seq INTEGER NOT NULL)`; present (migrated database) -> no DDL on the normal path.
- `_counter_table_checked = True` promotion removed; the attribute remains initialized to `False` for compatibility.
The `_ALLOCATION_SQL` savepoint/retry loop, `EventSequenceAllocationError` chaining, `latest_sequence`, `event_history`, and `_to_dict` are untouched.

## Goal fit
Closes both described variants of the stuck flag: a successful-but-rolled-back append no longer leaves the cached `True` behind because creation is re-established by the existence query on the next call; an allocation failure inside the savepoint loop cannot leave a stale capability bit (the bit is never promoted and is never the gating condition). Behaviour on migrated databases is unchanged (existence query returns present; no DDL on the hot path), and `db_manager` remains the schema owner.

## Risks found
1. `BEGIN IMMEDIATE` was added by the implementer beyond the plan's illustrative logic. It is transactionally justified (DDL/DML must participate in the caller's rollback instead of auto-committing under Python 3.11+ sqlite3 legacy mode) and is a no-op when a transaction is already active, but it is the one element not spelled out in the plan. It passed all targeted and neighbour tests, and preserves the "append does not commit" contract. No concern raised.
2. On a rolled-back failed allocation, the table-creation and `BEGIN` work live in the caller's (still-open) transaction; correct operation relies on the caller rolling back after `EventSequenceAllocationError` (the provided variant-(b) test does). If a caller neither commits nor rolls back, the created table can outlive the failed event, which is consistent with the pre-change contract and with SQLite transactional expectations.
3. Concurrency creation races rely on `CREATE TABLE IF NOT EXISTS` plus writer serialization/busy timeout; the invariant/concurrency test was run 10 times without flake. No failure observed.
4. `_counter_table_checked` can never read `True` after this change. No in-repo consumer references it (grep found only the field itself in `events.py`), so this is safe; external introspection relying on `True` after first append would need updating, which the plan explicitly permits.
