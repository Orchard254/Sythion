### F3 (required, r1) - CLOSED

The docstring's opening no longer says such an assertion "verifies nothing" (`:3-9`):

```
An ``assert`` whose test carries the boolean literal ``True`` in a *boolean
position* is degenerate: the literal decides that position instead of the
code under test, so the assertion does not check the property its shape
suggests while the suite that contains it advertises exactly the property
it does not check.
```

The self-contradiction with the third paragraph (`:23-28`, "a conjunction whose left operand carries the literal reduces to its right operand, and a literal under a negation fixes the outcome at false") is gone: the opening now claims only what is true in every flagged shape.

I checked the new sentence against the implementation for each of the four flagged shapes (measured, three-valued evaluation):

| flagged shape | what the shape advertises | what it actually checks | "does not check the property its shape suggests" holds? |
|---|---|---|---|
| `assert (x or True) and y` | `(x or True) AND y` | only `y`; `x` is never inspected | yes |
| `assert not (x or True)` | `not (x or True)` | nothing - the outcome is fixed at False | yes |
| `assert x or (y or True)` | `x OR (y OR True)` | only `x`; `y` is never inspected | yes |
| `assert True` | a property check | no property at all | yes |

In every flagged shape at least one advertised conjunct/disjunct is decided by the literal, so the property the shape suggests is not the property checked. The weakened wording is accurate. **Closed.**

### F5 (non-blocking in r1) - the clarification is IN, but it is INACCURATE - new required finding F9

Applied as written (`backend/tests/test_conversation_memory.py:637-640`):

```
# The fix returns early when verification fails, but the commit already happened.
# The count below is what this test's own session sees (autoflush); it is not a
# persistence check.  The key test is that the verification code path exists and
# runs: the production code logs this warning when the read-back finds no turns.
```

The clause "**what this test's own session sees**" is true. The two clauses after it are not:

1. **"(autoflush)" is wrong.** The session under test comes from the `memory_db_setup` fixture (`backend/tests/test_conversation_memory.py:22-27`), which yields `db_mgr.get_session()` -> `self.SessionLocal()` -> `sessionmaker(autocommit=False, **autoflush=False**, bind=self.engine)` (`backend/core/db_manager.py:88-92`). Measured on the real factory: `session.autoflush` is **False**. (Note the contrast: the site-2 `db` fixture uses a bare `sessionmaker(bind=engine)` - `backend/tests/conftest.py:413` - which is SQLAlchemy's default `autoflush=True`. The two tests in this item run on sessions with *opposite* autoflush settings, and the F5 sentence describes site 2's setting while sitting in site 1.)
2. **"it is not a persistence check" is wrong for this session.** With autoflush disabled, a query on the session does **not** flush pending objects, so an uncommitted row is *invisible* to it. Measured with the project's own `DatabaseManager` (TEMP probe): after `session.add(...)` of two `ConversationTurn`s without committing, `session.query(ConversationTurn).filter_by(task_id=...).all()` returns **0**; after `session.commit()` it returns **2**; an independent session also sees the **2** committed rows. So `assert len(turns) == 2` observes rows that are actually *in the database* - it is a persistence check in this configuration, and a regression that dropped `db.commit()` from `save_conversation_turn` (`:107`) would make it fail (0 != 2).

This also corrects round 1: r1's F5 rationale ("the query is on the same session, so pending (uncommitted) rows would also be returned") assumed SQLAlchemy's default `autoflush=True`. This project disables it, so the premise was wrong - and the fix text written from that premise is wrong too.

Why this is worth one more round rather than a note: it is a false claim about the code, in a file the diff already touches, in an item whose doctrine is that claims must match the code - and it *understates* the strength of the assertion the item just installed. A future maintainer reading "it is not a persistence check" may delete or "fix" a real check. See F9 for the fix shape.
