## Goal fit

Directly on goal.md's "release and operator readiness" and "verification before claims"
(`goal.md:32-37`). The repository's release-confidence signal is its CI pipeline, and
before this diff the pipeline was unreachable on the branch that exists, contained one
gate that was red for a directory reason, never executed the frontend suite, and
overrode the declared pytest pin. All four are now repaired in the smallest possible
place: one workflow file, one npm script, no runtime code.

**Simpler way?** No. The four defects are four separate edits and the constraints are
tight: the import *command* cannot change (`backend/api/routes.py` imports `backend.*`
absolutely), so only the directory can move; the trigger needs `master` *and* a manual
trigger; the vitest step needs the script split because `vitest` in watch mode is the
one thing that must not go into a CI step; the pin fix needs the unpinned override
removed from *both* jobs because criterion 4 applies to the whole file. The
`working-directory: ${{ github.workspace }}` form is the only one that works, because
`backend/api/routes.py` and `backend/main.py` both need the repo root on `sys.path`.

**Scope creep?** The pin-guard step is the one thing the six backlog criteria did not
ask for. The plan states this openly and justifies it (R-015 is the recurrence-prone
defect: "just add pytest to be safe" is exactly the line somebody re-adds, and nothing
in the repo would notice). I judge it a net positive - but only because the plan fixed
criterion 4 to use the *same* rule; see finding 1 for the two ways it can misfire and
why neither is a blocker.

**What did it break?** Nothing I could find. The removed job-level
`defaults.run.working-directory: backend` is fully compensated per-step (install and
test -> `backend`; guard and import gate -> the workspace root). The `provider-e2e`
job is untouched apart from the deleted unpinned install, which criterion 4 requires of
the whole file. The lockfile stays in sync. The `frontend` job's *name* is unchanged, so
any required status check already configured in branch protection keeps matching.

**The `provider-e2e` job - reachability, judged directly.**

Before this change the job was **unreachable by construction**: the workflow declared no
`workflow_dispatch` trigger, so `github.event_name == 'workflow_dispatch'` could never be
true and the job was dead code. After this change it is reachable **by a deliberate
manual dispatch only**, and still behind two gates I verified are byte-identical to
master's (`ci.yml:52-53` `if:`, `:54` `environment: provider-e2e`, `:55-57` `defaults`,
`:73-78` the `env:` block with `${{ secrets.OLLAMA_API_KEY }}` and the pytest
invocation). A push has `event_name == 'push'` and a pull request
`'pull_request'`, so **the credentialed job still cannot fire on either**.

So the change *increases* the reachability of a credentialed job: from "impossible" to
"one deliberate human click, subject to a repository variable and an environment". I
judge that acceptable, for three reasons: (a) it is a direct and required consequence
of backlog criterion 1, which asks for `workflow_dispatch`; (b) the residual gate is
unchanged and is a real gate, and the change touches no secret, no environment and no
variable; (c) the actor must already hold write access, which is strictly more power
than running one credentialed test job - and write access already allows running an
arbitrary `ci.yml` on a same-repo pull request, so the marginal exposure of the manual
trigger is small. The residual risk is **correctly recorded in three places**: the plan's
Open question 1, the implementer's finding 4, and `follow-ups.md:17`. I did not and
cannot read `vars.RUN_PROVIDER_E2E` from the checkout.

**The pin-guard step - judged on its merits.**

* *Is it a no-op on the merged file?* **Yes** - verified by executing the extracted
  `run:` block against the merged file: exit 0, no output, under both
  `$ErrorActionPreference='Continue'` and `'stop'`. It is not vacuous either: against
  master's file it exits 1 and names both offenders.
* *Can it match its own source?* **No, and structurally so.** Neither guard line's
  stripped form begins with a pip-install prefix (they begin with `$bad =` and
  `if ($bad)`), and the rule keys on "begins with" - a rule implementation necessarily
  carries the prefix as a quoted literal *inside* a longer line. Rule P on the merged
  file returns 0 offenders, and that run included the guard's own two lines. This is the
  defect the plan was redone for, and it is genuinely closed.
* *Can it false-positive on a legitimate future change?* **Yes, in one demonstrable
  class** - see finding 1. It is a wrong-message false positive on a change that
  contradicts the design, not a wrong-verdict one.
* *Is a guard that lives inside the file it guards a good idea?* It is forced by
  criterion 5 (no new file) rather than freely chosen, and the co-location is exactly
  what broke the plan's attempt 1. The honest trade-off: the subject and the instrument
  are the same file, so one commit can both add an unpinned install and neuter the
  guard - but that is true of every in-repo test, so it is not a special weakness. The
  guard does live in a job with no `if:` (`backend-tests`), so it really does run on
  every push and every pull request, and it scans the **whole** file, so it also
  protects the `provider-e2e` job's install line.
* *What breaks if the guard is wrong?* Every push and PR goes red, deterministically
  and within seconds, with the offending line printed. That is the right kind of red
  for this repository's thesis, and the remedy is one line in one file. I confirmed the
  failure is self-describing rather than mysterious: the error output names the exact
  offending text.

## Findings (most important first)

1. **`.github/workflows/ci.yml:26` - the guard's failure message is wrong for a
   legitimate future change.** Rule P's real predicate is "no `==`", so
   `python -m pip install "pytest>=7.4.4"` - a *version-constrained* install, which
   criterion 4's prose does not forbid - is flagged. Verified: the guard exits 1 and
   prints `unpinned pytest install: python -m pip install "pytest>=7.4.4"`, which is
   factually false. The same applies to `~=`, `!=` and `<` constraints, and the
   substring `pytest` also matches `pytest-cov` / `pytest-mock` / `pytest-xdist`
   (harmless here, since `pytest-cov==4.1.0` contains `==`). Practical exposure is low
   because the design makes `backend/requirements.txt` the single source of truth - a
   future edit that adds a `>=` install to `ci.yml` would contradict the design
   anyway - and the failure mode is a deterministic, self-describing red. **Not a
   criterion failure, not a blocker.** If the orchestrator wants it tightened, the
   cheapest fix is to reword the message to "installs pytest without an `==` pin"
   (or to accept any comparison operator in the predicate) - one line, one file, and
   the rule stays Rule P for the criterion check.

2. **`.github/workflows/ci.yml:26` - the guard's fail-safe on a missing or renamed
   workflow file depends on the runner's error preference.** Verified: if
   `.github/workflows/ci.yml` is not found, the guard exits **0** (silent green) under
   `$ErrorActionPreference='Continue'` and **1** under `'stop'`. GitHub's runner
   prepends `$ErrorActionPreference = 'stop'` to `pwsh`/`powershell` builtin scripts
   (actions/runner ADR 0277), so on the real runner the guard fails safe - but the
   property is inherited, not stated. **Not a blocker**; the one-word hardening
   `Get-Content .github/workflows/ci.yml -ErrorAction Stop` would make it
   unconditional.

3. **`.github/workflows/ci.yml:132-133` (pre-existing, deliberately out of scope) - the
   `tauri-build` job's "assert" is a no-op.** `run: Test-Path
   "src-tauri/target/release/sythion.exe"` writes `True`/`False` to stdout and the
   step exits **0 either way** - I simulated the runner's pwsh wrapper against a
   non-existent path and got step exit code 0. So the one job that builds the desktop
   shell does not actually gate on the shell binary. The plan put this job out of scope
   and no criterion covers it, so this is **not** a criterion failure of item 001 - but
   the item's title claims "CI actually gates this repository", and this job does not
   gate. Recommend a follow-up: change the step to `if (-not (Test-Path ...)) { throw
   ... }`.

4. **`backend/.env` (pre-existing; already escalated to item 006) - the repaired
   pipeline will be RED on its first real run.** A clean CI checkout has no
   `backend/.env` (`.gitignore:16`; `backend/core/config.py:175` loads exactly that
   path), so `backend/tests/test_setup_readiness.py:160` (`assert body["full_ready"] is
   True`) fails on the credential check, and the `backend-tests` job goes red for a
   reason that has nothing to do with item 001. This diff does not cause it and the
   plan correctly forbade fixing it here; the orchestrator has already escalated it to
   item 006. I re-state it because it changes what "item 001 delivered" means in
   practice: the pipeline will gate the repository, but it will not be green on day one.
   The `follow-ups.md:16` entry should name it explicitly, otherwise the first
   red run will be misread as a regression of this item.

5. **`.orchestra/follow-ups.md:16` (the orchestrator's file - a suggestion, not an
   edit) - name the expected *safe* outcome of a manual dispatch.** The implementer's
   proposed wording (its finding 10) was self-contradictory on this point - "a manual
   dispatch must be able to start the `provider-e2e` job ... confirm it is unset before
   dispatching" - if the variable is unset, the job does **not** start. The orchestrator's
   written line 17 avoids the contradiction ("confirm ... is NOT set to `1`"), and
   line 16 asks only that the jobs be observed. The observation would be sharper if it
   said what a *safe* first dispatch looks like: with `RUN_PROVIDER_E2E` unset, the
   `provider-e2e` job must be reported as **SKIPPED** - that is the safety check, and
   it is a different observation from "the credentialed job starts". I flag this only
   because the orchestrator copies the implementer's line; I did not edit the file.

6. **`.github/workflows/ci.yml:22` - the guard runs after "Set up Python" rather than
   immediately after checkout.** Cosmetic: it pays `setup-python`'s cost before it can
   fail a violation, and it makes the guard depend on an unrelated step succeeding.
   Moving it one step up is free and makes the "fails in seconds" property exact.
   Not a blocker; the plan placed it here deliberately (after the runtime is available
   and before the nine-minute install).

7. **`frontend/package.json:11-12` (informational) - the `frontend` job's name
   ("Frontend build + lint") now understates what the job does.** The plan kept it
   unchanged on purpose, so that a required status check already configured in branch
   protection keeps matching - the right call, and renaming it would be a breaking
   change to the branch-protection configuration. Flagged so that item 003 (which owns
   `docs/TESTING.md`'s "CI Pipeline" section) documents the job as it actually is.
