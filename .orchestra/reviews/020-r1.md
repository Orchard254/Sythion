## The two implementation details beyond the plan

1. **The loopback exemption in the probe's socket guard - justified, and it does not weaken this check.** It is **load-bearing**: with the guard refusing every connect, `asyncio.new_event_loop()` fails on Windows (`'ProactorEventLoop' object has no attribute '_ssock'` - the Proactor loop's self-pipe is a real loopback socket), which would kill the readiness file. It does not weaken the check as used: the readiness file drives a **fake** provider (`_Provider` in `test_setup_readiness.py`), no socket is created at all, and `network_attempts=0` in all three runs. The residual gap is only that the guard counts *non-loopback TCP connects* - a DNS lookup (`getaddrinfo`), a UDP `sendto`, or a connect to a local service would not be counted (see F3).
2. **The `.isolation-placeholder` in the scratch profile dir - right instinct, but it does not fence what its comment claims.** The comment says the placeholder stops "the legacy profile migration" from copying `~/.sythion` into the profile directory. Measured: in the **isolation-present** shape (runs 1 and 2 - the ones that matter) the isolation deletes `SYTHION_DATA_DIR`, so `data_dir()` resolves to `<scratch>/localappdata/Sythion (Synth)`, **not** `<scratch>/profile`; the placeholder is therefore in the wrong directory for that shape. I proved the gap: with the isolation active and `migrate_legacy_data_dir()` invoked, the legacy content **is** copied into `<scratch>/localappdata/Sythion (Synth)`. Today nothing happens, but for an unrelated reason: the readiness file builds `TestClient(app, ...)` **without a `with` block**, so the app lifespan never runs and `backend/main.py:87 migrate_legacy_data_dir()` is never called. The fence is accidental, not designed (F1).

## Findings (most important first)

1. **`backend/tests/test_env_isolation.py:156-161` (the `.isolation-placeholder`) - the fence is in the wrong directory for the shape that matters - MEDIUM, non-blocking.** In runs 1 and 2 the isolation deletes `SYTHION_DATA_DIR`, so the migration target is `<scratch>/localappdata/Sythion (Synth)`, which the placeholder does not cover; only the isolation-**removed** shape (run 3) has `<scratch>/profile` as the target. The scratch tree currently holds nothing but fakes only because the app lifespan never runs in the nested run (`TestClient` without a `with` block), not because of the placeholder - I measured that a `migrate_legacy_data_dir()` call in the isolation-present shape *does* copy the legacy directory into the scratch tree. **Fix shape:** also create `<scratch>/localappdata/Sythion (Synth)/.isolation-placeholder` (and keep the profile one), so both possible targets are non-empty; and/or redirect the child's `HOME`/`USERPROFILE` into the scratch tree so `backend/core/storage.py:LEGACY_DATA_DIR` (computed from `expanduser("~")` at import) points into the scratch as well - that closes it at the root. (Caveat if `HOME`/`USERPROFILE` are redirected: check that nothing in the nested path depends on the real user profile.)
2. **`backend/tests/test_env_isolation.py:416-419` (and `:437-440`, `:464-467`) - the raw child output is embedded in the failure message *before* the leak assertion runs - LOW.** `assert runN.returncode == 0, "...the output was:\n%s" % runN.output` renders the child's whole stdout/stderr, and `_assert_no_sentinel_leaked` is only reached later, so in the case where a sentinel *did* leak the value would already have been printed by the earlier assertion. Today every message is boolean-only and I verified no sentinel value appears in either shape, so nothing leaks - but the item's own contract is "no sentinel value is ever rendered", and this is the one place a value could escape. **Fix shape:** call `_assert_no_sentinel_leaked(run, label)` *before* the return-code assertion, and/or redact the two sentinel constants from `run.output` before embedding it in any message.
3. **`backend/tests/isolation_probe_template.py:75-96` - the guard counts only non-loopback TCP connects - LOW.** `socket.socket.connect` / `connect_ex` are patched; `getaddrinfo`, `sendto` (UDP) and any loopback connect to a local service are neither blocked nor counted, so `network_attempts=0` means "no non-loopback TCP connect attempt", not "no network I/O" (the plan's wording is stronger than what is enforced). **Fix shape:** patch `socket.getaddrinfo` and `socket.socket.sendto` as well, and/or rename the signal field to `non_loopback_connect_attempts` so the signal states exactly what it measures. (The readiness file creates no socket, so nothing exploits this today.)
4. **`backend/tests/isolation_probe_template.py:1-9` - the template is collected if it is named explicitly - INFORMATIONAL.** `python -m pytest backend/tests/isolation_probe_template.py --collect-only -q` reports "1 test collected": pytest collects a file named directly on the command line regardless of `python_files`, and the file contains a `test_` function. The repository's own run collects a **directory**, so the template contributes 0 (measured: 1628 -> 1629). If anyone runs it directly it errors out (empty `SIGNAL_PATH`). **Fix shape:** one line in the module docstring - "not a test module; do not run this file directly" - or move the probe body into a `probe.py` + a one-line `test_*.py` wrapper copied into the scratch tree.
5. **`plans/020.md:261-273` vs. the measurement - the plan's expectation of *which* run goes red is off by one - INFORMATIONAL, no code action.** The plan predicted that a repository-level deleted isolation turns **run 2** red; in fact **run 1** goes red first, because the process-environment sentinel (`SYTHION_SELECTED_MODEL`) is present in every run, not only in the `.env` run. The implementation is *stronger* than the plan (the check needs no `.env` at all), and the report's E6 agrees with my independent reproduction.
6. **`backend/tests/test_env_isolation.py:490-496` - a failure inside the `finally` replaces the original failure - INFORMATIONAL.** If the body fails and the scratch removal also fails, `pytest.fail` in the `finally` masks the first (and more informative) error. **Fix shape:** chain the removal error onto the original exception instead of raising a second one.
