## Is the new regression test meaningful?

`test_the_clean_settings_snapshot_survives_an_in_place_mutation`
(`backend/tests/test_setup_readiness.py:339-362`) is **meaningful, and it is the only guard in
this file that has teeth in a clean checkout.** Three measurements, all mine:

1. **Teeth against the exact regression it was written for.** Branch tip with **only** the
   one-line per-test copy reverted (`monkeypatch.setattr(settings, name, value)`; the diff is
   exactly `- list(value) if isinstance(value, list) else value` / `+ value`), in a **clean tree
   with no `.env`**: `1 failed, 10 passed`, the failure being
   `E AssertionError: assert 'C:/leaked-by-a-previous-test' not in ['C:/leaked-by-a-previous-test']`
   at `:357`. The test fails, and it fails **in a clean checkout**, which is where CI runs.
   This is a stronger claim than the implementer's own (their control ran in a tree with a
   `.env`); I re-ran it clean and it still fails. **The orchestrator's negative control is
   confirmed independently.**
2. **It is a tautology in ONE direction, and I measured it.** With the autouse isolation fixture
   **removed entirely** and a DUMMY `.env` present, the regression test still **PASSES**
   (`1 failed, 10 passed` - the failure being the *sibling* test
   `test_the_suite_does_not_inherit_the_local_env_file`, whose message again showed no value).
   The reason is structural: with the isolation gone, `settings.file_roots` is the singleton's
   own list and the snapshot is a copy of a *different* `Settings` instance, so "the leaked value
   is not in the snapshot" is trivially true. So the regression test detects "the snapshot is
   shared and mutable", and it does **not** detect "the isolation is gone".
3. **That gap is covered elsewhere, but not in CI.** With the isolation removed and a `.env`
   present, the sibling test fails - so in a tree with a `.env` the file as a whole is red. But
   with the isolation removed in a **clean** tree, the whole file is **green** (`11 passed`) -
   i.e. the isolation's absence is invisible on a CI runner. That is round 1's finding N4
   ("the isolation test is a discriminator in a tree with a `.env`, a tautology in a clean
   checkout"), unchanged by this redo, and the implementer states it honestly in the test's own
   docstring rather than overselling it.

**My judgement: meaningful, not a tautology, with one precisely-stated limit.** The test pins
the property it names ("the shared clean snapshot survives a test that mutates in place"), it
fails when that property is broken, and it is the only test in the file that fails in a clean
checkout. Its limit - it cannot see the isolation's own absence - is covered by the sibling test
where the sibling has teeth, and is a known, documented, non-blocking limitation of the item
(running the whole item on a CI runner still cannot detect a removed isolation). I would not
block on it; I would record it (finding 1 below).

## The scope question

**I still agree with round 1, and I re-derived it independently rather than inheriting it.**

**(a) The three-field scope is the backlog's own criterion 3**, not implementer scope creep
(`backlog.md:43` names `ollama_api_key`, `selected_model` and `file_roots`). Narrowing it to one
field would fix the one symptom and leave the class.

**(b) The ambient values are observationally inert.** Measured on the BASE code over the 16-file
set: `.env` absent -> `1 failed, 205 passed, 5 skipped`; DUMMY `.env` present -> `206 passed,
5 skipped`; the two outcome sets (211 triples each) differ in **exactly one** outcome -
`test_readiness_states`, failed -> passed. So no test's outcome depends on the ambient
`file_roots` or `selected_model`.

**(c) `file_roots = []` means the home+cwd fallback, so the isolation is STRICTER, not looser.**
`backend/tools/file_tools.py:181-207`: `roots = list(settings.file_roots or [])`; DB grants
REPLACE the env roots (`:198-199`); a non-empty list gets the repo root appended (`:200-205`);
**an empty list falls back to `[home, cwd]`** (`:207`). Measured in the base tree with the dummy
`.env`:

```
ambient settings.file_roots = ['C:\\Sythion\\dummy-root']
  BEFORE neutralisation: count = 2   ->  C:\Sythion\dummy-root , <tree>\backend
      includes home: False   includes cwd: False   includes backend dir: True
ambient settings.file_roots = []
  AFTER  neutralisation: count = 2   ->  C:\Users\orcha , <tree>
      includes home: True    includes cwd: True    includes backend dir: False
```

So under the isolation **more** paths are approved, never fewer: a test asserting a path is
REJECTED becomes *stricter* to satisfy, and cannot pass trivially - the opposite of the worry the
brief raised. The one direction that could hide a failure ("a path IS accessible becomes easier")
is empty in practice, by (b).

**(d) The decisive argument.** The isolation moves the developer's tree TOWARD the clean
checkout, i.e. toward exactly what CI sees; a test that can only pass with the developer's
ambient roots is a test that would be RED in CI, and the isolation surfaces that instead of
hiding it. **Conclusion: the scope is justified, bounded and in the direction the goal wants. I
would not narrow it.**
