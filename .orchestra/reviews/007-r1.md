## Does the guard close the hole?

**Yes, for the generic-credential namespace the product actually uses.**

* The **only** route to the vault in the whole repository is
  `backend/core/secrets.py` -> `win32cred.CredWrite` (`:77`) and
  `win32cred.CredDelete` (`:84`). Both are called as *module attributes* at
  call time (`win32cred.CredWrite(...)` after a function-local
  `import win32cred`), so a `monkeypatch.setattr(win32cred, "CredWrite", ...)`
  intercepts them. I grepped every `.py/.ps1/.bat/.js/.ts` in the tree
  (excluding `node_modules`/`.venv`/`site-packages`): there is **no** other
  `Cred*` call, **no** `from win32cred import CredWrite` (which would capture a
  direct reference and bypass the module patch), and **no** ctypes/advapi32
  credential route - the only `advapi32` use is `backend/tools/gui_tools.py:189-197`
  for token integrity level.
* The **packaged copy** `src-tauri/resources/backend/core/secrets.py` is
  byte-identical to `backend/core/secrets.py` (`git diff --no-index` -> empty),
  so the shipped product prefix is the same string the guard snapshots, and
  because the guard patches the `win32cred` *module* rather than the secrets
  module, even a test that imported the packaged copy would be intercepted.
* Other `win32cred` write APIs: `CredRename`, `CredWriteDomainCredentials`,
  `CredReadDomainCredentials` exist; `CredCreate` and `CredSet` do **not** exist
  in this build (`dir(win32cred)`). I measured the only plausible gap:
  `CredRename` on a `CRED_TYPE_GENERIC` credential fails with winerror **50,
  "The request is not supported"**, so a generic credential - the only kind the
  product writes - cannot be moved into the product namespace by a rename.
  `CredWriteDomainCredentials` writes DOMAIN credentials and cannot target the
  product's generic entry.
* **Scope boundary (real, but closed for today's suite):** the guard is
  acceptance-scoped, so a test *outside* `backend/tests/acceptance/` that wrote
  to the vault would not be caught. The implementer's master full-suite run
  with a product-target blocker recorded exactly **one** product-target attempt
  in the whole suite - the round-trip test - so the exposure is closed today.
* Reads are deliberately not intercepted (the plan's contract), and with the
  prefix patched the branch's round-trip test does not even *read* the product
  target.

## Is the self-check non-vacuous?

is unchanged - unfiltered enumeration + Python filtering. The misleading

## Is the exception type right?

Yes.

* `ProductCredentialWriteAttempt(AssertionError)` is caught by **no** handler
  in the path: `CredentialManagerStore.delete` catches only `pywintypes.error`
  (`secrets.py:85`), `get` catches only `pywintypes.error` (`:58`), `set`
  catches nothing at all, and `set_secret`/`delete_secret` catch nothing. So
  the delete path is not toothless - which is exactly why the implementer did
  not use `pywintypes.error`.
* The API path is not a swallow either: `routes.py:1942-1949`
  (`PUT /secrets/{name}`) calls `store_secret` with no `try/except`, and the
  acceptance app (built in the acceptance conftest) has no global exception
  handler - I measured it: the request raised `ProductCredentialWriteAttempt`
  straight out of the `TestClient`.
* Nothing in `backend/tests` uses `pytest.raises(AssertionError)` or
  `except AssertionError` (grep over the whole test tree: no match), so the
  chosen type cannot be swallowed by a test.
* pytest reports it as a **FAILED** test (not an ERROR), with a message that
  names the offending target and `request.node.nodeid` - I saw both in my own
  run.
* One caveat is recorded as finding 4 below: `backend/main.py:274`'s global
  `@app.exception_handler(Exception)` would convert the exception into a 500
  **if** a future acceptance test drove the write through `backend.main.app`.
  The write would still be blocked (the safety property holds); the test would
  just not go red. No acceptance test uses `main.app` today.

## Is the import-time snapshot correct?

Yes, and it is necessary - I verified the necessity directly rather than by
reading.

* `conftest.py:44` captures `secrets_module._CM_TARGET_PREFIX` at conftest
  **import** time (collection), before any test can patch it. `_cm_target()`
  (`secrets.py:32-33`) reads the module global at **call** time - that is what
  lets the round-trip test redirect the target, and it is exactly what would
  disarm a call-time guard.
* The "disarm attempt" - patch `_CM_TARGET_PREFIX` to the test prefix, then
  call `win32cred.CredWrite` with an explicit product target name - was
  **blocked**. A call-time read would have compared against the patched prefix
  and let it through.
* No other module can mutate the captured value: it is a module global of
  `backend.tests.acceptance.conftest`; nothing assigns to it, and
  `secrets_module._CM_TARGET_PREFIX` is a constant in `secrets.py` that only
  the round-trip test's `monkeypatch` touches (and restores). A test *could*
  deliberately `monkeypatch.setattr(conftest, "_PRODUCT_TARGET_PREFIX", "")`
  to disarm the guard; that is a self-inflicted edit of a test-only module and
  is noted, not objected to.
* The test's own snapshot (`test_secret_storage.py:35`) is a second, separate
  import-time capture. It must be separate from the patched attribute or the
  assertion at `:173` would be a tautology - and it is.

## Findings (most important first)

1. `backend/tests/acceptance/conftest.py:77` - the prefix comparison is
   **case-sensitive**, but Windows credential target names are not.
   **Measured:** writing `Sythion (Synth) [TEST]/caseprobe` and then
   `sythion (synth) [test]/caseprobe` produced **ONE** credential - the second
   write replaced the first, and the enumeration shows a single entry. A future
   test that wrote `sythion (synth)/ollama_api_key` would therefore land in the
   product's credential slot and would NOT trip
   `target.startswith(_PRODUCT_TARGET_PREFIX)`. Not reachable from the
   product's own code (the prefix is a constant) and nothing in the suite does
   it today, so this is **not** a criterion failure - but it is a one-line
   hardening: compare lower-cased.
2. `backend/tests/acceptance/conftest.py:89` - the guard **fails open** on a
   credential object it cannot read: `cred.get("TargetName", "") if
   hasattr(cred, "get") else ""` yields `""` for anything that is not
   dict-like, `""` passes the check, and the call is delegated. A non-dict
   credential carrying the product target would slip past. Fail closed
   instead (reject when the target cannot be determined). No such object
   exists in the repository today (`CredentialManagerStore.set` builds a plain
   dict), so this is hardening, not a criterion failure.
3. `backend/tests/acceptance/conftest.py:57-99` - the guard is
   acceptance-scoped, so a test **outside** `backend/tests/acceptance/` that
   writes to the vault is unguarded. Today's exposure is closed (the
   implementer's master full-suite run with a product-target blocker recorded
   exactly one product-target attempt in the whole suite - the round-trip
   test), but the boundary is real. Moving the guard to the root
   `backend/tests/conftest.py` is the right follow-up, and that file is still
   contended: item 002 edits `Makefile`, `pytest.ini`,
   `backend/tests/conftest.py`, `backend/tests/acceptance/test_gui_fixture.py`;
   item 006 edits `backend/tests/conftest.py`,
   `backend/tests/test_setup_readiness.py`. **Neither item touches item 007's
   two files**, and the acceptance conftest imports nothing those items change
   (`backend.models.database`, `backend.api.routes`, `backend.core.auth`,
   `backend.core.secrets`, `backend.tools.executor`,
   `backend.services.task_runner`). Item 006's new root-conftest autouse
   fixture neutralises `settings.ollama_api_key` / `selected_model` /
   `file_roots` only - it does not touch the secret store, and the round-trip
   test asserts on the STORE, not on settings, so the two items do not
   interact.
4. `backend/main.py:274` - the global `@app.exception_handler(Exception)` would
   turn the guard's exception into a 500 response if a future acceptance test
   drove a vault write through `backend.main.app` (the root conftest's
   `test_client` fixture). The write would still be blocked; the test would
   not go red. No acceptance test uses `main.app` today (grep: no match).
   Either raise a type the app's handler does not swallow, or state the
   constraint in the conftest docstring.
5. `backend/tests/acceptance/test_secret_storage.py:196` - `except Exception`

   or COM error would be reported as "the test-scoped credential was not found

   with a separate branch for anything else. Cosmetic - it still fails loudly.
6. `backend/tests/acceptance/conftest.py:88` - I checked the wrapper signature
   against the installed pywin32: `win32cred.CredWrite` here takes **at most 2
