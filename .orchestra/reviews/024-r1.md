## Effective guarded authority

`_effective_autonomy_is_guarded()` uses the exact runtime expression from the plan: `os.environ.get("SYTHION_AUTONOMY_LEVEL", core_config.settings.autonomy_level) == "guarded"`. It does not mutate the environment or settings.

- Env autonomous -> 409, before any write or DB mutation.
- Env guarded with settings autonomous -> 200 (runtime precedence is respected).
- Env unset with settings autonomous -> 409.
- Empty or unknown effective values -> 409.
- A forged persisted `autonomy_level='guarded'` cannot override an autonomous runtime configuration because the effective value is never read from `settings_metadata`.

## Atomic stage/rollback

`setup_safe_settings` validates authority first, then stages both `retention_days="90"` and `setup_safe_initial_config_applied="true"` with `set_setting` before a single `db.commit()`. Any exception during staging, flush, or commit triggers `db.rollback()` and returns bounded HTTP 500 without raw database detail. No success marker is written on a failed first application, and a previously committed marker/value remains unchanged because the transaction rolls back.

## Refresh honesty

`setup_readiness` now requires all three conditions:

- `get_setting(db, "setup_safe_initial_config_applied") == "true"`
- `get_setting(db, "retention_days") == "90"`
- `_effective_autonomy_is_guarded()`

A marker alone, wrong/malformed retention, or a non-guarded runtime now reports `safe_settings_ok=False` on every request. The existing `full_ready` and text-first checks are preserved, including STT/TTS absence.

## Frontend contract

The Continue handler:

1. calls `applySafeSettings()`;
2. throws if `result?.ok !== true`;
3. calls `refresh()`;
4. throws if `!canStartChat(report)` before `setStep(1)`.

This means an HTTP 200 with false `ok`, an API rejection, a failed refresh, or false safe readiness cannot advance to step 2. Optional microphone behavior is unchanged, and text-first setup still finishes without STT/TTS.
