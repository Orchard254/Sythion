## The two replacement assertions - are they real?

### Site 1 - `backend/tests/test_conversation_memory.py::test_post_task_intelligence_save_conversation_turn_verification`

The shipped test (`:628-641`) now asserts `len(turns) == 2` and `"Verification failed" in caplog.text`.

The assertion is not about the mock.
- The log assertion **can fail**, and I proved it rather than assuming it. Negative control: the same test body with the patched read-back session removed (so the real verification session finds the two committed turns) - result: `assert len(turns) == 2` **passes**, `assert "Verification failed" in caplog.text` **fails** with `AssertionError: assert 'Verification failed' in ''`. The assertion is therefore specific to the verification-failure branch, exactly as the plan claimed, and the pre-fix production code (no verification block -> no such warning) would go red on it.
- The `caplog` capture is pinned (`caplog.set_level(logging.WARNING, logger="backend.services.post_task_intelligence")`) and the module logger is a plain `logging.getLogger(__name__)` (no `propagate=False`), so the record is captured.
- **Nuance (F5)**: `assert len(turns) == 2` pins the *row count visible to the test's own session*, not their *persistence* - the query is on the same session, so pending (uncommitted) rows would also be returned. It also held in the negative control. The pair has teeth because of the log assertion; the count assertion on its own would not have caught the missing verification. The plan's phrasing "the commit half is observable in the test's own `turns` query" is therefore half true.

### Site 2 - `backend/tests/test_phase12_planning_learning.py::test_learned_planning_cannot_change_runtime_permissions`

The shipped test (`:362-400`) seeds one `Objective` row, snapshots every column of every goal row through a `goal_state()` helper that asserts the snapshot is non-empty, exercises the planning path (ten `DELEGATED_PLAN` outcomes plus a `select()` with a violated hard constraint) between the snapshots, and compares.

**F1 - (required) the comment above the site-1 assertion is now false.** `backend/tests/test_conversation_memory.py:633-635` still ends with "by checking that the verification log message was emitted (implicitly tested by no exception)", and the new explicit assertion `assert "Verification failed" in caplog.text` is four lines below it. The diff invalidates a pre-existing claim in a file the diff already touches - the same defect class this item exists to remove, and against `goal.md`'s "docs match the code" doctrine. *Fix shape*: delete the "(implicitly tested by no exception)" clause and the now-redundant "so we just verify the code path ran" sentence, e.g. "the verification log message is emitted (asserted below)". One line, no behaviour.

**F2 - (required) the failure message enumerates only three of the four guard positions.** `backend/tests/test_no_tautological_asserts.py:143-148` says "... in a boolean position (an operand of a conjunction or a disjunction, or the operand of a negation)". The rule also flags the **bare** literal - the assert's own test - which is the case the item is named after, and the message does not mention it. A reader hitting a bare-literal violation is told about a rule that does not describe their violation. *Fix shape*: add "or the assertion's own test" to the parenthetical. One line, message text only.

**F3 - (required) the docstring's opening rationale is false for two of the four shapes the rule now flags.** `backend/tests/test_no_tautological_asserts.py:3-6`: "the literal decides that position instead of the code under test, **so the assertion verifies nothing**". For `assert (x or True) and y` the assertion still verifies `y` (it reduces to the right operand), and for `assert not (x or True)` it verifies a *falsehood* (the outcome is fixed at false) - the docstring's own third paragraph (`:22-27`) says exactly that, so the file contradicts itself four paragraphs apart. Criterion 3 is about the claim matching the implementation, and the *rule* claim does; this sentence is a leftover of the old rationale and should go with it. *Fix shape*: reword to "... so the assertion does not check the property its shape suggests", or drop the clause - the third paragraph already carries the precise statement.

*Non-blocking observations (no change required, recorded for the trail):*

**F4** - the guard's test function is still named `test_no_assert_statement_disjoins_with_the_literal_true` (`:121`) although the rule now covers conjunctions and negations as well. Renaming would move the collected test id, which the plan forbids ("no test renamed"), so the name stays - but it is a claim too, and a future rename should be done deliberately.

**F5** - `assert len(turns) == 2` (site 1) pins the row count visible to the test's own session, not persistence (same-session query, autoflush), and it held in the negative control. *Optional strengthening*: read the turns back through a **fresh** session (`sessionmaker(bind=session.bind)`) so the assertion pins persistence, or state in the comment that the count is not a persistence check.

**F6** - site 2's comparison pins *persisted* state only: an uncommitted mutation is discarded by `db.expire_all()` and is not detected (measured). Correct semantics for "no goal mutation via planning"; a one-clause comment would make it explicit.

**F7** - `_source()` builds its placeholder map with `dict(zip(("or","true","and","not","assert"), _TAUTOLOGY_PARTS))` (`:117`). `zip` truncates silently, so adding a part to the tuple in the middle would *shift* the mapping (e.g. "and" -> the new part) rather than fail. *Fix shape*: an explicit dict of indices, or `assert len(parts) == 5`.

**F8** - `caplog.text` is the root handler's text, not the module logger's, so the assertion would also match an unrelated record containing the same phrase. *Optional*: filter `caplog.records` by `record.name == "backend.services.post_task_intelligence"`.

**F9** - the plan quotes 24 for "`not` over an operand that is not vacuous"; the measured figure is 145 (identical on base and branch). Only the violation count (0) is binding; the plan's number is wrong, not the code.
