## Findings (most important first)

**F1 (BLOCKING for ACCEPT - documentation only) `backend/tests/conftest.py:691-698` - the "Known constraint" paragraph states two behaviours that never co-occur in either client mode.**
It says: "A test that drives a vault write through ``backend/main.py.app`` gets a 409 ``VAULT_WRITE_BLOCKED`` response for it ... The exception itself still propagates out of the request, so such a test still goes red instead of passing silently."
- With the default `TestClient` (`raise_server_exceptions=True`) the caller never sees a response at all - the exception is raised out of the request.
- With `raise_server_exceptions=False` - the mode the item's own new file establishes as the way to observe the response - the caller does get the 409, but the exception does **not** propagate, so a test that asserts nothing passes silently.
Starlette 0.35.1's `ServerErrorMiddleware` sends the handler's response and then *always* re-raises (`starlette/middleware/errors.py`: "We always continue to raise the exception"), which is precisely why the two modes differ. The plan itself scoped the claim ("the exception still propagates out of a **default** `TestClient`", `plans/018.md:100-101`); the implementation dropped the qualifier. This paragraph is the guard's only documentation of its observable behaviour, and getting it wrong teaches future test authors the exact silent-pass failure mode this item exists to remove.
**Fix shape (exact text for the last two sentences of that paragraph, no code change):**
> A test that drives a **blocked** vault write through ``backend/main.py.app`` sees one of two outcomes, depending on the client: a default ``TestClient`` raises this exception out of the request, so the test goes red; a client built with ``raise_server_exceptions=False`` - or a real HTTP client - receives the 409 ``VAULT_WRITE_BLOCKED`` response and the exception does **not** propagate, so such a test must assert on the status to stay meaningful.

**F2 (LOW - same round) `backend/tests/test_vault_guard_exception_surfaces.py:15-28` - the module docstring presents the sentinel as an always-on proof.** It lists the sentinel among "three independent proofs are asserted ... the sentinel mode below makes the real Windows Credential Manager completely unreachable for the run", but the sentinel is opt-in (`SYTHION_VAULT_SENTINEL=1`) and is **not** armed in a normal run, so the third proof only exists in sentinel mode.
**Fix shape:** qualify that bullet, e.g. "* in sentinel mode (``SYTHION_VAULT_SENTINEL=1``) the real Windows Credential Manager is completely unreachable for the run - that proof is opt-in, because the acceptance round trip legitimately needs the real API."

**F3 (LOW - disclosed by the implementer; needs a follow-up record, not a code change) The vendored mirror `src-tauri/resources/backend/main.py` is now 33 lines behind `backend/main.py`.** Before this item the mirror was **byte-identical** to `master:backend/main.py` (both blob `ca49e74`) and the repo convention has been to update it in *every* commit that touched `backend/main.py` (`git log --follow` on the mirror shows it updated in `9347612`, `2469c09`, `9d93172`, `260b3aa`, `46dd0c5`, `6298465`, `49f12e4`, `0529fe2`, `6ce6660`); this is the first divergence.
