## The interceptor — cannot swallow an error, cannot corrupt a success, cannot leak

`frontend/src/services/api.ts:81-145` adds a **response** interceptor on the existing `apiClient` plus three module-private helpers (`messageOf`, `detailToText`, `errorReason`) and one interface (`ApiRejection`). **Nothing is exported**: the module's public surface is unchanged.

- **Cannot swallow.** The rejection handler's last statement is `return Promise.reject(error);`. `api.test.ts`'s `rejectedWith()` helper asserts the promise did **not** resolve and that the rejection is an `AxiosError`. My probe P10 confirms the rejection keeps `isAxiosError`, `status`, `response.status`, `code` and `config` — only `.message` is replaced.
- **Cannot corrupt a success.** The success handler is the identity `(response) => response`. Probe P11: `res.data` deep-equals the server's body, `res.status === 200`, the server's headers survive, and **no** `message` property is attached to the response.
- **Cannot leak the control token.** The message is built **only** from `error.response.data` — never from `config`, headers, URL or a raw body (`errorReason(body)` reads `body.detail` / `body.error` and nothing else). `getControlToken`, `configureBridge` and the request interceptor are byte-identical to master (the file is a pure `+65/-0` addition). Probe P12: after a rejection the request still carries `X-Control-Token`, and the message never contains it.
- **Never surfaces a raw body.** Probe: an HTML page, a Python traceback, a JSON array, and a JSON scalar string all leave axios's generic message intact (`Request failed with status code 500`); none of their content reaches the message. A structured `detail` is the backend's own sentence and is surfaced verbatim (trimmed); a `detail` **list** (FastAPI 422) becomes the `msg` fields joined with `"; "`; a `detail` object carrying `msg` becomes that `msg`; `detail` wins over the `error` slug; the slug is used when there is no `detail`; neither → axios's own message.

**The frontend test drives the real thing — and the simulation is faithful.** `api.test.ts` imports `apiClient from './api'` (the real module) and uses axios's own per-request `adapter` hook; there is **no** `vi.mock` anywhere in the file. I checked the simulation against the installed axios 1.19.0 source: `lib/core/settle.js` rejects with `new AxiosError('Request failed with status code ' + status, …, response)` where `response.data` is the **raw** body, and `lib/core/dispatchRequest.js`'s `onAdapterRejection` runs the default `transformResponse` over `reason.response.data` before the interceptor sees it. The test's `errorAdapter` reproduces that path exactly, so `error.response.data` is the parsed object a real server would produce — **no socket, no backend, no new dependency**. `AxiosError.message` is an own, writable, configurable data property (`lib/core/AxiosError.js`), so `error.message = reason` is legal and keeps the same error object.

## Findings (most important first)

**No required findings.** All four below are non-blocking; each carries a concrete fix shape for whoever wants it.

1. **`backend/api/routes.py:2201-2205` (the `_candidate` helper) — one previously-200 provider answer becomes a 502.** *Non-string provider text is now rejected rather than coerced.* The old inline parse let any truthy value through (`{"response": 7}` → `text = 7` → `str(7).strip()` truthy → **200** with `response_preview == "7"`; likewise `choices[0].message.content == 42` → 200, preview `"42"`). The new rule — *a candidate is taken only if its value is a `str`* — turns both into **502 "Inference returned an empty response"** (measured). This is **plan-mandated** (`plans/021.md`, "The rules that make the order deterministic": a number is *not* a candidate) and it is arguably more honest (a number is not the model's text, and a 200 with `response_preview="7"` was itself a small lie). It is, however, the single place where "the endpoint's contract is unchanged" has a narrow exception: **a status code can move 200 → 502 for a non-string provider answer**, and no test or report line mentions it. *Fix shape (either, one line):* (a) add one endpoint-level test to `backend/tests/test_onboarding_inference_response_shape.py` pinning `{"response": 7}` → **502**, so the narrowing is deliberate and visible; or (b) if the board wants the old leniency, change `_candidate` to `return str(value).strip() if value is not None else ""` — **but that re-admits exactly the truthy-garbage the plan rejects**, so (a) is the recommendation.
2. **`frontend/src/services/api.test.ts:146-177` (F8) — the second assertion cannot detect what its comment claims.** `headerKeys.push(Object.keys(config.headers))` snapshots the header **keys** of the very object that is later compared, so `expect(Object.keys(seen[0].headers)).toEqual(headerKeys[0])` only proves "no header was added or removed since the adapter ran" — it cannot see a header **value** mutated by the response interceptor (which holds `error.config`). 3. **`backend/api/routes.py:2263-2272` — the 502 **detail text** for a malformed body changed (the status code did not).** Under the old code a malformed `choices` (a dict) or a malformed `choices[0].message` (a str) raised inside the route and was mapped by the `except` block to **502 "Inference failed: 0"** / **502 "Inference failed: 'str' object has no attribute 'get'"**; the new code returns `""` and the route answers **502 "Inference returned an empty response"**.
