## The scope question

This is the question the brief asks me to answer carefully, so here is the evidence rather than an
opinion.

**The three-field scope is not implementer scope creep - it is the backlog's own criterion 3**
(`.orchestra/backlog.md:43`: "neutralises the ambient `.env`-sourced values (`ollama_api_key`,
`selected_model`, `file_roots`) for every test, so no future test can silently depend on a
developer's `.env`"). The implementer implemented exactly what the Scout wrote and the Planner
restated. So the question is not "did the implementer widen the brief" but "is the criterion right",
and here is my answer.

**(a) Is broadening to three fields justified?** Yes, and by the same argument that justifies the
item at all. `backend/.env` can supply ANY `SYTHION_`-prefixed field
(`backend/core/config.py:173-176` sets `env_prefix="SYTHION_"`), and the plan's own evidence says
the developer's file carries all three. An isolation that covers one field of three would leave the
other two leaking and would therefore not deliver the criterion's stated purpose ("no future test can
silently depend on a developer's `.env`"). Narrowing to `ollama_api_key` alone would fix the ONE
defect on the board while leaving the class of defect in place. The generalisation is the right
call, and it is bounded: exactly three named fields, one fixture, one line each.

**(b) Does replacing the developer's file roots with the clean default change what any test
observes?** I measured it rather than assuming it. On the BASE code, in the same scratch tree, with
a dummy `.env` carrying all three ambient fields versus with no `.env` at all, over an 18-file set
that includes every module that touches `file_roots`, `selected_model` or the settings store
(`test_file_roots_grants.py`, `test_settings_store.py`, `test_settings_api.py`,
`test_file_search.py`, `test_tools.py`, `test_memory_tools.py`, `test_new_tools.py`,
`test_health_api.py`, `test_phase6_model_selection.py`, `test_phase975_capabilities.py`,
`test_setup_readiness.py`, and six acceptance modules):

```
base, no .env   -> 219 triples, 1 failed (test_readiness_states)
base, dummy .env-> 219 triples, 0 failures
OUTCOME SETS EQUAL: False   -- the ONLY difference is:
   ('backend.tests.test_setup_readiness', 'test_readiness_states', 'failed') | ['passed']
```

So the ambient `file_roots` value and the ambient `selected_model` value change **nothing** that any
current test observes; the only ambient-dependent outcome in the whole set is the readiness test
this item is about. R-019's "exactly ONE test depends on the ambient state" is confirmed
independently.

**Do those tests assert against the ambient value or against their own fixture?** Against their own
fixture, in every case I could find. `backend/tests/test_file_roots_grants.py` has an
`empty_env_roots` fixture that sets `settings.file_roots = []` (`:30`) and three tests that
monkeypatch their own roots (`:59`, `:105`); `test_settings_store.py:101-130` monkeypatches
`settings.file_roots` in every case it asserts on it; `test_settings_api.py:60` does the same; the
acceptance modules monkeypatch `backend.tools.file_tools._approved_roots` directly
(`test_target_validation.py:68,79,90,102,113`, `test_canonical_file_checks.py:22`,
`test_file_mutations.py:18`, `test_action_approval.py:28,95,167,265`, `test_file_search.py:24`,
`test_tools.py:284,386`, `test_new_tools.py:29`, `test_cancellation.py:112`). The ONE test that
consumes the ambient roots is `backend/tests/acceptance/test_target_validation.py:216`
(`target = _approved_roots()[0]`), and it only needs *some* root to exist, which holds under both
configurations. **No file-root test asserts against the ambient value.**

**(c) Could neutralising `file_roots` make a test PASS FOR THE WRONG REASON?** I looked for exactly
this and it does not happen - but the mechanism is the OPPOSITE of what the brief anticipated, and
that is worth recording because the opposite risk is real and is only latent.

`backend/tools/file_tools.py:181-207`: `roots = list(settings.file_roots or [])`; DB grants REPLACE
the env roots when present (`:198-199`); if the list is non-empty the repo root is appended
(`:200-205`); **if the list is EMPTY the policy falls back to `[home, cwd]`** (`:207`). So
`file_roots = []` does not mean "no file access" - it means "the home directory and the current
working directory are approved". Measured in a scratch tree with a dummy `.env`:

```
approved roots BEFORE neutralisation (ambient file_roots set): count = 2
  includes home: False   includes cwd: False   includes backend dir: True
approved roots AFTER  neutralisation (file_roots = []):          count = 2
  includes home: True    includes cwd: True    includes backend dir: False
```

Consequences, in both directions:
* A test that asserts a path is REJECTED outside the roots becomes **stricter** to satisfy under
  the isolation (home+cwd admits more paths than a narrow configured set), so the isolation cannot
  make such a test pass trivially. The brief's worry - "a restriction test that would have failed
  with the developer's real roots now sees `[]` and passes trivially" - is therefore **not the
  mechanism**; the actual direction is the opposite.
* A test that asserts a path IS accessible becomes **looser** to satisfy under the isolation. That
  is the direction that COULD hide a failure, and I found no such test: every file-root test pins
  its own roots, and the measured outcome sets are identical.
* The single test that would be affected by a *narrow* ambient root set
  (`test_target_validation.py:216`) needs only a root to exist, and one always does.

**And the decisive argument, which is stronger than all of the above:** the isolation moves the
developer's tree TOWARD the clean checkout, i.e. toward exactly what CI sees. A test that can only
pass with the developer's ambient roots is a test that would be RED in CI - the isolation surfaces
that instead of hiding it. The one thing isolation can never do is make a test green in a way CI
would not reproduce, because after the isolation the effective configuration IS CI's configuration.
The scope is therefore **justified, bounded, and in the direction the goal wants.** I would not
narrow it to one field.

**What I would still change (non-blocking):** the conftest's comment presents `file_roots = []` as
"the clean value" without saying that `[]` selects the home+cwd fallback. A reader could easily
misread the isolation as "the suite has no file access". One sentence fixes it (finding N1).

## The provider_e2e carve-out

**The reasoning is correct and the carve-out is exactly as narrow as it needs to be.** I verified
both shapes the repository uses:

* `backend/tests/test_phase975_provider_e2e.py:53-61` and `backend/tests/test_phase10_provider_e2e.py:27-31`
  use a MODULE-LEVEL `pytestmark` list that includes `pytest.mark.provider_e2e` and
  `skipif(not _provider_ready())`. `_provider_ready()` (`:41-50`) calls
  `resolve_ollama_api_key(settings.ollama_api_key)` - a module-level expression, evaluated at
  IMPORT time, before any fixture can run. Without the carve-out the import-time gate would still
  see the developer's key (the gate passes) and the live call would then run with no credential -
  a confusing 401. The carve-out prevents exactly that. ✓
* `backend/tests/test_phase105_concurrency.py:962` and `backend/tests/test_phase1075_hardening.py:728`
  mark a single METHOD and skip at runtime unless `SYTHION_RUN_PROVIDER_E2E=1`. ✓

I probed the marker lookup directly in a scratch tree (never in the branch):
* a module-level `pytestmark = [pytest.mark.provider_e2e]` IS found by
  `request.node.get_closest_marker("provider_e2e")` (pytest walks the node chain, so the module's
  own markers are found) -> all tests in those two modules are exempt, which is intended;
* a method-level marker is found -> only that method is exempt; **its unmarked sibling in the same
  class is NOT exempt** and receives the clean value (probed: `get_closest_marker` -> `None`, and
  `settings.ollama_api_key == ""`). So the carve-out does not leak into the two large files that
  also contain many ordinary tests. ✓
* an ordinary test in a tree with a `.env` sees `""`; a `provider_e2e`-marked test sees the ambient
  value. ✓

**Is there a hole?** The carve-out is keyed on the `provider_e2e` MARKER, so the only items that
keep the ambient credential are items explicitly marked for live-provider use, and those are
skipped unless `SYTHION_RUN_PROVIDER_E2E=1`. The one coupling worth recording (finding N2) is that
the carve-out keeps the ambient value for the whole `provider_e2e` population, and
`.github/workflows/ci.yml:72-78` exports `SYTHION_OLLAMA_API_KEY` and `SYTHION_SELECTED_MODEL` in
the `provider-e2e` job - but that job runs ONLY `tests/test_phase975_provider_e2e.py -m provider_e2e`
(`:78`), i.e. exactly the exempted population, so the two facts cancel out today. If that job ever
runs more than that module, the exported variables would reach the whole suite, because the
isolation covers the `.env` FILE but not the process environment (finding N2). I did not run the
live provider path (the plan forbids it), so the "the opt-in live run still works with a real
credential" claim remains **unverified** - as the implementer also states.

`test_the_suite_does_not_inherit_the_local_env_file` is honest about itself: a discriminator in a

* **Tautology (a clean checkout):** with no `.env`, `Settings(_env_file=None)` and the singleton

I accept the limitation: the tripwire is worth having (it is what catches a future field being
dropped from `_LOCAL_ENV_FIELDS` or the fixture being refactored away, in the trees where that
matters), and the environment-level invariant - "the suite's outcome set is the same with and
without a `.env`" - is proved at the verification level instead, where it is meaningful. A
CI-meaningful guard would need a nested pytest run against a generated `.env`; that is a follow-up,
not a criterion failure (N4).

**But the test as written has a defect that must be fixed: it can PRINT the credential.** See R1.

## Findings (most important first)

1. **`backend/tests/test_setup_readiness.py:328-330` - the isolation test compares the credential
   BY VALUE, so its failure message prints the credential.** `assert core_config.settings.ollama_api_key
   == clean.ollama_api_key` renders both operands on failure. I removed the isolation fixture in a
   scratch copy (outside the repository) with a dummy `.env` present and got:
   `E AssertionError: assert 'dummy-not-a-real-credential' == ''` / `E + dummy-not-a-real-credential`.

   XML artifact. I verified which assertion shapes are safe and which are not, with a fake
   credential-shaped string:
   * `assert a == b` -> **echoes the value**;
   * `assert bool(a) == bool(b)` -> **echoes the value** ("where True = bool('sk-fake-...')") - so
