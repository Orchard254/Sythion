## The three defects to fix

### Defect 1 (blocking) - criterion 4's check fails the plan's own pin-guard step

Attempt 1 restates acceptance criterion 4 as:

> Check: `Select-String -Path .github/workflows/ci.yml -Pattern 'pip
> install.*pytest'` returns nothing.

and also proposes a new **pin-guard step** whose own source code lives inside
`ci.yml` and necessarily contains the words "pip install" and "pytest" on one
line. The orchestrator verified both failure modes with real commands:

```
A) criterion-4 check against a plausible inline guard
   Select-String -Path <guard.yml> -Pattern 'pip install.*pytest'
   -> 1 match: line 6: if "pip install" in line and "pytest" in line:

B) a natural guard implementation flagging ITSELF
   for line in open(".github/workflows/ci.yml"):
       if "pip install" in line and "pytest" in line:
           if "==" not in line: bad.append(line)
   -> self-flagged lines: 1
      if "pip install" in line and "pytest" in line:
```

So the guard **exits 1 on the merged file** - which attempt 1's own text
forbids ("it must be a **no-op on the merged file** (exit 0)") and which
attempt 1 itself lists as risk 5 ("a false positive that reddens every push")
- and criterion 4's check returns a match, so criterion 4 fails.

Both failures follow from the plan as written. The plan must specify ONE
matching rule and use it in BOTH places. Options you may choose between:

- **Drop the pin-guard step.** The backlog criteria do not require it. Criterion
  4 is about the file's content, and the Reviewer checks the content. This is
  the simplest resolution and it removes a mechanism that can redden every
  push.
- **Keep the guard, and specify its matching rule so it cannot match itself** -
  for example, only consider lines whose stripped form *begins with* the pip
  invocation, so the guard's own source (which is indented and not a command
  line) is never a candidate. Then restate criterion 4's check with the SAME
  rule, so both agree.

Whichever you choose, the corrected plan must contain a line that states the
matching rule once and says both the guard and criterion 4's check use it.
Then **verify it yourself**: write the rule out, apply it to your own proposed
`ci.yml` text, and show the result in the plan. A plan whose acceptance
criterion contradicts its own proposed file is what we are fixing.

### Defect 2 (blocking) - criterion 4's stated proof may be impossible locally

Attempt 1's criterion-4 proof is:

> in a clean venv, `python -m pip install -r backend/requirements.txt` then
> `python -m pytest --version` -> `pytest 7.4.4`

The local interpreter is CPython **3.14.7**. `backend/requirements.txt` pins
`pyaudio==0.2.14`, `vosk==0.3.45` and `whispercpp==0.0.17`; those need to build
from source when no wheel matches the interpreter, so a clean-venv install of
the whole file on 3.14.7 is likely to fail - and attempt 1's own risk 6
already says so. The Implementer must not be sent into a proof that cannot
produce its evidence.

The proof attempt 1 ACTUALLY used, and which does work, was a throwaway venv
with **only the pinned test tooling** installed (`pytest==7.4.4`,
`pytest-asyncio==0.23.3`), using `--system-site-packages`. Restate the proof
that way, and state separately that the CI-side `pip install -r
requirements.txt` on Python 3.11 cannot be exercised locally and belongs in
the follow-up.

### Defect 3 (minor) - the guard is an addition the criteria did not ask for

Attempt 1 adds a mechanism that the backlog criteria do not require, while
criterion 5 forbids any new file - so the guard must live inside `ci.yml`,
which is exactly what creates Defect 1. Make the plan explicit about whether
the guard is kept because it earns its place, and if it is kept, say what
breaks if it is later wrong (a red pipeline on every push) and why that is
acceptable. If you cannot make that argument, drop it.
