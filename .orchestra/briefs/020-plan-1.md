## The hard part - read this carefully

Criterion 1 asks for a test that **spawns a pytest subprocess against a scratch
copy of the tree** with a generated `backend/.env` holding a sentinel
`SYTHION_OLLAMA_API_KEY`, and asserts the isolation neutralises it - and that
**removing the isolation makes that subprocess run fail**. That second half is
the whole point: the check must have TEETH against a DELETED isolation, and
that is exactly what the 006 verifier could not achieve.

Your plan must therefore say, concretely:

- How the scratch tree is produced (which files are copied, how the generated
  `.env` is written, where the scratch tree lives, and that it is removed).
  Copying the whole tree is expensive; say what is the minimum that makes the
  subprocess meaningful, and why.
- What the subprocess RUNS (which pytest invocation, which test file(s), with
  what working directory and which environment), and what its OUTPUT must show
  for the isolation to be considered WORKING. Give the exact expected signal -
  e.g. a sentinel-specific assertion - so the check is not "the run passed".
- **How the NEGATIVE control works**: the plan must specify how the test proves
  that WITHOUT the isolation the subprocess run FAILS (or shows the sentinel).
  If that requires mutating the scratch copy's conftest (e.g. deleting or
  neutering the autouse fixture in the SCRATCH tree only), say so - the scratch
  tree is disposable, the repository's own conftest must not be touched by the
  test.
- How long the subprocess may take and how the test bounds it (a timeout), and
  what happens on a timeout (fail, not hang).
- The test must perform NO network I/O and must NOT touch a real profile
  directory or the real user database. Say how that is guaranteed (e.g. the
  scratch tree's `SYTHION_DATA_DIR`).
- Whether the subprocess needs the repository's dependencies to be importable
  and how that is guaranteed (the same interpreter, the repository root on
  `sys.path`).
