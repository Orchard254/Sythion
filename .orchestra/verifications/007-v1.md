## The central claim, verified independently

**My route** (designed by me, not re-run from the implementer's or the
Reviewer's reports): a pytest plugin installed **outside the repository**
(`C:\Users\orcha\AppData\Local\Temp\opencode\ver007-harness\vspy.py`, loaded
with `-p vspy` and `PYTHONPATH`) that installs **two** recording layers:

1. an **API layer**, immediately above the real `win32cred.CredWrite` /
   `CredDelete` - anything it records reached the credential API boundary;
2. an **ATTEMPT layer**, installed in a `pytest_runtest_setup` hookwrapper
   whose post-yield code runs *after* the fixtures, i.e. after the guard's
   autouse fixture has already patched `win32cred`. It therefore wraps the
   guard's own wrapper and sees **every** call the test makes, the ones the
   guard rejects included.

The plugin is also a **hard safety interlock**: a product-prefixed target is
never delegated to the real Windows API (it is recorded and refused), so no
run started with it could touch the product's credential even if the guard
were broken.

## Findings

1. **The claim holds, and it holds for the right reason.** The branch does
   not merely *fail* to write the product target - it never attempts it.
   The whole-suite attempt-layer record (0 product-prefixed attempts over
   1611 tests) distinguishes that from "the write happened and was undone",
   which is the failure mode a before/after enumeration cannot see and which
   master exhibits.
2. **The guard blocks before the real vault, and that is measurable.** The
   attempt layer records 3 product-prefixed attempts while the API layer
   records 0 of them. The interlock and the `VSPY_DELEGATE=0` setting mean
   the real Windows API was unreachable for every target in that run.
3. **The guard fires against master's own offending test file**, not only
   against a synthetic probe - it is not a stub.
4. **The guard is complete for the namespace the product uses, in both
   spellings and on both operations.** I re-grepped the tree myself: the
   only route to the vault is `backend/core/secrets.py` -> `win32cred.CredWrite`
   (`:77`) / `CredDelete` (`:84`), both called as module attributes at call
   time, and there is **no** `from win32cred import CredWrite` anywhere that
   would capture a direct reference and bypass a module-level patch.
5. **The guard's scope boundary is real and still open** (the Reviewer's
   finding 3, which I confirm by measurement). The guard is an autouse
   fixture in `backend/tests/acceptance/conftest.py`, so a test **outside**
   that directory that wrote to the vault would be unguarded. I measured
   this directly: the **same** probe file, run from outside the acceptance
   tree, is **not** protected - it passes (exit 0) and the product target
   **reaches the credential API layer** (my interlock refused it, so the real
   vault was still untouched):

   ```

   layer stack: ('ver007-harness/probe_outside.py::test_...', 'api_write', 'api_delete')
   attempt-layer calls: 1   -> attempt write 'Sythion (Synth)/ollama_api_key'
   api-layer calls:     1   -> api REFUSED-write 'Sythion (Synth)/ollama_api_key'
   ```

   Today's exposure is nonetheless closed - my whole-suite spy over **1611**
   tests recorded only **2** credential operations in the entire backend
   tree, both test-scoped, and the master full-suite run under the fake

6. **A pre-existing native crash occurred in my first full-suite run**
