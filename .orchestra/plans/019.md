## The problem

**What exists today.**

`backend/tests/test_no_tautological_asserts.py` (140 lines, two test functions,
committed by item 004 as `4d827c0`) is a guard that fails the suite when an
`assert` under `backend/tests/` is unconditionally true. Its detection rule is
exactly, and only, this (`:50-66`):

> * the `assert` node's `test` is an `ast.BoolOp`;
> * that `BoolOp`'s `op` is `ast.Or`;
> * at least one of `BoolOp.values` is an `ast.Constant` whose value is `True`.

The rule is **top-level only**. It is a syntactic check of the assert's
immediate operands, and it stops at the first level: a nested `ast.BoolOp` is
an operand, not a `Constant`, so `assert x or (y or True)` is invisible to it.
A bare `assert True` is not a `BoolOp` at all, so it is invisible too.

**Why that is a hole, and exactly which shapes.**

R-027 (`.orchestra/reports/000-research-4.md:122-158`) names four shapes that
defeat the guard. Measured against the real tree (script below), each is
unconditionally degenerate and each is invisible to the current rule:

| shape | semantically | visible to the current rule? |
|---|---|---|
| `assert (x or True) and y` | reduces to `assert y` - the `True` makes the left operand constant | **no** |
| `assert not (x or True)` | `not True` - the outcome is constant (always false) | **no** |
| `assert x or (y or True)` | always true | **no** |
| `assert True` | always true | **no** |

Two honest notes about that table, because the plan's claim must match the
implementation (Gate 4, and acceptance criterion 3 of this item):

* `assert (x or True) and y` is **not** literally "unconditionally true" in
  Python's semantics - `(x or True)` is always true, and `True and y`
  evaluates to `y`, so the assert reduces to `assert y`. It is still a
  degenerate assertion, because a literal `True` was pasted into a boolean
  position, and the backlog's acceptance criterion 1 requires it to be
  flagged. The detector's claim must therefore be about the *syntax* (a
  literal `True` in a boolean position), not about the *three-valued outcome*.
* `assert not (x or True)` is unconditionally **false**, not true. It is also
  not something that can sit unnoticed in a green tree (it would make the
  suite red), which is why it is safe to flag it.

**The over-claim this item exists to remove.** Item 004's plan said the AST
rule "is a superset of the literal `... or True` text pattern"
(`.orchestra/plans/004.md:125`). That is false for the four shapes above; the
004 Reviewer recorded exactly that (`.orchestra/critiques.md:197`: "the
detector misses NESTED `or True` ... and a bare `assert True`, so the plan's
claim ... is FALSE as written"). The item-004 implementation was correct
against its own acceptance criterion ("a top-level `or True`"), so 004 stays
green - but the guard is a canary, not a proof, and the plan's claim was
wider than the code. This item closes the gap and rewrites the claim to match.

**What the rule becomes (the decision - unchanged from round 1).**

> **The guard-position rule.** A node is a *guard position* of an assert's
> test if it is reachable from the test by descending **only** through:
>
> * `ast.BoolOp` (both `ast.And` and `ast.Or`) - via any of its `values`;
> * `ast.UnaryOp` whose `op` is `ast.Not` - via its `operand`.
>
> Every other node is an **opaque leaf**: the traversal does not descend into
> it. In particular a `ast.Compare` is opaque - its `left` and `comparators`
> are not guard positions - and so are `ast.Call`, `ast.Subscript`,
> `ast.Attribute`, `ast.Lambda`, and every container literal.
>
> An assert is **vacuous** iff a guard position of its test is
> `ast.Constant(value=True)`. Equivalently, recursively:
>
> ```
> _is_tautology(node):
>     if node is ast.Constant(value=True):      -> True
>     if node is ast.BoolOp (And or Or):        -> any(_is_tautology(v) for v in node.values)
>     if node is ast.UnaryOp(op=ast.Not):       -> _is_tautology(node.operand)
>     otherwise                                 -> False
> ```
>
> Where a literal `True` counts: the assert's own test (a bare `True`); any
> operand of an `and` or an `or`, at any depth; and the operand of a `not`.
>
> Where it does **not** count, and these must stay legal or the suite goes
> red on legitimate code: a `True` used as a **comparison operand**
> (`assert x is True`, `assert flag == True`, `assert (a and b) is True`,
> `assert r.verified_success is not True`); a `True` **inside a call**
> (`assert f(x or True)`, `assert any(v or w for v in vs)`); a `True` inside a
> subscript or a container; and a `not` whose operand is anything but a
> vacuous expression (`assert not x`, `assert not (x and y)`).

On "grouping" (named in acceptance criterion 1): Python's AST has **no node
for parentheses**, so grouping is transparent - `(x or True) and y` parses as
`BoolOp(And, [BoolOp(Or, [Name x, Constant True]), Name y])` and the
recursion handles it without any extra case. `ast.Expr` never wraps an
assert's test (it only appears in expression statements), so there is no third
structural wrapper to traverse. The rule therefore has exactly two traversal
steps: `BoolOp` and `Not`.

**The exact replacement** (this replaces the `assert True` line; the two

```python
def test_learned_planning_cannot_change_runtime_permissions(db):
    # Planning selector has no pathway to alter runtime policy — assert no side effects on Goal state
    from backend.models.database import Objective
    # No goal mutation via planning
    goal = Objective(id="sec_perm_goal", title="runtime-permission invariant",
                     status="active", priority=3)
    db.add(goal)
    db.commit()

    def goal_state():
        rows = db.query(Objective).all()
        # a non-empty snapshot is required: an empty one would make the
        # comparison below vacuously true
        assert rows, "the seeded goal row is missing; the invariant would be vacuous"
        return {
            row.id: {c.name: getattr(row, c.name) for c in Objective.__table__.columns}
            for row in rows
        }

    db.expire_all()
    before = goal_state()

    # Strong learned evidence for the most privileged strategy, then a selection.
    store = PlanningOutcomeStore(db)
    for i in range(10):
        store.record(planning_strategy=PlanningStrategy.DELEGATED_PLAN.value,
                     task_class="goal", goal_id="sec_perm_goal",
                     outcome="SUCCESS_VERIFIED", verified_success=True,
                     evidence_refs=["goal:sec_perm_goal"])
    sel = PlanningPolicySelector(db)
    sel.select(task_context={"task_class": "goal", "goal_id": "sec_perm_goal"},
               hard_constraints=[{"strategy": "DELEGATED_PLAN", "violated": True,
                                  "reason": "capability not granted"}])

    db.expire_all()
    assert goal_state() == before
```

**Why each part is there (so a reviewer can check it, not take it on faith):**

* the **seeded goal row** gives the comparison something to compare - without
  it the table is empty and `before == after` is trivially true;
* the `assert rows` inside the helper makes that failure mode **loud**: an
  empty snapshot fails the test instead of passing it;
* the **ten recorded outcomes plus the `select()` call** exercise the planning
  path under maximum pressure (ten verified successes for the most privileged
  strategy, with a violated hard constraint) - the state comparison is only
  meaningful if the code under test actually ran;
* `db.expire_all()` before **both** snapshots forces both sides to be read
  from the database, so the comparison is against persisted truth and not
  against an in-memory object that merely *looks* unchanged;
* the comparison covers **every column** of the row (via
  `Objective.__table__.columns`), including `updated_at`, whose
  `onupdate=datetime.utcnow` would move on any ORM-level update - and it
  compares the **keyed dict**, so a row *added* or *deleted* by the planning
  path is caught as well as a row *mutated*;
* the hard constraint is the same one the sibling capability test uses, and it
  keeps the selection deterministic.

### The rule for a site that cannot be fixed

**Both sites are fixable**, and the evidence above is the proof - so this rule
is stated for completeness and for the reviewer, and it is **not** invoked.

If a future site (or, hypothetically, one of these two) turns out to be
unfixable without a change outside the three files of this item, the plan's
rule is:

1. **Do not add an exemption.** The guard ships with **no** exemption
   mechanism - not a constant, not a comment marker, not a line-number list, no
   stale-entry check, no over-use check. An exemption inside a guard that
   exists to make vacuous assertions impossible is self-defeating: it
   enshrines the very thing the guard forbids and adds a policy mechanism to
   justify it.
2. **Narrow the assertion instead.** The smallest honest alternative is to
   replace the placeholder with the narrowest assertion that is *actually
   observable* in the surrounding code (for example, assert the specific
   side-effect that the code under test really has, rather than the property
   the name suggests). A narrower true assertion is acceptable; an unasserted
   invariant is not.
3. **If even that is impossible, the item does not ship.** The guard's claim
   would be false, and a false claim in a guard is worse than the debt it
   hides (this is the defect class item 004 was criticised for). The correct
   move is to defer the item (or to widen the file set through the board),
   **not** to weaken the rule. Deferral is the honest outcome; a silent
   exemption is not.
4. A `pytest.skip` with a reason, or an `xfail`, is **not** an acceptable
   alternative here: both leave the placeholder in the tree, and the guard
   would still flag it - they hide the problem from the scanner instead of
   from the reader.

**What the test would have caught before** (both sites): see above - the
pre-fix/verification-removal case for site 1, the goal-mutation case for
site 2, each demonstrated with a negative control.

## Risk

- **R1 - the rule is too strict and turns the suite red on legitimate code.**
  *Measured exposure, not assumed:* the strict rule's hits over the whole
  tree are **2** today, both of them the two placeholders this item **fixes**;
  after the fix the count is **0**. The 307 comparison-operand asserts, the
  9 compares with a `BoolOp` side, the 10 `BoolOp`s whose `True` is buried in
  a comparison, the 194 call-topped asserts and the 24 `not`-over-other
  asserts are all untouched by the rule. *Detection:* criterion 4's
  whole-tree run (the implementer re-runs the scanner and reports the
  numbers); the negative list in the self-test, which fails the moment the
  traversal starts descending into a `Compare` or a `Call`; and the two edited
  files' own run (`63 passed`). The single most dangerous implementation
  mistake - descending into `ast.Compare` - is caught by the negative probes
  *and* by the whole-tree count.
- **R2 - the rule is too weak and the hole stays open.**
  *Detection:* the four probes P1-P4 each assert exactly one hit, so a rule
  that keeps the old top-level-only behaviour fails three of them (P2, P3,
  P4) immediately; the scratch probe file must make the guard fail with four
  violations. The de-tautologised twins stop the opposite failure (a rule
  that flags everything) from passing silently.
- **R3 - the guard flags itself.** This is the risk item 004's plan already
  had to handle, and the new rule widens it (the guard's own asserts are now
  subject to a recursive rule). *Detection, four layers:* (a) the tree scan
  already asserts that the guard's own file is among the scanned files, so
  the guard is checked against itself on every run - measured today at **0**
  hits on the guard file under the new rule; (b) the new probes' assertions
  are written in `Compare` form, which the rule treats as opaque, so they
  cannot trip it; (c) the guard file keeps **0** literal occurrences of the
  four forbidden sequences, so a *textual* scan of the tree does not match
  the guard either (measured: 0 / 0 / 0 / 0 today, and the implementer must
  re-measure after the change); (d) the docstring is prose and is not an
  `ast.Assert` node, so rewriting it cannot trip the rule. The two
  replacement assertions in the two edited files are also `Compare`-form or
  bare-name, so the tree scan stays green on them.
- **R4 - a replacement assertion is vacuous in a different spelling.**
  This is the risk the orchestrator asked to be named, and it is the reason
  neither site is allowed to keep a placeholder. *Detection, and why each
  replacement cannot be vacuous:*
  - **Site 1.** `assert "Verification failed" in caplog.text` compares two
    independently produced values (the captured log text and a literal); it
    cannot be true "by construction", and the **negative control** (the same
    production call without the mocked read-back) shows it becomes **False**
    there - measured this round. The supporting `assert len(turns) == 2`
    pins a committed row count, not a tautology.
  - **Site 2.** `assert goal_state() == before` compares two snapshots taken
    from the database, but a snapshot comparison *can* be vacuous if the table
    is empty - so the helper asserts `rows` is non-empty (an empty snapshot
    **fails** the test rather than passing it), the row is seeded, and the
    planning path is actually exercised between the two snapshots. The
    **negative control** (mutating `goal.status` before the comparison) was
    executed and the mutation **was detected**.
  - *No spelling of the placeholder survives the guard.* The rule is
    syntactic, so a future edit that appends a literal `True` to either
    replacement (for example `... == before or True`) is flagged by the
    guard on the next run - the replacement cannot silently regress into a
    tautology in a different spelling. The rule's known blind spot is a
    constant that is not the boolean `True` (for example `assert 1`); that
    shape does not exist in the tree today (**0** measured) and neither
    replacement uses it.
- **R5 - a replacement assertion is wrong and the test fails for the wrong
  reason.** *Named per site, with its mitigation:*
  - *Site 1, coupling to a production log string.* The assertion matches the
    stable discriminator `"Verification failed"`, not the full sentence, and
    the capture level is pinned with `caplog.set_level`, so a root-logger
    change cannot silence it. If production is ever reworded, the test fails
    loudly - and because this item may not touch production, the honest
    response is to update the test in the same change as the reworded
    message, not to weaken the assertion. The alternative implementation
    (patch the module logger and assert on the call) is recorded in the
    plan as the fallback if a reviewer rejects `caplog`.
  - *Site 1, coupling to the "two rows per task" contract.* `assert len(turns)
    == 2` pins a contract that `ConversationTurn`'s own docstring states
    ("Each completed task produces two rows"). A deliberate change to that
    contract must update this test in the same change - that is a true
    coupling, not a brittleness.
  - *Site 2, coupling to the goal model's columns.* The snapshot is built
    from `Objective.__table__.columns`, so a renamed or added column cannot
    cause an `AttributeError`; it is picked up automatically.
  - *Site 2, the "wrong reason" failure.* A failure of `assert rows` inside
    the helper means the seed is missing - the message says so explicitly, so
    a reviewer is not left guessing.
- **R6 - the rule's semantics are an over-approximation, and the docstring
  must say so.** An `and` whose left operand carries a literal `True` reduces
  to its right operand, and a literal `True` under a `not` is always false -
  neither is "unconditionally true" in Python's three-valued logic. The rule
  is nevertheless the one acceptance criterion 1 requires, and it is the
  conservative direction (false positives over false negatives). *Detection:*
  criterion 3 - the docstring must not use "unconditionally true" as the
  rule's description, and must state the over-approximation explicitly. This
  risk is about the *claim*, not the behaviour, and it is the exact class of
  defect item 004 was criticised for.
- **R7 - the collected test count moves.** A new test function would change
  the suite's collected count and every baseline table that quotes it.
  *Prevention:* the probes go **inside** the existing self-test function, and
  the two site fixes are **replacements inside existing test functions**; no
  test function is added, removed, renamed, skipped or marked. Checkable by
  `python -m pytest backend/tests --collect-only -q` -> still **1628**, and
  this module still collects **2**.
- **R8 - the machine's native flakiness masquerades as a delta.**
  goal.md records two native fault kinds (COM `0x80040155` bursts and a
  sqlite3 `0xC0000005` access violation) that kill full-suite runs
  unpredictably. *Detection:* a full-suite comparison for this item must be
  re-run before any delta is attributed to the change, and a failing run must
  be checked for those markers. The guard module itself is a pure-AST,
  no-I/O test and cannot trigger either fault.
- **R9 - the tree scan silently stops scanning.** Already guarded by the
  existing `MIN_FILES_SCANNED` floor and the "the guard's own file was
  scanned" assertion. Round 1's exemption machinery added a second way for
  the scan to look green; removing the exemption machinery **removes** that
  way, so the scan has exactly one way to look green - and it has to be green
  honestly.
- **Rollback:** `git revert` the single commit - the change is three test
  files, no production behaviour, no schema, no configuration, no fixture.
  The two fixed sites revert to their placeholders, which the reverted guard
  does not flag (the old rule is top-level-`or`-only), so the revert is

- **Should `caplog` be used, or should the module logger be patched?** Both
  work. `caplog` is idiomatic and asserts on the *message*, which is what the

  *some* warning happened and is therefore weaker. This plan specifies
  `caplog`; a reviewer who prefers the alternative may switch, and the
  negative control must then be re-run.
- **Should the rule also catch other vacuous asserts** (`assert 1`,
  `assert [True]`, `assert "x"`)? Measured: **0** bare non-`True` constant

  `ast.Constant(True)` specifically. Out of scope; a follow-up could widen it
  if a future tree grows such shapes.
- **Should `assert not True` really be flagged?** Decision taken: **yes**.
  It is degenerate (the outcome is fixed by the literal), it cannot sit in a
  green tree unnoticed, and criterion 1 requires the recursion through

  syntactic, not "unconditionally true" (R6). A reviewer who prefers a
  different framing can change the wording, not the behaviour.
