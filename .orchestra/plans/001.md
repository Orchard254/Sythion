# Plan for 001

## The problem

This repository's release-confidence signal is its CI pipeline, and that pipeline
has never gated this repository. Four independent defects, one file (plus one
`package.json` script), one branch. Adopted from `research.md` as **R-001**,
**R-002**, **R-014**, **R-015**.

1. **R-002 - the trigger misses the branch.** `.github/workflows/ci.yml:3-6` is
   `on: push: branches: [main]`. The repository's only branch is `master`
   (`git branch -a` -> `master`, `remotes/origin/HEAD -> origin/master`,
   `remotes/origin/master`; there is no `main`, local or remote). A push to
   `master` therefore skips the entire workflow. There is no `workflow_dispatch`
   either, so the workflow cannot even be started by hand.
2. **R-001 - the one gate that exists is broken.** The `backend-tests` job sets
   `defaults.run.working-directory: backend` for every step
   (`.github/workflows/ci.yml:12-14`), then the import-gate step at `:35-36`
   runs `python -c "import backend.main; import backend.api.routes"` *inside*
   `backend/`, where the `backend` package is not importable -> exit 1,
   `ModuleNotFoundError: No module named 'backend'`. The identical command from
   the repository root exits 0 (`make build-backend`, `Makefile:62-63`, and
   `goal.md`'s "Build" command are the repo-root form). The gate is red for a
   reason that has nothing to do with the code.
3. **R-014 - the frontend suite is never executed.** The `frontend` job
   (`:72-93`) runs exactly three steps: `npm ci`, `npm run lint`,
   `npm run build`. There is no `vitest` step anywhere in the file, although
   the repository carries a real, green suite: 5 files / 49 tests
   (`frontend/src/lib/*.test.ts`). `frontend/package.json:11` maps `"test"` to
   bare `vitest` (watch mode), which is exactly the command that must not be
   put in a CI step.
4. **R-015 - CI overrides the declared pytest.** `:24-28` and `:58-62` run
   `python -m pip install -r requirements.txt` (which pins `pytest==7.4.4` and
   `pytest-asyncio==0.23.3`, `backend/requirements.txt:43-44`) **and then**
   `python -m pip install pytest pytest-asyncio` with no version constraint
   (the offending lines are `ci.yml:28` and `ci.yml:62`). The unpinned second
   install wins, so the version CI exercises is never the version the
   repository declares.

The result is a pipeline that contains a broken gate, skips the branch the
repository actually uses, never runs half the test suite, and tests a pytest
version nobody declared. This is the "release and operator readiness" and
"verification before claims" half of `goal.md` (`docs/QUALITY_GATES.md:34-44`,
`:88-97`) failing in the most literal way possible.

### Facts the plan relies on (established; do not re-derive)

- `backend/api/routes.py:15-21` imports **absolutely** (`from
  backend.models.database import ...`). Therefore the import-gate command
  *must* be executed with the repository root on `sys.path`. The defect is the
  working directory, **not** the import target; changing the target to
  `api.routes` would break, because `api/routes.py` itself needs `backend.*`
  to be importable. The command stays byte-identical and the directory moves.
- The import gate as written, run from the repository root, exits 0.
- `frontend/src/lib/*.test.ts` contains no `document.` / `window.` / `jsdom`
  usage, so the suite runs in vitest's default `node` environment - no
  `environment: jsdom` and no new devDependency are needed.
- `frontend/package-lock.json` is `lockfileVersion: 3` and its `packages[""]`
  entry records `dependencies` / `devDependencies` but **not** `scripts`.
  Changing the `scripts` block therefore does not desynchronise the lockfile
  and `npm ci` keeps working.
- The pinned test toolchain is viable. Measured on this machine in a throwaway
  `--system-site-packages` venv with `pytest==7.4.4` + `pytest-asyncio==0.23.3`

  - `python -m pytest backend/tests/test_work_state.py

- The `frontend` script split is verified: with the proposed

### Defect 3 (minor) - the guard was an addition the criteria did not ask for

*What was wrong.* Attempt 1 added a mechanism the backlog criteria never
required, while criterion 5 forbids any new file - which is precisely what
forced the mechanism inside `ci.yml` and created Defect 1.

*What changed.* The guard is **kept**, and the argument for keeping it is now
made explicitly. It earns its place because R-015 is the one defect of the
four that is *recurrence-prone*: the unpinned install line is exactly the kind
of line somebody adds again ("just add pytest to be safe"), and nothing in
this repository would notice. Criterion 4 is checked by a human reviewer at
review time - once - whereas the guard checks the same rule on every push and
every pull request, forever.

*What breaks if the guard is later wrong, and why that is acceptable.* Every
push and pull request goes red with a message naming the offending lines.
That is acceptable because the failure mode is **deterministic and
self-describing**: it is a text scan of a file that is already in the
checkout - no network, no clock, no environment, no flake - so a wrong rule
produces an immediate, named failure rather than a mystery, and the remedy is
one line in one file. It is also the *correct* kind of red: the whole thesis
of this item is that a gate which is red for the wrong reason (the import
gate) or silently green (the missing vitest step) is worse than a gate that
is red for the right reason. The rule is verified below against the exact
file this plan describes (zero offenders, exit 0) **and** against `master`
(two offenders, exit 1), so it is neither vacuous nor self-triggering, and the
guard is placed *before* the install step so a violation fails in seconds
instead of after a nine-minute dependency install.

The cost is one `Get-Content` of a ~120-line file: milliseconds.

## How it will be proven

All commands below are run from `C:\Sythion\sythion` unless a directory is
named. "master" means the current `master` commit; "the branch" means
`orchestra/001-ci-gates-repo` with this item's change applied.

### Rule P - the one matching rule

> **Rule P.** In `.github/workflows/ci.yml`, a line is a **pip-install line**
> if its stripped form (leading whitespace removed) **begins with**
> `pip install` or `python -m pip install`. A pip-install line is an
> **offender** if it mentions `pytest` (which also covers `pytest-asyncio`)
> and does **not** contain `==`.
>
> **The guard step and criterion 4's check both apply exactly this rule, to
> the same file.** The guard is the rule executed by the pipeline; the
> criterion-4 check is the rule executed by the Reviewer and the Verifier.
> There is no second, looser pattern anywhere in this plan.

Because "begins with" is the discriminator, the guard's own source is never a
candidate: a rule implementation necessarily mentions the prefix as a quoted
literal *inside* a longer line, never at the start of a stripped line. This
is verified, not assumed - see "Corrections from attempt 1".

### Test that pins the invariant

Three checks live inside the workflow itself (so they re-run on every push and
every pull request), and each of them is also runnable locally as a plain
command. All are part of the change described below.

1. **The import gate** (`.github/workflows/ci.yml`, `backend-tests` job) is the
   committed check for the directory invariant: if the working directory ever
   regresses to `backend/`, the step goes red with
   `ModuleNotFoundError: No module named 'backend'`. It is already the
   repository's declared build gate (`Makefile:62-63`, `goal.md` "Build").
2. **The vitest step** (`.github/workflows/ci.yml`, `frontend` job) is the
   committed check for "the frontend suite is part of the pipeline": it fails
   if the suite regresses and it fails (by hanging / non-zero exit) if the
   script is left in watch mode.
3. **The pin guard** - a new step in the `backend-tests` job, placed after
   "Set up Python" and before "Install dependencies" - is the committed check
   for R-015. It is **Rule P, verbatim**: it reads `.github/workflows/ci.yml`
   from the checkout and fails the job if Rule P finds an offender, naming
   the offending lines. It uses only PowerShell built-ins (no PyYAML, no new
   package) and it is a **no-op on the merged file** (exit 0) - verified in
   "Corrections from attempt 1". The equivalent local check the Verifier runs

4. **The full-suite run under the pinned toolchain** - the Implementer runs
   the whole backend suite with `pytest==7.4.4` / `pytest-asyncio==0.23.3`

## Risk

### What is most likely to break

The characteristic failure of this item is **a workflow that looks right and
still does not gate**. Ranked:

1. **The trigger still misses the branch.** The most likely silent failure is
   a `branches:` list that names the wrong branch, or a malformed `on:` block
   (wrong indentation, or `branches` nested under the wrong key) that GitHub
   rejects or ignores. Mitigation: criterion 1 is a text check on the file,
   and the file is read back in the item report. Note also that a
   `workflow_dispatch:` trigger only becomes usable once the workflow exists
   on the **default branch** - so the hand-dispatch half of criterion 1 can
   only be exercised after the merge (criterion 6 / follow-up).
2. **A step runs from the wrong directory.** This is R-001 itself, and it has
   a second, subtler form: a step-level `working-directory` composed with a
   job-level default can resolve somewhere unexpected. The plan removes the
   job-level default from `backend-tests` so that every `run:` step states
   its own directory, and the import gate states the repository root
   explicitly. The negative control (the same command from `backend/` -> exit
   1) is run and recorded, so the verifier can see that the gate is
   directory-sensitive rather than accidentally green.
3. **The vitest step is green locally and red (or hung) on the runner.**
   Concrete causes and how this plan pre-empts them: the script is left as
   bare `vitest` (watch mode) - pre-empted by `"test": "vitest run"`; the
   tests need a DOM environment the runner lacks - ruled out, the five test
   files use no `document.`/`window.` and run in vitest's default `node`
   environment, and no `jsdom` dependency is added; `npm ci` failing before
   the test step - pre-existing, not introduced here; vitest 1.6.1 needing a
   newer Node than 20 - not the case. Note explicitly: the plan does **not**
   rely on `CI=true` to suppress watch mode - vitest would auto-disable
   watching in GitHub Actions, which would make a watch-mode script *look*
   correct in CI while still hanging every developer's machine. The script is
   explicitly non-watch so both behave the same.
4. **The pinned pytest (7.4.4) is not the pytest the suite was last green
   with.** Switching CI from "unpinned latest" (8.x on a runner) to the
   declared 7.4.4 changes what CI exercises. Probed on this machine in a
   throwaway venv with `pytest==7.4.4` + `pytest-asyncio==0.23.3`:
   `test_work_state.py` + `test_phase105_concurrency.py` +
   `test_phase1075_hardening.py` run green (105 passed, 5 skipped, exit 0),
   and the **full suite collects the identical 1609 tests** (exit 0). The
   Implementer must additionally run the **full** suite under the pinned
   toolchain and record the counts against the pre-change baseline
   (1564 passed / 45 skipped / 1609 collected). If the pinned toolchain
   surfaces a genuine incompatibility, the correct response is to **report**
   it - the pin may not be quietly relaxed, because the pin is what
   criterion 4 requires.
5. **The pin-guard step misfires and reddens every push.** The rule is
   verified against the exact file this plan describes (zero offenders, exit
   0) and against `master` (two offenders, exit 1), so it is neither
   vacuous nor self-triggering; the guard's own source lines are provably not
   candidates. The residual risk is a *future* edit that adds a pip-install
   line the rule misreads - which is the intended behaviour, not a bug. If
   the guard is ever wrong, the failure is deterministic, immediate and
   self-describing (it names the offending line), and the remedy is one line
   in one file. The Implementer must still run the guard locally and record
   exit 0 before proposing the branch.
6. **The very first real run of this pipeline fails for reasons that have
   nothing to do with this item.** This workflow has never gated this
   repository, so nothing in it has ever been executed on a runner. The
   measured facts: `backend/requirements.txt` pins `pyaudio==0.2.14`,
   `vosk==0.3.45` and `whispercpp==0.0.17`; `vosk` is a universal
   `py3-none-win_amd64` wheel and `pyaudio` has a **cp311** wheel, but
   **`whispercpp==0.0.17` has no wheel for cp311 (or for cp314) and must be
   built from source on the runner** - so the `Install dependencies` step may
   fail on the first run, on a package this item does not touch. The suite
   may also behave differently on Python 3.11 than on the local 3.14.7, and
   the `tauri-build` job may need a toolchain the runner lacks. All of these
   are **pre-existing** conditions of a pipeline that never ran, and none of
   them may be fixed inside this item (criterion 5 forbids touching
   `requirements.txt`; criterion 6 forbids running the workflow). If they
   appear, the Implementer records them in the item report and they become
   follow-up entries. The one thing that is forbidden is responding by
   weakening a gate.
7. **The `provider-e2e` job starts running when it must not.** Adding
   `workflow_dispatch` makes that job reachable. Its own gate is unchanged
   (`github.event_name == 'workflow_dispatch'` **and**
   `vars.RUN_PROVIDER_E2E == '1'`, plus the `provider-e2e` environment and
   the injected secret), so it still cannot fire on a push or a pull
   request. The residual risk is that the repository variable is *already*
   set to `'1'` in the GitHub settings, which is not visible from the
   repository - see "Open questions". The Implementer must not dispatch the
   workflow and must not touch the variable, the environment or the secret.

### Rollback

One commit, two files, no state and no data. `git revert <commit>` on the
branch, or `git checkout master -- .github/workflows/ci.yml
frontend/package.json`. Nothing else to undo: no schema, no migration, no
installed artefact, no secret, no published artefact. The only residual after
a revert is the `npm test` behaviour change, which reverts with the same
commit. If a bad run lands on `master`, revert immediately - the pipeline
returns to "never runs", which is the pre-change state and no worse.

## Sensitivity

**`infra`.**

* Behavioural sensitivity is low: the change touches the CI definition and
  one `npm` script. No runtime module, no HTTP contract, no schema, no
  auth/token/secret path, no release payload, no new dependency. Nothing on
  `goal.md`'s off-limits list is touched or read-modified.
* But the *outcome* of this item cannot be observed from inside the
  repository. `.github/workflows/**` is in the orchestrator classifier's
  EXTERNAL path list, so this item is EXTERNAL tier: the in-repo change
  merges, and the act of watching the workflow run on GitHub is an outside
  action that nobody performs in this run. That is why criterion 6 exists and
  why it is recorded as a follow-up rather than attempted.
* Because the sensitivity is `infra`, the Implementer must pin the invariant
  before asking for a review: the invariant is
  **"the workflow file's declared trigger, step working directories, install
  sources and test commands are exactly what this plan specifies"**, and it is
  pinned by the three committed checks in `ci.yml` (import gate, vitest step,
  pin guard) plus the five-part reproduction above, all of which are executed
  and recorded before the branch is proposed.
