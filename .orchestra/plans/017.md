# Plan for 017

## The problem

`DbEventLedger._counter_table_checked` caches a *transactional* fact as if it were a permanent
capability of the instance. The current code executes

```
CREATE TABLE IF NOT EXISTS task_event_sequences (...)
```

inside the caller's transaction and immediately sets `self._counter_table_checked = True`.
That creation is part of the transaction it runs in, so a caller rollback removes the table
while the instance-level bit survives. The next `append_event` on the same `DbEventLedger`
trusts the bit, skips creation, and lets `_ALLOCATION_SQL` fail with
`no such table: task_event_sequences` (surfaced as `EventSequenceAllocationError`).
The same cached `True` can also survive a failure inside the allocation/savepoint loop.
`db_manager.py` already owns this schema object at migration time; `events.py` treats its
existence as a one-time boolean instead of re-establishing it within the append's own
transaction.

## How it will be proven

- Reproduction (fails on base, passes on the branch):
  1. Start from a database where `task_event_sequences` is absent but `task_events`
     and `tasks` exist. Append once, then `session.rollback()` so the creation rolls back.
  2. On base: the second `append_event` on the same ledger ends in
     `EventSequenceAllocationError` whose cause is `no such table: task_event_sequences`;
     no event persists.
  3. On the branch: the second `append_event` returns `1`. After the caller commits,
     reopening the database shows one `task_events` row with `sequence_num = 1` for that task,
     proving transactional participation survived.

- Invariant-pinning tests (new regression tests; each must fail before the change and pass after):
  - `test_counter_table_not_stuck_variant_a_caller_rollback`: (a) a successful
    `append_event` that the caller rolls back must leave the next append on the
    same ledger able to allocate and persist.
  - `test_counter_table_not_stuck_variant_b_failed_allocation`: (b) an allocation
    failure inside the savepoint loop (`EventSequenceAllocationError`) must not prevent
    the next append once the inducing fault is removed. The test must assert the
    error was raised and that no partial row survived.
  - Both tests must check the persisted result by committing and re-reading through a
    fresh `DbEventLedger`, not only an in-memory count, so they cannot pass for the wrong reason.
  - The tests must name the variant they exercise (the variant is part of the test name).

- Acceptance criteria, restated objectively:
  1. The regression tests above fail on the base tree and pass after the change.
  2. Variant (a) caller-rollback-after-successful-append and variant (b) failed-allocation
     are both covered and individually named.
  3. `git diff --name-only` lists only `backend/runtime/events.py` and the new test file;
     nothing under `backend/models/` or `backend/migrations/`; no change to
     `backend/core/db_manager.py:128-131`; the `uq_task_events_task_sequence` index definition
     is unchanged.
  4. `append_event` and `event_history` signatures are unchanged. `_to_dict`
     keeps exactly these keys: `id`, `event_type`, `event_data`, `sequence_num`, `created_at`.
  5. `backend/tests/test_event_ledger_sequence_invariant.py`,
     `backend/tests/test_runtime/test_event_ledger_concurrency.py`, and the new regression
     tests remain green for 10 consecutive runs; the full suite keeps the pre-change
     passed/skipped counts on CPython 3.14.7.

- Existing tests that must remain green:
  `test_multi_append_preserves_earlier_pending_rows`,
  `test_latest_sequence_accounts_for_pending_rows`,
  `test_migration_idempotent_and_counter_floor`,
  `test_event_ledger_concurrency_kernel_ordering_still`, and all `@pytest.mark.concurrency`
  entry points using temp `DatabaseManager` databases.

## The change

- The only production file to edit is `backend/runtime/events.py`. The new regression tests
  live in one additional test file under `backend/tests/` (the concurrency test directories
  are acceptable). No model, migration, schema, API, or `_to_dict` change is permitted.

- Replace the cached boolean guard at the top of `append_event` with a transaction-resident
  existence check:
  - Query `sqlite_master` in `self._session` for `task_event_sequences` in the same
    transaction that will perform the allocation.
  - If the table is absent, execute the idempotent `CREATE TABLE IF NOT EXISTS
    task_event_sequences (...)`.
  - Do not promote `_counter_table_checked` to `True` as a fact that survives a rollback.
    Keep the instance attribute initialized to `False` for compatibility, but do not make
    correctness depend on it.

- Because the check and the possible creation are evaluated inside the append transaction,
  a caller rollback causes the next append's existence query to see the table as absent
  and recreate it. On a migrated database the query returns present, so no DDL runs on the
  normal append path.

- The allocation loop, savepoint, retry, and `EventSequenceAllocationError` behaviour are
  otherwise unchanged. Do not alter `latest_sequence`, `event_history`, or `_to_dict`.

- `_counter_table_checked` remains available as a compatibility field but is no longer
  the gating condition; if an implementation chooses to retain it as a cache, it must be
  reset to `False` on `EventSequenceAllocationError` and must not be relied on across calls
  whose transactions may have rolled back.

Illustrative logic only (not code to paste):

```
table_present = SELECT 1 FROM sqlite_master
                WHERE type='table' AND name='task_event_sequences'
if not table_present:
    CREATE TABLE IF NOT EXISTS task_event_sequences (task_id ... , next_seq ...)
# then run the unchanged ALLOCATION_ATTEMPTS loop
```

## Risk

- A fix that always re-runs `CREATE` can hide a genuine `db_manager` migration failure
  because the append path would recreate the table anyway. Detectability: keep the creation
  conditional on an existence query rather than unconditional DDL, keep `db_manager.py`
  untouched as the schema owner, and include both a migrated-database case (table already
  exists before append) and a non-migrated case in the tests. The migration must still be
  exercised independently by existing migration/integration tests.
- A fix that merely flips `_counter_table_checked` without transactional participation
  can pass a shallow test. Detectability: variant (a) forces an actual `session.rollback()`
  after a successful append on a table that did not exist before the call; the test then
  commits the second append and verifies the row through a fresh session.
- Per-append existence query adds one read against `sqlite_master`. This is small, but on
  a fresh database several writers can race through the creation branch. Detectability:
  reuse `CREATE TABLE IF NOT EXISTS`, rely on SQLite's writer serialization and the
  existing busy timeout, and exercise the concurrency invariant test for ten consecutive runs.
- `latest_sequence` and `event_history` already tolerate a missing table by catching
  exceptions. Keep them side-effect free (no schema creation) so reads cannot mask a missing table.

## Sensitivity

- Sensitivity: sensitive
- Domain: data
- Why: the event ledger is the audit/replay substrate. A cached flag that survives a
  legitimate caller rollback turns a successful transaction abort into a hard
  `no such table` failure on the next append.

## Open questions

- Whether `_counter_table_checked` should be removed entirely or retained as a
  compatibility field is an implementation detail; keeping it initialized to `False`
  avoids breaking any introspection code, while correctness must no longer depend on it.
- The precise mechanism used by tests to induce the savepoint-loop failure (monkeypatching
  the allocation SQL, lowering `ALLOCATION_ATTEMPTS`, or a colliding row) is left to the
  test author; the plan requires the test to name the variant it exercises and to assert that
  no partial event survived.
- If a reviewer prefers the stricter option of clearing the flag only on allocation failure,
  that option does not by itself close variant (a), because no allocation failure occurs after
  a successful-but-rolled-back append. The recommended transaction-resident existence check is
  the one that closes both variants.
