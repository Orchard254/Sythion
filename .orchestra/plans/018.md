# Plan for 018

Item: 018 - "The vault-write guard must not be swallowed by the FastAPI global
exception handler" (R-026).
Role: planner. Design only - no implementation, no stubs, no branch, no commit.

## The problem

**What exists today.**

- `backend/tests/conftest.py:622-742` installs the autouse, function-scoped
  `_forbid_product_credential_writes` guard. It snapshots the product prefix
  (`secrets_module._CM_TARGET_PREFIX` -> `"Sythion (Synth)/"`) at conftest
  IMPORT time, wraps `win32cred.CredWrite` / `win32cred.CredDelete`, and
  raises `ProductCredentialWriteAttempt` (`backend/tests/conftest.py:652-659`,
  an `AssertionError` subclass) **before** delegating to the real API
  (`conftest.py:732-741`). Reads (`CredRead`) are deliberately not
  intercepted.
- `backend/main.py:274-285` registers `@app.exception_handler(Exception)`.
  In Starlette 0.35.1 a handler registered for `Exception` becomes the
  `ServerErrorMiddleware` error handler (`starlette/applications.py:84-110`),
  so it answers *every* unhandled exception with
  `500 {"error": "INTERNAL_ERROR", "detail": str(exc), "code": "500"}`.
- The conftest docstring already states the consequence
  (`backend/tests/conftest.py:683-687`): a test that drove a vault write
  through `backend.main.app` "would get a 500 response instead of this
  exception - the write would still be blocked, but the test would not go
  red".

**Why it is still a real hole (and a precise, narrower one than the brief
assumes).**

Starlette's `ServerErrorMiddleware` sends the 500 response and then **re-raises**
the exception (`starlette/middleware/errors.py`: "We always continue to raise
the exception"). Consequences, measured on this machine (see "How it will be
proven"):

- A `TestClient(app)` built with the default `raise_server_exceptions=True`
  already fails the test with `ProductCredentialWriteAttempt` - the exception
  escapes into the test. The guard is not fully "swallowed" in that mode.
- A real HTTP client (uvicorn) receives the generic 500 body and nothing else.
- A `TestClient(app, raise_server_exceptions=False)` - the mode that observes
  the *response contract* - receives the generic 500 and nothing else.

So the defect is precise: **the HTTP outcome of a blocked vault write is
indistinguishable from the HTTP outcome of any other fault.** The guard
degrades from "a check that names itself" into "a circuit breaker whose
failure looks like a crash". The R-026 exposure is latent (no test drives
`main.app` for a secrets write today) but it is one test away.

**Measured today (base tree), with the real guard and the real production
route, and with `win32cred.CredWrite`/`CredDelete` replaced by sentinels
BEFORE the guard was installed so the real vault was unreachable:**

| request | observed response |
|---|---|
| `PUT /api/v1/secrets/ollama_api_key` (real `CredentialManagerStore`) | `500 {"error":"INTERNAL_ERROR","detail":"test <nodeid> attempted to write the product credential target 'Sythion (Synth)/ollama_api_key'. ...","code":"500"}` |
| same request, default `TestClient` | raises `ProductCredentialWriteAttempt` out of the request |
| same route, a store whose `set()` raises `RuntimeError` | `500 {"error":"INTERNAL_ERROR","detail":"simulated vault failure","code":"500"}` |

The sentinel standing in for the real Windows Credential Manager was reached
**0 times** in every run above.

**The trap the fix must not fall into.** `ProductCredentialWriteAttempt` is
defined in a TEST file. `backend/main.py` is PRODUCTION code and must never
import from `backend/tests/`. The fix therefore needs a contract that both
sides can honour without an import in either direction.

**The shape chosen (one shape, stated once).**

> **The vault-write-violation marker contract.**
> `backend/main.py` defines the constant
> `VAULT_WRITE_VIOLATION_ATTR = "sythion_vault_write_violation"` and treats an
> exception as a *vault-write violation* exactly when that exception exposes a
> truthy attribute of that name. The global exception handler maps such an
> exception to HTTP **409** with the body
> `{"error": "VAULT_WRITE_BLOCKED", "detail": <the exception's message>, "code": "409"}`.
> Every other exception keeps the existing generic 500 response, byte for byte.
> `backend/tests/conftest.py` declares that attribute on
> `ProductCredentialWriteAttempt`. Neither side imports the other.

Why this shape and not the alternatives:

- **Not a production->test import.** The marker is a *name*, not a type. The
  production side never sees `backend.tests`. Grep-proof: no module under
  `backend/` outside `backend/tests/` may import `backend.tests` after this
  change, and none does today.
- **Not a test->production import either.** The guard stays self-contained.
  Importing the exception type from `backend.main` into `backend/tests/conftest.py`
  would drag the whole application (routers, executors, logging configuration)
  into every pytest session at conftest-import time, and it would need a new
  production module to live in - which acceptance criterion 4 forbids.
- **Not "the guard raises an `HTTPException`".** That alternative was measured
  and rejected: when the violation is an `HTTPException` subclass, Starlette's
  `ExceptionMiddleware` answers it and the exception **never reaches**
  `ServerErrorMiddleware`, so it is never re-raised. A test that PUT a secret
  through the app and did not assert the status would then get a 409 and pass
  silently - i.e. the fix would *remove the guard's teeth* in exactly the mode
  (`raise_server_exceptions=True`) where the guard is loudest today. The marker
  shape keeps both: the response is distinct **and** the exception still
  propagates out of a default `TestClient`.
- **Marker, not `isinstance`.** An `isinstance` check would need a shared class,
  i.e. an import in one direction or a new production module. The attribute
  protocol is a standard Python idiom, is one line on each side, and is pinned
  by a test so the two spellings cannot drift.

## Risk

- **R1 - "a fix that turns every 500 into something else weakens the error
  contract."**
  *Detection:* the new branch is entered only on a **positive** marker check
  (an exception that explicitly declares itself a violation), so a generic
  exception cannot be diverted by accident. `test_genuine_fault_on_the_same_route_is_still_a_generic_500`
  drives the *same* endpoint with a genuine `RuntimeError` and asserts
  `500` + `INTERNAL_ERROR` + `"500"` - measured identical on base and on the
  fixed handler. The diff review shows the 500 branch is untouched, and the
  full-suite per-test outcome comparison (criterion 5) catches any other
  response change.
- **R2 - "a fix that makes the guard raise a type the handler turns into a
  400 silently could still hide the write."**
  *Detection:* the regression test asserts the **exact** status (`409`), the
  **exact** error slug (`VAULT_WRITE_BLOCKED`), the **exact** code (`"409"`)
  and that the guard's own message (naming the product target) is in
  `detail` - a generic 400 or a silent 2xx fails on at least one of those.
  It also asserts `status != 500` and `not 2xx` explicitly. The marker branch
  returns a `JSONResponse` from the global handler; it is not an
  `HTTPException`, so FastAPI's own 400/404/422 handling cannot intercept it.
  And `test_vault_write_violation_still_raises_out_of_a_default_test_client`
  pins that the violation is still *loud* (the exception escapes a default
  `TestClient`), so "blocked but quiet" is impossible in either client mode.
- **R3 - "the new test itself becomes a write path to the real vault."**
  *Prevention, three layers:*
  1. The test deliberately drives the **product-prefixed** target
     (`Sythion (Synth)/ollama_api_key`) - the one target the guard blocks -
     so the test's write attempt is stopped by the guard *before* the
     `win32cred` call (`conftest.py:732-741`). The test never writes to a
     test-scoped target either; it proves the *block*, not a round trip.
  2. The test proves the block happened: the `CredWrite` spy records the
     intercepted attempt, and the response carries the guard's message.
  3. The test proves the vault was not modified: a read-only fingerprint
     (presence + SHA-256 of the blob, never the blob) of the real product
     credential is identical before and after.
  *Extra assurance for the implementer/verifier:* run the new test with
  `win32cred.CredWrite`/`CredDelete` replaced by sentinels **before** the
  conftest's guard is installed (the technique already recorded in project
  memory: the guard's captured "original write" then IS the sentinel), so a
  regression in the guard would hit the sentinel instead of the real vault.
  The measurement used to produce the evidence in this plan used exactly that
  method, and the sentinel was reached 0 times.
- **R4 - contract drift (the attribute name is written in two files).**
  *Detection:* `test_violation_marker_contract_is_shared_by_handler_and_guard`
  asserts that `backend.main.VAULT_WRITE_VIOLATION_ATTR` equals the name the
  guard declares, and that an ordinary exception does not carry it. A rename
  on one side only turns that test red.
- **R5 - honest-debt risk: the new branch is dead code in a packaged build.**
  The violation only exists inside the test suite, which the payload excludes.
  This is accepted deliberately (it is the price of not weakening the 500
  contract) and is stated here rather than hidden.
- **R6 - environment coupling.** The new test needs `pywin32` and Windows;
  it skips cleanly when `win32cred` cannot be imported, exactly like
  `backend/tests/test_vault_guard_root_scope.py:20-22`. It must not require
  network, a live profile directory, the database or the app's lifespan (the
  `TestClient` is used **without** `with`, so `lifespan` does not run and no
  profile lock is taken).
- **R7 - test isolation.** The test pins `secrets_module._store` (restored by
  `monkeypatch`) and `backend.main.control_token` (restored in a `finally`);
  it mutates no other global state and adds no route to the shared app
  object.
- **R8 - the suite is not deterministic on this machine** (goal.md records two
  native fault kinds, `0x80040155` COM bursts and a `0xC0000005` access
  violation in `test_phase105_concurrency.py`). The full-suite comparison for
  criterion 5 must re-run a failing run before attributing a delta to this
  item, and a re-run is only acceptable if the failing test has no reference
  to credentials, the app or the exception handler.

## Sensitivity

- **Sensitivity tier:** sensitive - the change touches a production safety
  surface (`backend/main.py`'s only global exception handler) and a guard
  that protects the user's real credential slot.
- **Domain:** security - the item exists to keep a safety guard's failure
  observable instead of indistinguishable from an unrelated crash.

## Open questions

- **Why 409 and not 403?** `403` is already used in this app for the control
  boundary's "Untrusted request origin" (`backend/core/auth.py:120`), so
  reusing it for a different meaning would blur an operator-facing contract;
  `409` is already part of this API's vocabulary for "the current state of the
  target does not permit this operation" (`backend/api/routes.py:221, 1346`),
  and the block is exactly that: the target is write-protected, the request
  was well formed, and retrying will not help. A reviewer who prefers 403 can
  change one constant (`VAULT_WRITE_VIOLATION_STATUS`) - the whole shape
  survives.
- **Should the vendored mirror `src-tauri/resources/backend/main.py` be
  updated in the same commit?** Not in this item - criterion 4 fixes the file
  set, the mirror is refreshed by the staging script at build time, and the
  new branch is unreachable in a packaged build. It belongs in the next
  payload refresh; it should be recorded in the item's report rather than
  left implicit.
- **Should the contract instead be a shared production exception class**
  (`class VaultWriteViolation` in `backend/main.py`, imported by the
  conftest)? It would give an `isinstance` check instead of an attribute
  protocol, but it needs either a new production module (criterion 4 forbids
  it) or a conftest-time import of the whole application (a real cost and a
  real coupling risk for every pytest session in the repo). Recorded as a
  possible future refactor if a *production* safety check ever needs the same
  contract.
- **Is the default-`TestClient` behaviour (the exception still propagating)
  part of the contract?** The plan treats it as one: it is the guard's teeth
  today, and `test_vault_write_violation_still_raises_out_of_a_default_test_client`
  pins it. If a future item wants the violation to be a *handled* outcome in
  every client mode, that is a deliberate change to the guard's semantics and
  deserves its own item.
- **Should the regression test assert the guard's whole `detail` string?**
  No - the message text is not a contract and would make the test brittle.
  The test asserts the stable parts (status, error slug, code) plus the
  presence of the product target name inside `detail`.
- **Not determined here:** the exact pre-change suite counts. They must be
  measured on the base commit with the project's own commands and compared
  per-test; this plan deliberately quotes no count, because goal.md records
  that the collected/passed counts in the documents have drifted before and
  that the warning count is not a stable baseline.
