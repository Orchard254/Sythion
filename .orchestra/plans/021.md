# Plan for 021

## The problem

Two independent defects sit between a working model and a working first run.
The user clicks **Test selected model** during setup, the provider answers
correctly, and the app says "Request failed with status code 502" and refuses
to continue.

**Half 1 - the backend parses the wrong provider response shape (R-028).**

`backend/api/routes.py:2215-2220` (inside `POST /onboarding/inference`,
`:2186-2238`) reads **only** the OpenAI-compatible and legacy shapes:

```python
text = ""
if isinstance(resp, dict):
    choices = resp.get("choices") or []
    if choices and isinstance(choices[0], dict):
        text = (choices[0].get("message") or {}).get("content", "") or choices[0].get("text", "")
    text = text or resp.get("response", "") or ""
if not str(text).strip():
    raise HTTPException(status_code=502, detail="Inference returned an empty response")
```

Ollama Cloud's **native** `/api/chat` shape - `message.content` - is never
read. The orchestrator's live probe (R-028's Evidence field) recorded the
provider's exact answer:

```json
{"model":"minimax-m3.1-flash","message":{"role":"assistant","content":"OK"},"done":true,"done_reason":"stop","eval_count":2}
```

The current parser applied to that body yields `''`, so `:2222` raises
`HTTPException(502, "Inference returned an empty response")` **although the
model answered**. This is the FIRST-RUN GATE: a fresh install cannot get past
setup even though the model, the key and the account are all fine.

Every other consumer in the codebase already gets this right and reads
`message.content` **first**: `backend/agents/reasoner.py:310-318`,
`backend/cognitive/reasoning.py:187`, `backend/adapters/ollama_adapter.py:219`.
Only this one endpoint diverged.

**Half 2 - the frontend throws the backend's reason away (R-029).**

`frontend/src/services/api.ts:73-79` registers a **request** interceptor only.
There is no response interceptor anywhere in the file. `frontend/src/screens/Setup.tsx:46-51`
surfaces `e instanceof Error ? e.message : ...`, and for an axios rejection
`e.message` is the *constructed* string `"Request failed with status code 502"`.
The backend's precise cause - `"Inference returned an empty response"`
(`routes.py:2222`), `"Invalid Ollama Cloud API key"` (`:2155`), `"Model 'X' is
not available"` (`:2210`), `"Network failure during inference: ..."` (`:2237`) -
is serialised by FastAPI into the body's `detail` field and is **never read**
(`grep` for `e.response` over `frontend/src`: no hits).

That is why the failure was undiagnosable from the UI and why it took a
live-API probe to find. The frontend has no reason to be the place where the
reason dies: `frontend/src/services/api.ts` is the **only** axios instance in
the app, and ~15 call sites across the frontend surface `err.message`
(`Setup.tsx:49`, `Assistant.tsx:132`, `Dashboard.tsx:197`, `Security.tsx:103`,
`Memory.tsx:93`, `Settings.tsx:66`, `CommandComposer.tsx:57`,
`TaskDetailDrawer.tsx:50`, `GoalDetailDrawer.tsx:358`, `useAppInit.ts:60`,
`Companion.tsx:124`, `CompanionSurface.tsx:112`, `Overview.tsx:333`). Fixing
the message once at the axios boundary repairs all of them without touching a
single screen.

**The design constraint that decides this plan:** the tests must be
hermetic. They feed **response bodies in**; they never make an HTTP call to
the provider. The live probe was the EVIDENCE; the committed tests replay the
recorded body as a fixture constant.

## How it will be proven

### The mechanism in one paragraph

The backend half is proven by **two layers of test over the same three
recorded bodies**: a fast unit layer over a pure parsing helper, and an
endpoint layer that drives the real `POST /api/v1/onboarding/inference` through
FastAPI's `TestClient` with a **stub provider** whose `chat()` returns the
body under test. The frontend half is proven by driving the **real axios
instance** with a **per-request custom `adapter`** - axios's own documented
extension point (`frontend/node_modules/axios/lib/adapters/adapters.js:65-115`
accepts a function adapter) - so the whole axios pipeline (request
interceptor -> adapter -> response interceptor) runs with **no socket, no
backend and no new dependency**.

## The change

### Files to change, and how

**1. `backend/api/routes.py` (MODIFIED - internal parsing only).**

* **New module-level helper**, placed immediately above the endpoint (before
  `:2186`), following the file's existing convention of module-level private
  helpers (`_decode_event_data:691`, `_safe_json_loads:1614`,
  `_restore_secret:2161`):

  ```python
  def _extract_inference_text(response: Any) -> str:
      """Return the model's text from a provider response, or '' if there is none.

      Order (the FIRST candidate that yields a non-blank string wins):
        1. native Ollama /api/chat      -> response["message"]["content"]
        2. OpenAI-compatible chat       -> response["choices"][0]["message"]["content"]
        3. OpenAI-compatible legacy     -> response["choices"][0]["text"]
        4. legacy Ollama /api/generate  -> response["response"]

      The order matches backend/agents/reasoner.py:310-318 and
      backend/cognitive/reasoning.py:187, which read ``message.content`` first.
      Every access is type-guarded, so a malformed body yields '' instead of
      an exception.
      """
  ```

  **The exact order and the exact fallbacks:**

  | Order | Shape | Access | Where the shape comes from |
  |---|---|---|---|
  | 1 | native Ollama `/api/chat` | `response["message"]["content"]` | the live body in R-028's Evidence |
  | 2 | OpenAI-compatible chat | `response["choices"][0]["message"]["content"]` | `reasoner.py:317` |
  | 3 | OpenAI-compatible legacy completions | `response["choices"][0]["text"]` | the route's current `choices[0].get("text")` |
  | 4 | legacy Ollama `/api/generate` | `response["response"]` | the route's current `resp.get("response")` |

  **The rules that make the order deterministic:**
  * A candidate is **taken** only if its value is a `str` **and**
    `value.strip()` is non-empty. A `None`, a dict, a list, a number, or a
    whitespace-only string is **not** a candidate - the parser moves to the
    next shape.
  * A candidate whose **container** is not the expected type is **skipped**,
    never an error: `message` not a dict, `choices` not a list, `choices` empty,
    `choices[0]` not a dict.
  * Nothing is raised, logged or swallowed silently: the helper returns `""`
    when no candidate qualifies.
  * The result is the **stripped** string.

* **The endpoint body changes by two lines**: `:2215-2220` is replaced with
  `text = _extract_inference_text(resp)`. The guard at `:2221`
  (`if not str(text).strip(): raise HTTPException(status_code=502, detail="Inference returned an empty response")`)
  **stays**, as do the success body at `:2229`, the `set_setting` evidence
  write, and the `except` mapping at `:2230-2238` (401 / 503 / 502).

* **What does NOT change (this is the off-limits argument).**
  `backend/api/routes.py` is on `goal.md`'s off-limits list ("Public HTTP API
  shape"). The change is **behaviour-preserving on the wire**: the path, the
  method, the request handling, the status codes (400 / 400 / 200 / 502 / 401 /
  503), the response keys and the response values' meaning are all unchanged.
  Only the *internal* interpretation of the provider's body changes - from
  "only the OpenAI-compatible shape counts" to "the native shape counts too,
  and it counts first". **How that is pinned:** (a) B13 pins the status codes
  and the response keys; (b) B11/B12 pin the 502 for an empty and for an
  unrecognised body; (c) the route has no `response_model=` and no return
  annotation, so `app.openapi()` is byte-identical before and after; (d) no
  schema is touched, so no request/response contract can have moved.

* **A response that is none of the four known shapes**: the helper returns
  `""`; the endpoint raises the **unchanged** 502 `"Inference returned an empty
  response"`. So it **does not crash** (every access is type-guarded - B7) and
  it **does not silently report success** (the empty-text guard at `:2221` is
  kept - B11/B12). The 502 is the honest answer: the provider answered with a
  body Sythion does not understand.

**2. `frontend/src/services/api.ts` (MODIFIED - response side only).**

* **Where**: a **response** interceptor registered on the existing
  `apiClient`, immediately after the request interceptor (i.e. after
  `:79`), plus two module-private helpers above it. Nothing else in the file
  moves.

* **What it does** - the exact behaviour table:

  | # | Situation | `error.response.data` | Resulting `error.message` | Everything else |
  |---|---|---|---|---|
  | 1 | **Success** (2xx) | n/a | n/a - the response is passed through **unchanged** (`response.data`, `response.status`, `response.headers` are the axios values) | nothing is mutated, no message is attached |
  | 2 | Error with a `detail` **string** | `{"detail":"Inference returned an empty response"}` | **`"Inference returned an empty response"`** (verbatim, trimmed) | `error.response`, `error.status`, `error.config`, `error.code` are untouched; the promise still **rejects** with the same error object |
  | 3 | Error with `detail` as a **list** (FastAPI 422) | `{"detail":[{"loc":["body","model_id"],"msg":"field required"}]}` | **`"field required"`** - the `msg` fields joined with `"; "` | as above |
  | 4 | Error with an **`error` slug** and no `detail` | `{"error":"VAULT_WRITE_BLOCKED","code":"409"}` | **`"VAULT_WRITE_BLOCKLED"`** (verbatim) | as above |
  | 5 | Error with **both** | `{"error":"INTERNAL_ERROR","detail":"boom","code":"500"}` | **`"boom"`** - `detail` wins over the slug | as above |
  | 6 | Error with **no body** | `""` or `undefined` | **unchanged**: axios's `"Request failed with status code 502"` | as above |
  | 7 | Error whose body is **not a structured error** (plain text, HTML, a stack trace) | `"Traceback (most recent call last): ..."` | **unchanged**: axios's generic message - a raw body is **never** surfaced | as above |
  | 8 | **Network error, no response at all** | `error.response === undefined` | **unchanged**: axios's `"Network Error"` | the error is re-rejected completely untouched |

* **The precedence rule, stated once**: `detail` (string, or the `msg` fields
  of a `detail` list) > `error` slug > axios's own message. Only **structured
  JSON fields** are ever used; a raw body is never surfaced (row 7), which is
  what keeps a stack trace or an HTML error page out of the UI.

* **The request side is untouched.** The request interceptor (`:73-79`),
  `getControlToken` (`:47-62`) and `configureBridge` (`:39-43`) are
  **byte-identical**; a response interceptor cannot affect them, and F8 proves
  the token is still attached on the way out. The control token is never read
  by the response interceptor, so it cannot leak into a message (F9).

* **The error is never swallowed.** The rejection handler always ends with
  `return Promise.reject(error);`. Nothing is converted into a success, and no
  error is dropped.

* **The mechanism**: the handler **replaces `error.message`** on the same
  `AxiosError` object rather than throwing a new error. `AxiosError.message`
  is a writable, configurable own property
  (`frontend/node_modules/axios/lib/core/AxiosError.js:150-158`), and the
  error keeps `response`, `status`, `config` and `code`, so any future code
  that wants the status code or the raw body still has them. Every existing
  frontend call site reads `err.message` (15 sites listed above), so all of
  them improve at once - **without editing a single screen**.

* **Two module-private helpers** (NOT exported): one that turns a `detail`
  value into text (string -> trimmed; list -> the `msg` fields joined with
  `"; "`; object with a `msg` -> that `msg`; anything else -> `""`), and one
  that picks `detail` then `error` from the body. They stay private so the
  module's **public surface does not change** (Gate 6) and so the test has to
  exercise the real interceptor rather than a helper.

## Risk

### Backend half

* **B-R1 - a parser fixed for the native shape but LOSING the OpenAI-compatible
  or legacy shape.** This is the named risk of the item. A reordering that
  drops `choices[0].message.content`, `choices[0].text` or `response` would
  break every other provider path in the product. **Mitigation**: B2, B3, B4
  (each shape alone) and B5 (all four shapes in one body, native wins) -
  the three-shape test exists for exactly this. The helper's order is written
  down in this plan, so "the parser was reordered" is a diff a reviewer can
  see against a stated table.
* **B-R2 - a parser that reports SUCCESS for an empty answer.** If the helper
  returned a truthy placeholder (or the guard at `:2221` were deleted), the
  endpoint would answer 200 with an empty `response_preview` and the setup
  gate would advance on a lie - the exact class of defect this repository
  exists to eliminate. **Mitigation**: the helper returns `""` and nothing
  else; the `:2221` guard is kept; B11 (empty body -> 502), B12 (unrecognised
  body -> 502) and B6 (no text -> `""`) pin it. A test asserts the status
  code, not just the parse result.
* **B-R3 - a change that alters the endpoint's STATUS CODES.** A careless
  edit could turn the "model not available" 400 into a 404, or the 502 into a
  500, or swallow the 401/503 mapping at `:2234-2237`. **Mitigation**: B13
  pins 400/400/200; B11/B12 pin the 502; the diff touches exactly two lines
  of the endpoint body (`text = ...`), and the `except` mapping is not
  touched at all.
* **B-R4 - a parser that CRASHES on a malformed body.** `response["message"]`
  could be a string, `choices` could be a dict, `choices[0]` could be `null`,
  `content` could be a list. An unguarded access turns a provider oddity into
  a 500 and a stack trace in the operator's face. **Mitigation**: every access
  is type-guarded and the helper never raises; B7 feeds six malformed bodies
  and asserts `""` with no exception; B12 asserts the endpoint answers **502**,
  not 500, for an unrecognised body.
* **B-R5 - the test becomes a live-API test.** The obvious wrong turn is to
  "prove" the fix by calling Ollama Cloud. That test would need the user's
  credential, would fail on every machine without it, and would put a secret
  in the suite - which is precisely what item 007 exists to prevent.
  **Mitigation**: the recorded body is a constant; the provider is a stub;
  the test file reads no secret and opens no socket.

### Frontend half

* **F-R1 - an interceptor that SWALLOWS a real error.** A rejection handler
  that returns a resolved value (or forgets `Promise.reject`) would turn a
  failed setup into a false success. **Mitigation**: the handler always ends
  with `return Promise.reject(error)`; F1 asserts the promise rejects **and**
  that `err.response.status === 502` (the failure is still fully visible).
* **F-R2 - the interceptor CHANGES the message for successful requests.** A
  handler installed on the success path that rewrites `response.data` would
  corrupt every payload the app reads. **Mitigation**: the success handler is
  the identity `(response) => response`; F6 asserts `res.data` deep-equals the
  server's body and `res.status === 200`.
* **F-R3 - the control token LEAKS into a message.** The token is the local
  control boundary's secret (`backend/core/auth.py`, `goal.md`'s off-limits
  list). If the interceptor ever surfaced the request config, the URL, the
  headers or a raw body, the token could reach the screen. **Mitigation**: the
  message is built **only** from the response body's `detail` / `error`
  fields - never from the config, the headers or the request; F9 asserts the
  message does not contain the token that the request interceptor attached,
  and F8 asserts the token is still attached to the request (i.e. the request
  side was not "fixed" by removing it).
* **F-R4 - the interceptor SURFACES A RAW STACK TRACE.** A naive
  `String(error.response.data)` would put an HTML error page or a Python
  traceback in front of the operator. **Mitigation**: only structured JSON
  fields are used; a non-object body is never used (rows 6-7 of the table);
  F5 feeds a plain-text traceback body and asserts the message is the generic
  one and contains no `Traceback`.
* **F-R5 - the message change breaks an existing screen.** ~15 call sites
  display `err.message`; a longer, backend-authored string could overflow a
  panel. **Mitigation**: the message is the backend's own sentence, already
  written for humans (`"Inference returned an empty response"`); no screen is
  edited, so no layout assumption changes. This is a cosmetic risk, not a
  functional one, and it is the intended outcome of the item.
* **F-R6 - a new dependency sneaks in.** `axios-mock-adapter` is the obvious
  tool and it is not installed; adding it would change
  `frontend/package.json` (outside criterion 6) and the lock file.
  **Mitigation**: the test uses axios's own documented `adapter` hook -
  verified in `frontend/node_modules/axios/lib/adapters/adapters.js:65-115`
  (a function adapter is a "resolved handle") and
  `lib/core/dispatchRequest.js:39-79` (the rejection path transforms
  `reason.response.data`). `frontend/package.json` is unchanged.

## Sensitivity

**Sensitivity: `sensitive`.**

`backend/api/routes.py` is on `goal.md`'s off-limits list ("Public HTTP API
shape: `backend/api/routes.py`, `backend/api/schemas.py`"), so the
sensitive-change gate applies even though the diff is two lines of internal
parsing. The reasons it is classed `sensitive` rather than `none`:

1. The file **is** the public HTTP API surface, and the change sits inside the
   one route a first-time user must pass through. A mistake here is not a
   cosmetic bug: it either blocks setup (the status quo) or it lets a
   non-answer through as a success.
2. The route is on the **credential-bearing** path (it calls the provider
   with the configured key), so the file's neighbourhood is where this
   repository's gates are strictest.

**Why the change nevertheless qualifies under the gate's own wording**
("off-limits to change *behaviourally* unless the sensitive-change gate
passes"): the endpoint's **contract does not change**. Same path, same
method, same request handling, same status codes, same response keys, same
OpenAPI document; only the *interpretation of the provider's body* changes
inside the function. The contract is pinned by B13 (status codes + response
keys), B11/B12 (the 502), and the fact that no schema file is touched. The
frontend half is not off-limits at all (`frontend/src/services/api.ts` is not
on the list), but it is the change that makes the operator-visible behaviour
honest, so it is graded with the same rigour.

**Domain: `api`.** Both halves are the HTTP API boundary: the backend route
that parses a provider response and defines the error contract, and the
frontend HTTP client that maps that contract onto what the operator reads.
Nothing else in the product is touched.

## Open questions

1. **The detail string for an UNRECOGNISED body.** The plan keeps
   `"Inference returned an empty response"` for every no-text case, because
   the string is part of the endpoint's operator-visible contract (criterion
   3) and a second string would be a new public behaviour. It is slightly
   imprecise: an unrecognised body was not "empty", it was *unparseable*.
   Distinguishing the two (e.g. `"Inference returned an unrecognised response
   shape"`) would be more honest but would add a string the criteria do not
   ask for. **The plan's decision: keep the string unchanged**; if the board
   prefers the distinction, it is a one-line change in the same file plus one
   test, and it must not change the status code.
2. **Should the message carry the status code?** The plan's decision: **no** -
   the message is exactly the backend's `detail`, verbatim, so that what the
   test asserts is exactly what the backend said. The status code remains
   reachable on `error.response.status` / `error.status` for any future code
   that wants it, and mixing the two would create a third message form that
   nothing pins. A reviewer may prefer
   `"Inference returned an empty response (HTTP 502)"`; that is a
   product-copy decision, not a correctness one.
3. **Should the `error` slug be humanised?** The backend's slug is a machine
   token (`"VAULT_WRITE_BLOCKLED"`, `"INTERNAL_ERROR"`). The plan uses it
   **verbatim** - no invented prose, because a rewritten slug would be text
   the backend never said. The human-readable companion for those two shapes
   is the `detail` field, which the plan prefers anyway (row 5 of the table).
4. **The frontend CI job DOES run the frontend suite - this open question was
   WRONG when first written and is corrected here.** The plan originally cited
   R-014 ("the `frontend` job is `npm ci` + `npm run lint` + `npm run build`")
   and concluded the new frontend test would "only gate CI once R-014 lands".
   That is FALSE: **R-014 was already fixed by item 001** (commit `3ec2d46`).
   As of 2026-10-22 the `frontend` job runs four steps - `npm ci`,
   `npm run lint`, `npm run build`, and `Test (vitest)` -> `npm test` at
   `.github/workflows/ci.yml:103-104` - and `frontend/package.json` maps
   `"test": "vitest run"` (non-interactive; `"test:watch": "vitest"` is the
   watch script). The repository's own `docs/TESTING.md:126` calls `npm test`
   "the CI frontend step" and `docs/TESTING.md:170` names the vitest step, so
   the docs are already correct. **The new frontend test therefore gates CI
   once this item merges.** The implementer must NOT report the opposite - if
   the report says the frontend test is local-only, that statement is wrong
   and the implementer should have checked `ci.yml` before writing it.
5. **The pre-change suite baseline must be measured, not quoted.** `goal.md`'s
   "1564 passed / 45 skipped / 1609 collected" was measured before items
   017-020 landed; `plans/020.md` records 1628 collected on a later tree. The
   implementer measures the baseline on the **branch base** and reports the
   delta (planned: +13 backend tests, +9 frontend tests, skipped unchanged,
   no existing verdict changed). Any number in the item report must come from
   an executed run.
6. **Whether the helper should be public.** The plan's decision: **private**
   (`_extract_inference_text`), so `backend.api.routes`' public import surface
   does not change (Gate 6) and the endpoint's contract is provably
   untouched. A reviewer who prefers a public `extract_inference_text` (so
   other modules could reuse it) would be widening the surface of an
   off-limits file - worth flagging, but not worth it here.
7. **Not measured here**: the behaviour in the packaged Tauri shell (the
   interceptor runs in the same bundle, but the packaged path was not
   exercised). The plan's evidence is the repository's own test suites; the
   live-provider confirmation stays with the human operator, as R-028's
   evidence shows it must.
