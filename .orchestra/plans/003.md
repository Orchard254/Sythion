### Test that pins the invariant

There is no new test file in this item (the item's scope is two scripts and
seven documents). The invariants are pinned by the two committed scripts, and
each script has a **pass path and a fail path that must both be demonstrated**.

**I. `scripts/measure_test_baseline.py` - the invariant is "a published number
comes from a run that COMPLETED".**

The script runs each suite in a **child process** and classifies the child's
outcome. A run is COMPLETE only if **all three** hold:

1. the child exited **0**;
2. the child's output contains a parseable pytest summary line
   (`<n> passed, <m> skipped, ... in <t>s`);
3. the child's output contains **no native-fault marker**.

Condition 3 is separate from condition 1 on purpose. The suite has **two**
distinct native-failure modes on this machine (2 crashes in 6 observed
full-suite runs):

- **Fault A** - a burst of ~294 COM/UIA faults (`0x80040155`,
  `0x8001010d`) on the single `sythion-uia-mta` thread inside
  `backend/tools/gui_tools.py:_UIADriver._find_window`. It **does not kill the
  process**; the run continued for another 23 percentage points in the
  captured run. A script that looks only at the exit code would see `0` and a
  summary line and would happily publish the numbers of a run that was
  bleeding native faults.
- **Fault B** - `Windows fatal exception: access violation` (`0xC0000005`)
  inside native sqlite3, in the two `tfn` threads of
  `backend/tests/test_phase105_concurrency.py::TestBudgetAtomicity::test_concurrent_budget_does_not_exceed`.
  It **does** kill the interpreter, with no pytest summary at all.

So: exit code 0 is not sufficient, and a summary line is not sufficient. The
fault markers the script looks for are `Windows fatal exception`,
`Fatal Python error:` and the faulthandler dump header (`Thread 0x... [` /
`Current thread 0x...`). **Any other outcome - crash, non-zero exit, test
failures, "no tests collected" (pytest exit 5), interrupted (2), usage error
(4), missing summary line, or a native-fault marker - publishes NO counts at
all.** The JSON then carries `"complete": false` and a `status` that says
which, the count keys are **absent**, and the script exits **2**. A JSON that
contains a count is a count from a completed, fault-free run; a JSON without
counts is not a baseline and must not be pasted into a document.

**Retry.** Because roughly one run in three dies, the script runs each suite
in a **fresh child process** up to `--attempts` times (default 3) and stops at
the first COMPLETE attempt. Every attempt is recorded in the JSON
(`attempts: [{attempt, exit_code, status, seconds, tail}]`), including the
crashed ones. A fresh process per attempt is mandatory: neither fault
reproduces in isolation (30/30 and 25/25 clean single-test runs), so
re-running the same process would prove nothing.

**The two failure demonstrations (mandatory, cheap, deterministic).** The
Implementer must show the fail path without waiting for a lucky crash. The
script takes `--makefile PATH`, so a **sandbox Makefile outside the
repository** can be used:

- **D1 (crash):** a sandbox Makefile whose `test:` recipe runs a two-line
  Python program that dereferences a null pointer through `ctypes`. The child
  dies with `0xC0000005`; the script must print `"status": "crashed"`, the
  attempt's exit code, **no counts**, and exit **2**.
- **D2 (usage error / incomplete):** a sandbox Makefile whose `test:` recipe
  points at a path that does not exist. The child exits 4; the script must
  print `"status": "failed"`, **no counts**, and exit **2**.

Both transcripts go into the report, with the sandbox files. "A guard that has
never been seen to fail is not a guard" applies to a measurement script just
as much as to a test.

## The change

### The two decisions the brief leaves open

#### (a) What the script does when the suite is not clean

**Decision: the script publishes no numbers from an incomplete run, ever. It
runs each suite in a child process, classifies the outcome, retries a crashed
suite in a fresh process, and prints counts only for a COMPLETE run.**

The reasoning, in the order that produced it:

1. *A crashed run has no counts to publish.* Fault B kills the interpreter
   before pytest prints a summary, so there is literally nothing to publish -
   the failure mode to defend against is not "the count is wrong" but "the
   script invents a count".
2. *A faulted run has counts that must not be published.* Fault A does **not**
   kill the process. A run that took 294 native COM faults and then finished
   still prints `N passed, M skipped` and still exits 0. Those numbers are
   probably right and are certainly not *verified*; publishing them means
   publishing a number from a run that was bleeding native exceptions. The
   script therefore treats a native-fault marker in the output as
   disqualifying, independently of the exit code.
3. *A failing run must not become the baseline.* A non-zero exit (test
   failures, pytest's exit 5 for "no tests collected", 2 for interrupted, 4
   for a usage error) is reported as such, with the exit code and the tail of
   the output, and no counts.
4. *A crashed run is normal on this machine, so "crash" must not mean
   "give up".* With roughly one run in three dying, a script that published
   counts only on a first-attempt success would be unusable. Hence the retry
   (default 3 fresh processes per suite) and hence the JSON's `attempts`
   array - every attempt is recorded, crashed ones included, so nobody can
   claim a green number that was cherry-picked from a set of attempts.

The JSON shape when the run was clean (the shape the documents quote):

```json
{
  "schema_version": 1,
  "status": "ok",
  "complete": true,
  "measured_at": "<ISO-8601>",
  "git": {"commit": "<sha>", "branch": "<name>", "dirty": false},
  "python_version": "3.14.7",
  "platform": "Windows",
  "platform_release": "<kernel release>",
  "pytest_version": "8.4.2",
  "ci_python_version": "3.11",
  "passed": <backend passed>,
  "skipped": <backend skipped>,
  "collected": <backend collected>,
  "duration_seconds": <backend wall time>,
  "suites": {
    "backend":   {"command": [...], "exit_code": 0, "passed": ..., "skipped": ...,
                  "collected": ..., "duration_seconds": ..., "complete": true},
    "acceptance":{"command": [...], "exit_code": 0, "passed": ..., "skipped": ...,
                  "collected": ..., "duration_seconds": ..., "complete": true}
  },
  "attempts": [{"suite": "backend", "attempt": 1, "exit_code": 0, "status": "ok",
                "seconds": 402.3}, ...]
}
```

The top-level `passed` / `skipped` / `collected` / `duration_seconds` are the
**backend suite's** (the headline baseline); the acceptance suite's numbers
live under `suites.acceptance`. When the run was not clean, the count keys are
**absent** from the JSON, `"complete"` is `false`, and `"status"` is one of
`crashed` / `faulted` / `failed` / `incomplete` / `inconsistent`, with the
offending attempt's exit code and output tail in `attempts`.

Three further rules the script must obey:

- **No warning count, ever.** The parser reads past the warnings counter and
  discards it. It is not in the JSON, not in the log, not in the report.
- **`collected` is measured, not guessed.** It is the sum of the run's
  outcome counters (passed + skipped + failed + errors + xfailed + xpassed),
  which is exactly pytest's collected count when nothing is deselected - and
  the `make test` recipe has no `-m` expression. If the derived command ever
  *does* contain a marker expression, the script measures `collected` with
  `--collect-only` instead of summing. Either way the script records
  `collected_source`, and `--check-collected` re-measures it independently with
  `--collect-only -q`; a disagreement is `"status": "inconsistent"` and
  publishes nothing.
- **The commands are read from the `Makefile`, not retyped.** The script
  parses the `test` and `test-acceptance` targets out of the repository's
  `Makefile` and runs the pytest command found there. `make` is **not
  installed on this machine** (verified: `Get-Command make` returns nothing),
  so the script runs the command directly with `sys.executable -m pytest` -
  but the command it runs is the Makefile's, so the script can never measure
  something the Makefile does not run. If the Makefile has no such target, the
  script refuses to run (exit 3) rather than inventing a command.

#### (b) Does the script write the numbers into the documents?

**Decision: the script PRINTS. It does not write into the documents. Drift is
made DETECTABLE, not prevented.**

Why printing and not writing:

- Acceptance criterion 1 says the script "prints a machine-readable summary";
  criterion 2 ties the documents to "the numbers printed by the last executed
  run". Nothing in the contract asks for a writer, and a writer is a much
  bigger hammer: the numbers live in a badge URL, in bullet lists, in two
  tables and in six files, in five different prose shapes. A script that
  rewrites prose has to know all five shapes, and the day it meets a sixth it
  silently mangles a document. Documentation is prose; a human owns it.
- A writer also hides the failure. If the script rewrites the numbers, the
  documents can never disagree with the measurement - but they also can never
  *be* the measurement, because nobody read them. Gate 3 ("verification before
  claims") and Gate 9 ("honest handling of debt") are about a human being able
  to look at a claim and see what backs it.

How a reviewer tells that the documents are **stale**:

1. **One command.** `python scripts/measure_test_baseline.py --check` re-measures
   and compares. Exit **0** = the documents agree with a fresh measurement on
   this interpreter. Exit **1** = the documents are **stale** (it prints every
   offending line, the number it found and the number measured). Exit **2** =
   the measurement did not complete (crash) - **inconclusive, not a failure of
   the documents**; the reviewer must re-run. Exit **3** = the running
   interpreter/platform differs from the one the documents name - the
   documents are not stale, they were measured elsewhere (this matters: CI
   pins Python 3.11, the reference machine is 3.14.7).
2. **The cheap form.** `python scripts/measure_test_baseline.py --check-collected`
   compares the documents' collected count against a fresh
   `--collect-only` run (~100 s). This catches the commonest drift - a test
   added or removed by a later item - without a full suite run.
3. **The documents themselves.** Every baseline block carries the interpreter,
   the OS, the measurement date and the command that produced it, so a reader

#### 1. `scripts/measure_test_baseline.py` (NEW)

Repository-root-relative invocation, standard library only (no PyYAML, no new

CLI:


| Flag | Meaning |
|------|---------|
| `--root PATH` | Repository root (default: the script's parent's parent). |
| `--makefile PATH` | The Makefile to read the `test` / `test-acceptance` recipes from (default: `<root>/Makefile`). Exists so the failure demonstrations D1/D2 can use a sandbox Makefile **without touching the repository**. |

#### 2. `scripts/check_doc_paths.py` (NEW)

Standard library only. Purpose: every module the authority documents name must
exist on disk.

**What counts as a reference (and what does not).** This is the judgement the
brief asks for, and the answer has three parts:

1. **A reference is written in code font.** The script scans **inline code
   spans** (backticks) and **fenced code blocks**. It does **not** scan plain
   prose. This is not an arbitrary choice: `docs/PROJECT_STATUS.md:44` contains
   the prose shorthand "backend/acceptance", which is not a path to anything
   (the real one is `backend/tests/acceptance`). A prose scanner false-alarms
   on it. A document references a module by writing it in code font; prose
   that merely names a subsystem is not a reference.
2. **A path-shaped token is classified, not assumed.** A token is
   path-shaped if it contains a `/` or ends with a known source/document
   extension. Tokens that are not path-shaped (`TaskEvent`, `ConversationTurn`,
   `BaseTool`, `Objective`, `PlanStep`) are ignored - they are type names, not
   paths.
3. **Classification and resolution:**

| Class | Shape | Resolution | Verdict |
|-------|-------|-----------|---------|
| MODULE | `backend/...` ending in `.py` (or another source extension) | repository root | must exist as a **file** |
| DIRECTORY | `backend/...` with no extension | repository root | must exist as a **directory** (a directory reference is legitimate and counts as resolved) |
| DOCUMENT | any other path with a `/` or a document extension (`docs/ARCHITECTURE.md`, `FINAL_STATUS.md`, `../../docs/X.md`) | first relative to the **document's own directory**, then relative to the **repository root** | must exist |
| MODULE BY NAME | a bare `*.py` filename (`task_runner.py`, `skill_engine.py`) | searched for under `backend/` | exactly one match -> resolved; **no match -> MISSING**; several matches -> **ambiguous** (reported, non-fatal unless `--strict`) |
| MARKDOWN LINK TARGET | `[text](target)` | relative to the document's directory (markdown semantics); `http(s)://`, `mailto:` and `#anchor` targets are skipped | must exist |

The bare-name rule is what gives the script teeth on the exact defect this
item is about: `backend/services/README.md:55-56` names the two deleted
modules as bare filenames, which a `backend/...`-only scanner would never see.

**A legitimately absent file.** The script carries one explicit, documented
mapping `ALLOWED_ABSENT: dict[str, str]` (path -> reason). An entry is
reported as `allowed (absent by design: <reason>)` and is **not** counted as
missing; an entry whose path **now exists** is reported as a *stale allowlist
entry* (a warning by default, fatal under `--strict`). The mapping starts
**empty**, and the Implementer must not add an entry to make a failure
disappear: if a documented module does not exist, the document is wrong, and
the fix is to correct the document.

**Output and exit codes.** Human-readable by default (`missing paths: 0` on
success; each missing path printed as `<document>:<line>: <path>`), `--json`
for machine consumption. Exit **0** = zero missing paths, **1** = at least
one missing path, **2** = usage error. `--strict` additionally fails on
ambiguous names and stale allowlist entries.

**The fail-path demonstration (mandatory).** `--docs` and `--root` exist so
the demonstration needs no repository edit: copy one of the four documents to
a temporary file outside the repository, add one bullet naming a module that
does not exist, and run
`python scripts/check_doc_paths.py --docs <that copy>`. The script must exit
**1** and name the missing path with its line number. The transcript goes into
the report. The same run against the unmodified four documents must exit **0**
with `missing paths: 0`.

## Risk

### What is most likely to break

**Risk 1 - the documents and the script drift apart again.** The script
measures, a human edits the prose, the two disagree, and nobody notices
because a document that reads well is indistinguishable from a document that
is true. This is the *defining* risk of the item: an item that updates five
documents once has fixed a symptom.

Mitigations, in order of strength:

1. **`--check` is one command and it fails loudly.** Every quoted pair in
   every scope document must be a measured pair (rule C1). A stale number
   anywhere in the six documents fails the check with the file, the line and
   both numbers.
2. **`--check-collected` makes the drift check cheap enough to actually
   happen.** The collected count is the number that moves with every merged
   item, and it costs ~100 s to measure, not ~12 minutes. A reviewer will
   actually run that; nobody runs a 12-minute check.
3. **The check is structural.** It compares against the measurement, not
   against a banned list, so it keeps working after the numbers move again.
4. **One quote per document.** The canonical block is the single place a
   number is stated; the other places point at it. Fewer copies, fewer places
   to drift.
5. **The documents name their provenance** - interpreter, OS, date and the
   command that produced them - so the claim is visibly a measurement.

**Risk 2 - the measurement script is 9-12 minutes long, so the "last executed
run" is always stale.** A full-suite run measured 389-436 s on the reference
machine, the acceptance suite ~26 s, and a crashed attempt costs the same
again; with a ~1-in-3 crash rate and up to 3 attempts, a full run can cost 20
minutes. Nobody runs that on every merge.

Mitigations:

1. **`--check-collected` (about 100 s)** is the practical drift detector and
   is the check the plan asks the team to run after any change that adds or
   removes a test.
2. **`--fast` (about 1 minute)** measures the acceptance suite only - enough
   to see that the acceptance numbers have not moved and that the scripts
   still work.
3. **A full re-measurement is only needed when the collected count moves**,
   which the cheap check detects.
4. **The script's cost is stated up front** in the docstring and in
   `docs/TESTING.md`, so nobody is surprised by it and nobody blames the tool.
5. **The retry is bounded** (`--attempts`, default 3) so a bad day cannot
   turn into an hour of runs.

**Risk 3 - the scripts become a second source of truth that contradicts the
Makefile and the workflow they are supposed to describe.** The dangerous
shape is a script that says "the full suite is `python -m pytest backend/tests
-q`" while the Makefile says something else.

Mitigations:

1. **The scripts READ the Makefile and the workflow.** The pytest commands
   come out of the `Makefile`'s `test` and `test-acceptance` recipes; the CI
   Python version comes out of `.github/workflows/ci.yml`. Neither is retyped.
2. **The script refuses to guess.** No `test` target in the Makefile -> exit 3
   with a message, not a fallback command.
3. **The documents describe the Makefile, not the script.** The script
   measures; `docs/TESTING.md` describes the Makefile's targets. The two are
   related but not merged, so a change to the Makefile shows up in the
   documents' table (criterion 7) and in the measurement, and never as a
   contradiction inside the script.

**Risk 4 - the path check false-alarms.** A check that reports missing paths
that are not missing trains the team to ignore it, which is worse than not
having it.

Mitigations: the classification rules above (code font only; path-shaped
tokens only; directories are legitimate; markdown link targets are resolved
with markdown semantics); the `ALLOWED_ABSENT` mechanism with a mandatory
reason, so a legitimate absence is *declared* rather than tolerated; ambiguity
is reported but not fatal by default (`--strict` makes it fatal); and the
Implementer must demonstrate the fail path on a sandbox copy, so the pass path
is known to be reachable.

**Risk 5 - the measurement is taken on the wrong tree, or a number is
cherry-picked from a set of attempts.** The numbers in the documents must
come from a run on the branch tip, after item 002 merged. Mitigations: the
script records the commit it measured (`git.commit` in the JSON) and the
report records it; every attempt is recorded, so a number taken from attempt
3 of 3 is visible as such; a crashed attempt can never contribute a number.

**Risk 6 - no complete measurement can be obtained at all** (three consecutive
crashes, or a machine that is too loaded). Then the item **cannot** fill in
the numbers, and the Implementer must report that rather than typing a number
from this plan, from `master`, or from memory. The plan states this
explicitly: a guessed number is the defect this item exists to remove, and
copying one out of this plan would reproduce it in a new place.

**Risk 7 - the merge ordering.** Item 003 merged before item 002 would
document a Makefile that is about to change, and the tables would be wrong on
arrival. Mitigation: item 003 is built on a branch cut from `master` **after**
item 002 merges, and the Implementer re-reads the merged `Makefile`,
`pytest.ini` and `ci.yml` before writing the tables. The verification
(reproduction rows R1-R8, `--check`, the path check) happens on the **merged
tree**, not on the branch in isolation.

### Rollback

Revert the branch's commits. The branch touches two new scripts and seven
Markdown files; there is no generated artefact, no database, no credential, no
payload, no CI change and no persistent state. The only cache to clear is
`.pytest_cache`. Rolling back restores exactly today's behaviour, including
today's wrong numbers and today's two deleted modules - i.e. it restores the
defect, which is the correct semantics of a revert and is stated here so no
one mistakes the rollback for a neutral act.
