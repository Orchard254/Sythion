# Plan for 002

Item: **002 - Makefile test selections and pytest configuration stop claiming what they do not do**
(candidates R-003, R-005). Base branch: `master` at `C:\Sythion\sythion`.
Implementer branch: `orchestra/002-test-selection-truth`.

---

## The problem

The repository has no pytest configuration file at all, and the Makefile selects
tests with marker expressions that select nothing. Concretely, measured on
`master` (CPython 3.14.7, pytest 8.4.2, Windows):

- `python -m pytest backend/tests --collect-only` prints a header with
  `rootdir: C:\Sythion\sythion` and **no `configfile:` line** - there is no
  `pytest.ini`, no `pyproject.toml`, no `setup.cfg` anywhere in the tree.
- `-m gui`, `-m network` and `-m acceptance` each report *no tests collected
  (1609 deselected)* and exit **5**. `make test-gui` and `make test-network`
  therefore run **zero** tests; `make test-unit` (`-m "not acceptance"`)
  deselects **0** tests and is byte-identical to the full suite;
  `make test-fast` (`-m "not slow and not flaky and not integration and not
  gui and not network"`) deselects exactly **1** test (the single `slow` one),
  so the "fast" suite is the whole suite minus one test.
- `gui`, `network` and `acceptance` are declared in
  `backend/tests/conftest.py::pytest_configure` but applied to **zero** tests;
  `flaky` and `integration` are likewise applied to zero (they appear only in
  the comment at `conftest.py:29`). Conversely `concurrency` (applied at
  `backend/tests/test_phase105_concurrency.py:39` and
  `backend/tests/test_phase1075_hardening.py:35`) and `gated_soak`
  (`backend/tests/test_phase115_soak.py:15`) are applied but never declared,
  so every full run emits **3** `PytestUnknownMarkWarning`s.
- `docs/TESTING.md:37-58` describes all of these commands and markers as
  meaningful selections and quotes runtimes ("~55s", "~25s", "~10s") that are
  wrong by roughly an order of magnitude.

The consequence is not a broken test suite - the suite is green (1609
collected, 1564 passed / 45 skipped in the recorded baseline). The
consequence is that **every future agent that trusts `make test-fast`,
`make test-gui`, `make test-network` or `make test-unit` is wrong about the
repository**: the commands claim a selection they do not perform, and the
repository has no single place where the test-selection contract is written
down. This item makes the selections and the configuration say what they
actually do. It does **not** make the suite faster and it does **not** change
any runtime behaviour.

### Test that pins the invariant

Three layers, all committed, all runnable by a person who was not in this
conversation.

**(a) `make check-test-selections` - a new Makefile target (committed).**
It runs `python -m pytest backend/tests -m "<expression>" --collect-only -q`
once for **every** `-m` expression the Makefile uses, and Make aborts on the
first non-zero exit - and pytest's exit code is 5 for an empty selection. The
target therefore fails on `master` (exit 5) and passes on the branch. It is
the executable form of acceptance criterion 3, and it is the check a
developer or a CI job runs to prove the Makefile's selections are real.

**(b) The selection-contract guard inside `backend/tests/conftest.py`
(committed).** This is the mechanical answer to the risk named in the brief
("a marker applied to the wrong set of tests silently narrows the suite").
The guard has two parts:

- *Classification* - a `pytest_itemcollected` hook applies two rules:
  `acceptance` to every item whose file is under `backend/tests/acceptance/`,
  and `network` to every item that already carries `provider_e2e`.
  **The hook must be `pytest_itemcollected`, not `pytest_collection_modifyitems`.**
  pytest's own marker deselection runs first (the mark plugin's
  `deselect_by_mark` is registered `tryfirst`), so a marker added in
  `pytest_collection_modifyitems` is invisible to `-m` and `-m "not
  acceptance"` would deselect nothing. This was verified empirically on this
  machine against pytest 8.4.2: `pytest_collection_modifyitems` -> `-m "not
  acceptance"` still selected the test; `pytest_itemcollected` -> the test was
  correctly deselected. The same ordering holds in pytest 7.4.4, the version
  pinned in `backend/requirements.txt`.
- *Verification* - a `pytest_collection_finish` hook asserts, on every
  **full-tree** collection, that:
  1. every marker carried by every collected item is a declared marker
     (no unknown mark anywhere);
  2. the set of items carrying `acceptance` is **exactly** the set of items
     whose file is under `backend/tests/acceptance/`;
  3. the set of items carrying `gui` is **exactly** the set of items in
     `backend/tests/acceptance/test_gui_fixture.py`;
  4. the set of items carrying `network` is **exactly** the set of items
     carrying `provider_e2e`;
  5. (guard against a stale configuration) the root config file named by
     pytest is the one in the repository root and it declares all ten
     canonical markers.

  The guard is active only when the invocation collected the whole
  `backend/tests` tree - detected from the command-line path arguments (or
  from the absence of path arguments, in which case the config's `testpaths`
  selected exactly that tree). A partial run such as
  `pytest backend/tests/test_work_state.py` must **not** fail the guard.
  A violation aborts the session with `pytest.UsageError`, which pytest
  reports as `ERROR: <message>` and exits **4** (verified on this machine:
  the message is printed and the exit code is 4, not an INTERNALERROR
  traceback).

  Rules 2-4 are the drift detectors: the moment somebody marks one more test
  `gui`, moves the acceptance directory, or applies `network` by hand, the
  next full-suite run **aborts** instead of silently narrowing the fast
  suite.

**(c) The selection table in the item report (evidence).** The report must
contain one row per marker with: the marker, the **list of files** whose
tests carry it, the number of tests selected, and the exit code of
`python -m pytest backend/tests -m "<marker>" --collect-only -q`. It must
also contain the **complete list of node IDs** that `make test-fast`
deselects. The Verifier re-runs the same commands and compares the numbers
and the file lists against the table. This is the human-readable half of the
anti-silent-narrowing check: the population of every marker is written down,
so a reviewer can see what "fast" actually excludes.

**The guard must be shown to fire.** The Implementer temporarily applies
`@pytest.mark.gui` to one test in a different file, runs
`python -m pytest backend/tests --collect-only -q`, records the resulting
`ERROR:` line and the exit code 4, and then reverts the temporary edit. The
same demonstration is made once for the undeclared-marker rule (apply a
marker that is not in the canonical ten). Both transcripts go into the
report. A guard that has never been seen to fail is not a guard.

## The change

### The decision this item makes (and why)

**The markers are APPLIED to the tests they were meant to describe. None of
the Makefile's test targets is removed.**

`backend/tests/acceptance/` is a real directory of 24 test modules and is
already selected **by path** (`make test-acceptance` runs
`pytest backend/tests/acceptance -q`) - that target is honest today and stays
honest. The dishonest ones are the three that select by marker and select
nothing: `-m gui`, `-m network`, `-m acceptance`.

- `acceptance` -> applied to every test under `backend/tests/acceptance/`.
  It is a property of the *directory*, so it is applied by a path rule
  (24 files are not edited).
- `gui` -> applied to `backend/tests/acceptance/test_gui_fixture.py` only.
  That module is the only test module in the repository that requires a live
  interactive Windows desktop and the real UI Automation stack (it launches
  `scripts/gui_fixture_app.py` and drives the real `comtypes` driver over the
  real MTA worker; it skips itself when no interactive desktop is available).
  The GUI *unit* tests (`backend/tests/test_gui_tools.py`,
  `test_window_list.py`, `test_browser_tabs.py`) substitute a fake driver or
  mock `win32gui` entirely, so they do **not** require a GUI and stay in the
  default and fast suites. The marker means "requires a live GUI", and the
  marker description in the configuration says so in those words.
- `network` -> applied to every `provider_e2e` test. Those are the only
  tests in the repository that need an outbound network connection: they are
  the real provider-backed E2E tests and they are skipped unless
  `SYTHION_RUN_PROVIDER_E2E=1` and provider credentials are configured. The
  rule "provider_e2e implies network" is applied as a *rule*, so the two
  `provider_e2e` tests that live in the files item 004 is editing
  (`test_phase105_concurrency.py:943`, `test_phase1075_hardening.py:728`) are
  covered **without editing those files**.

Why apply rather than remove the targets: the three targets exist because
three real, useful selections exist (the acceptance gates, the live GUI
gate, the provider E2E gate). Removing them would throw away a capability
and would still leave the marker vocabulary in the configuration describing
sets that do not exist. Applying the markers keeps every target, makes every
`-m` expression in the Makefile select a real, non-empty, enumerable set, and
makes `make test-unit` mean what its name says.

**`flaky` and `integration` are the exception.** They are applied to zero
tests, and there is no evidence in the repository to populate them honestly:
`flaky` would be a claim about instability that cannot be reproduced on
demand (R-007 is a native crash, not a flaky assertion), and `integration`
would mean excluding `backend/tests/test_integration.py` - a hermetic,
in-memory, fast suite - from the fast suite, which removes coverage for no
gain. So both markers stay **declared** (so a future test can carry them and
the guard does not abort), and their two no-op clauses
(`not flaky`, `not integration`) are **removed from the `test-fast`
expression**: a clause that deselects nothing is a claim the target cannot
back. This is the "or dropped from the Makefile's expressions" branch of
acceptance criterion 3.

**This item makes the selections truthful, not fast.** `make test-fast` will
still run most of the suite, because the suite is hermetic - there is little
that *can* be excluded without losing real coverage. The target keeps its
name; its Makefile comment states exactly what it excludes; the measured
runtimes are item 003's business. Making the target genuinely fast would
require excluding the acceptance gates or a large named part of the suite by
name, which is precisely the silent-narrowing failure mode this item exists
to remove - it is a separate item, recorded as a follow-up.

## Risk

### What is most likely to break

**The defining risk is a marker applied to the wrong set of tests, which
silently narrows the suite** - `make test-fast` becomes fast by running
less, `make test-unit` starts excluding tests nobody intended to exclude,
and nobody notices because a passing pytest run looks identical. This item
creates three new marker populations, so it is exactly the item where that
failure can happen.

Mitigations, in order of strength:

1. **The guard (b) asserts the population of every marker as an identity**
   (`gui` == the GUI module, `network` == the `provider_e2e` set,
   `acceptance` == the acceptance directory) and **aborts** the run on a
   full-tree collection when an identity breaks. A mis-applied marker cannot
   reach a green run.
2. **The guard also aborts on any undeclared marker**, so the population
   cannot drift into a set the configuration does not describe.
3. **`make check-test-selections` fails loudly** (pytest exit 5) when a
   selection collects nothing - the "the target claims a selection it does
   not perform" case.
4. **The report writes every population down** (per marker: the files, the
   test count, the exit code) plus the complete list of node IDs that
   `make test-fast` deselects, so a reviewer sees the narrowing instead of
   inferring it.
5. **The full suite's collected count is pinned at 1609** before and after,
   so no test can be lost from `make test` unnoticed.

**Second most likely to break: the guard itself.** It runs on every
full-tree collection, so a false positive would break CI and every local
run. Mitigations: the guard is skipped for partial runs; it uses only APIs
present in pytest 7.0+; the Implementer must demonstrate both the pass path
and the fail path (the temporary mis-marking demonstration) before the
branch is proposed; and the guard's failure mode is a clean
`ERROR: <message>` + exit 4, not an INTERNALERROR.

**Third: `testpaths = backend/tests` changes the no-argument invocation.**
It is deliberate and it is a strict improvement (it stops the default
invocation from importing 13 root-level scripts and the vendored runtime's
third-party test modules), but it is a change and it is recorded as such in
criterion 4 and in the report.

**Fourth: the suite is not deterministic on this machine.** R-007 records a
native `0x80040155` COM fault in the `sythion-uia-mta` worker thread, which

`backend/tests/acceptance/test_gui_fixture.py` - the module this item marks

silently re-run until a green one appears. Note that the change does

**Fifth: the `network` marker population is a rule, not a file list.** If a

## Open questions

None of these blocks the Implementer - each has a stated default in the plan
above. They are recorded because a different answer would change the diff.

1. **The guard lives in `backend/tests/conftest.py`, not in a new test
   file.** Acceptance criterion 6 lists "the new root pytest configuration
   file, `backend/tests/conftest.py` and test files whose marker
   classification was corrected" - a *new* `backend/tests/test_test_selection_contract.py`
   is not literally in that list, even though item 004 establishes the
   precedent of a committed guard test under `backend/tests/`. This plan
   keeps the guard inside the explicitly allowed `conftest.py` to satisfy
   criterion 6 as written. If the orchestrator prefers a separate test
   file, the guard moves there unchanged and criterion 6's list gains "the
   new guard test file" - flagging it because it is a literal deviation from
   a criterion the Scout wrote.
2. **`flaky` and `integration` stay declared but unapplied, and their
   clauses leave the `test-fast` expression.** The alternative - populating
   `integration` with `backend/tests/test_integration.py` - would narrow
   `make test-fast` by that file's test count for no speed gain, and
   populating `flaky` needs reproducible evidence of instability that the
   repository does not have. If the orchestrator wants those markers
   populated anyway, that is a decision with a measurable cost and it should
   be made explicitly.
3. **`gui` covers only `backend/tests/acceptance/test_gui_fixture.py`.** The
   mocked GUI unit tests (`backend/tests/test_gui_tools.py`) are
   deliberately excluded from the `gui` population, because they do not
   require a live desktop. If the orchestrator wants `make test-gui` to mean
   "the GUI subsystem" rather than "the tests that need a live GUI", then
   `test_gui_tools.py` joins the population and `make test-fast` loses that
   file's tests - a decision with a measurable cost.
4. **`make test-fast` remains slow.** The suite is hermetic, so an honest
   fast target would have to exclude the acceptance gates (or another large
   named part of the suite) by name. That is a separate item and is
   recorded as a follow-up rather than smuggled in here.
5. **The exact counts are measured, not planned.** The plan states the
   *identities* that must hold (which files carry which marker, and that the
   selected and deselected sets partition the 1609 collected tests) rather
   than hard-coded numbers, because the counts are machine- and
   branch-specific. The expected values - 4 GUI tests, 5 provider-E2E tests,
   1 slow test, 10 deselected by `make test-fast`, 1599 selected - are the
   Implementer's prediction to be confirmed or corrected in the report, with
   the corrected numbers recorded.
6. **CI integration of `make check-test-selections` is not in this item.**
   Item 001 owns `.github/workflows/ci.yml`; adding a second full collection
   per CI run is a separate decision and is recorded as a follow-up.
