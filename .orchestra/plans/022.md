# Plan for 022

## The problem

`DelegationService.validate` is the only gate between a `PROPOSED` specialist
delegation and an admitted (counted) one. The fan-out cap
(`max_specialists_per_task`, default `2`) is enforced by one conditional UPDATE
(`_ADMIT_SQL` in `backend/agents/delegation.py`) plus a module-global
`RLock` (`_admission_lock`) and an explicit `BEGIN IMMEDIATE`. The cap is the
only bound on specialist fan-out per task/goal, so a bypass is a real
boundary breach, not a test cosmetic.

The field evidence (R-030, re-run by the Researcher in
`.orchestra/reports/000-research-6.md` and `.orchestra/reports/000-scout-6.md`)
is an *intermittent* failure of

`backend/tests/test_phase95_hardening.py::TestAdmissionAtomicity::test_two_callers_at_boundary_only_one_admits`

under the in-memory `StaticPool` harness: 2 failures in 10 isolated runs, with
`assert total <= 2` failing at `total == 3` (`max_specialists_per_task == 2`,
one delegation already admitted, both concurrent validators admitted) and the
secondary `assert len(oks) <= 1` failing with both proposals accepted. That is
an admitted count of 3 where the limit is 2.

The decisive open question - and the whole point of this item - is **where**
that bypass happens. The harness deliberately makes two threads share one
`StaticPool` connection (`backend/tests/conftest.py:test_db`, an in-memory
`sqlite://` with `check_same_thread=False`). SQLite connections are **not**
thread-safe; sharing one connection across threads interleaves transaction state
and corrupts reads. Production does **not** share a connection: `DatabaseManager`
(`backend/core/db_manager.py:52-89`) uses a normal `QueuePool` over a file-backed
WAL database, every session checks out its own connection, and `_ADMIT_SQL` is a
single SQL statement that acquires the writer lock for its whole duration.

**Classification expectation (Branch B / harness-only):** the bypass is an
artifact of the shared-connection harness. The cross-process admission test
(`backend/tests/test_admission_concurrency_process.py`) already passes, and a
file-backed, per-thread-session reproduction is expected to pass 20/20. If that
expectation ever fails, the plan switches to Branch A (a production fix of the
admission boundary) and stops; see **Open questions**.

This plan's job is to make that classification into **committed evidence**
rather than an assertion, to document the harness invariant in `delegation.py`,
and to add the file-backed boundary test that the item's acceptance criteria
require. It deliberately performs **no behavioural change to production logic**.

## How it will be proven

### The mechanism in one paragraph

Branch B rests on one fact about SQLite: a single conditional `UPDATE ... WHERE
(SELECT COUNT(*) ...) < :limit` is an ordinary write statement; SQLite's writer
lock serialises two such statements on separate connections, so the second cannot
even *evaluate* its count subquery until the first has committed its new
`VALIDATED` row. The explicit `BEGIN IMMEDIATE` at `delegation.py:453` is an
additional, conservative writer-lease capture, but the statement alone is the
guarantee. The in-memory harness instead gives both threads the *same* DBAPI
connection, so they do not contend on a lock at all - they interleave - which is
exactly the `"sqlite3.InterfaceError: bad parameter..."` / stale-row shape
observed. The cross-process test (`multiprocessing`, two real databases/
connections) is the honest production analogue and already passes; the new
file-backed test in this item makes that honest analogue runnable in the
default collection without spawning a process.

Exact assertions for every admitted-count check (including the new file-backed
test and the existing harness test):

- thread results contain **at most** `limit - already_admitted` (`== 1` here)
  successes, i.e. `len([r for r in results if r.get("ok")]) <= 1`;
- the persisted count never exceeds the cap:
  `active_delegations_for_task(sess, "t-...", None) <= settings.max_specialists_per_task`
  (limit 2 in the test);
- no validator that raised an exception or returned "delegation ... not found"
  is counted as an admission (admission is `rowcount == 1` on `_ADMIT_SQL`,
  nothing else).
- the idempotent already-`VALIDATED` short-circuit is exercised separately:
  calling `validate` on an already-validated id returns `{"ok": True, "reasons": []}`
  and is **not** counted as a new admission (covered by the unchanged
  `validate` early-return at `delegation.py:395-396`).

## The change

### Files to change

- `backend/agents/delegation.py` (**documentation only**).
  - Add a short invariant note next to `_admission_lock` / `_ADMIT_SQL`
    (around the module-level constants, lines 54-81) stating, in plain terms,
    that:
    - the cross-process guarantee lives in the single conditional UPDATE:
      SQLite's writer lock serialises two validators on separate connections, so
      the second's count subquery is evaluated only after the first has committed
      its admission;
    - `_admission_lock` (an in-process `RLock`) is a best-effort fast path only
      and must **not** be treated as the cross-process guarantee;
    - a `StaticPool` / single-connection harness sharing one DBAPI connection
      across threads is **not** a valid concurrency test surface: it bypasses the
      writer lock that is the actual guarantee and produces interleaved state.
      Concurrency evidence must come from per-thread sessions / separate
      processes on a file-backed database;
    - the idempotent already-`VALIDATED` short-circuit
      (`validate`, lines 394-396) is deliberately not folded into the count
      predicate, so a duplicate validator never consumes a second slot.
  - No statement, signature, SQL text, return value, or behaviour change in
    `validate`, `propose`, `active_delegations_for_task`, or any transition.

- `backend/tests/test_admission_concurrency_filebacked.py` (**new file**).
  Structure (mirroring `test_admission_concurrency_process.py`'s setup for
  definitions + `ensure_definitions` + the first admitted delegation, but without
  `multiprocessing`):

  ```python
  MAX = 2   # patched onto settings.max_specialists_per_task

  def _make_db(db_path):
      engine = create_engine(
          f"sqlite:///{db_path}",
          connect_args={"check_same_thread": False, "timeout": 30},
      )
      with engine.connect() as conn:
          conn.execute(text("PRAGMA journal_mode=WAL"))
          conn.execute(text("PRAGMA busy_timeout=5000"))
          conn.commit()
      Base.metadata.create_all(engine)
      return engine

  def _seed(engine):
      session = sessionmaker(bind=engine)()
      svc = AgentService(session); svc.ensure_definitions()
      main = svc.get_or_create_main()
      ds = DelegationService(session)
      first = ds.propose(DelegationRequest(... task_id="t-boundary" ...))
      assert first["error"] is None
      assert ds.validate(first["delegation"].id)["ok"]
      second = ds.propose(... objective="second job" ...)
      third  = ds.propose(... objective="third job" ...)
      assert second["delegation"] is not None and third["delegation"] is not None
      session.commit()
      return second["delegation"].id, third["delegation"].id, session, engine
  ```

  `TestAdmissionFileBacked`:
  - `test_concurrent_admission_boundary_shared_writer_connection`:
    seed a file-backed DB, open one session (one connection), and run two
    validators **behind a `threading.Lock`** (so the single connection is never
    used concurrently). Assert the admitted thread count <= 1 and the persisted
    count <= 2. This is the literal harness-class anti-pattern control; it is
    expected clean, not a production claim.
  - `test_concurrent_admission_per_thread_sessions_at_boundary`:
    seed a file-backed DB, close/commit the seed session (dispose engine),
    reopen with a shared `QueuePool` engine, then spawn **two `threading.Thread`s,
    each creating its own session from that engine**, a `threading.Barrier(2)`
    for start synchronisation, each calling `DelegationService(sess).validate(id)`,
    commit, close. Join both with a 10 s timeout. Assert:
      - both joined (no hang);
      - `len([r for _, r in results if r.get("ok")]) <= 1`;
      - `active_delegations_for_task(check_sess, "t-boundary", None) <= 2`;
      - a re-opened read session sees no row left `PROPOSED` beyond the
        validator outcomes recorded in `results` (no uncommitted partial state).
    No `multiprocessing` and no background daemon thread; `tmp_path` provides the
    file (pytest cleans it up).

- `backend/tests/test_phase95_hardening.py` (**documentation only / no logic**):
  a one-line note in the `TestAdmissionAtomicity` class docstring explaining
  that the in-memory case exercises the shared-connection **harness contract**,
  not the cross-process writer guarantee, and pointing at the new file-backed
  test for production-parity evidence. No test body, assertion, or marker change.

- `backend/tests/test_admission_concurrency_process.py` (**no code change
  required**; re-run and record result). If a flaky child-hang regression is
  observed it may be fixed only in-process cleanup terms, not by weakening the
  assertion.

## Risk

- **Most likely to break (this plan's branch bet):** the production race is real
  but not reproduced by the 20-run file-backed matrix - e.g. a future pool
  configuration (or a DB layer that does not hold the writer lock across the
  statement) could regress it silently. Mitigation: the new file-backed test is
  the canary; it exercises the **actual** `DatabaseManager`-style QueuePool + WAL
  path, and the cross-process test remains the authoritative multi-process
  analogue. If either ever exceeds the cap, the item flips to Branch A and the
  test failure becomes the reproduction.
- **Test-only risk:** the new shared-writer test (`_shared_writer_connection`)
  runs on a file-backed WAL DB with busy timeout; no hang is expected, but
  file locking permissions on Windows tmp paths can be flaky. Mitigation:
  `tmp_path` (pytest-managed, unique), `engine.dispose()`, join timeouts, and
  WAL cleanup in a `finally`. No dangling process is added to default
  collection.
- **Counting risk in tests:** `active_delegations_for_task` sums a task-side
  count and a goal-side count; the new test uses a task-only scope
  (`goal_id=None`) so the helper cannot double-count. This keeps the assertion
  arithmetic identical to `_ADMITTED_COUNT_SQL`'s single OR-clause count for
  this scope.
- **Rollback:** revert the two changed files (`backend/tests/test_admission_concurrency_filebacked.py`
  removed, the comment block in `backend/agents/delegation.py` removed). Zero
  behavioural state changes, no migration, no schema. A `git checkout -- backend/agents/delegation.py`
  plus deleting the new test file restores the tree exactly; the source SQL and
  logic are untouched, so the only risk of dropping the change is that the
  harness-only classification stops being *committed* evidence (the existing
  Researcher measurements remain in `.orchestra/reports/000-research-6.md`).

## Sensitivity

- **Sensitive / data.** The adjudicated classification: `sensitive` (no
  higher / external tier - no network call, no secret, no auth boundary, no
  external dependency involved) and domain **data** (concurrency control over a
  durable admission count). Not `security` specifically, because the fan-out cap
  is a deterministic data invariant enforced inside the protected kernel
  boundary rather than an auth or credential gate; not `api`, because no
  request/response contract, route, schema, or tool argument changes. The
  off-limits surfaces (`backend/models/`, `backend/migrations/`,
  `backend/core/db_manager.py`, auth, secrets, safety gates, public API) are
  untouched. Sensitive-change review is satisfied by pinning the existing
  invariant tests plus the new file-backed boundary test before verification,
  exactly as criteria 2 and 7 require.
- If the implementer ever needs to take Branch A, that branch becomes **both**
  `sensitive` and `data` with a behavioural DB-boundary edit and would need
  re-planning under the same gate; it must not be attempted casually.

## Open questions

None that blocks. The plan is **not** gated on a human decision.

Branch policy for the implementer:

1. Run the matrix first - (a) harness, (b) shared-writer file-backed, (c)
   per-thread file-backed, plus the cross-process counterpart - and record the
   outcomes in the item report before editing any test assertion. If **both**
   (b) and (c) are clean, execute this plan verbatim (Branch B: docs + tests,
   no production behavioural change).
2. If (b) or (c) **fails** the limit, stop. Do **not** classify a real
   production bypass as a harness artifact, and do **not** weaken the existing
   (a) case. Switch to **Branch A**: return to planning with a production fix
   that serialises the read+update at the writer boundary (keep `BEGIN
   IMMEDIATE`, consider an explicit writer lease / a single statement that
   performs the count and update, or moving admission to a reserved writer
   connection), preserving `_ADMIT_SQL`'s `< :limit` intent, the idempotent
   already-`VALIDATED` path, and `validate`'s `{"ok", "reasons"}` contract, then
   re-plan under the sensitive-change gate.
3. If only (a) fails and (b)/(c) are clean, that is the expected harness-only
   outcome and is exactly what this plan captures. The existing in-memory case
   stays in the suite as a diagnostic (not skipped, not xfail'd, not marked):
   its documented purpose is now explicit in the delegation invariant note.
4. `active_delegations_for_task`'s task-vs-goal double-sum is **not** a Branch
   trigger for this item; it is a read-side helper over a different scope shape
   than `_ADMITTED_COUNT_SQL`. If a future item wants to make the two agree
   literally, that is a separate, test-pinned change and is deliberately out of
   scope here.
