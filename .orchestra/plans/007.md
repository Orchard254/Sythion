# Plan for 007

> Item: **007 - The acceptance suite must never write to or delete the product's
> real credential** (candidate R-020).
> Branch: `orchestra/007-no-real-vault-writes`, branched from `master`.
> Scope: **tests only** - no production module is changed by the planned work.
> Every line number below is as of `master` `702ffc5`.

## The problem

`backend/tests/acceptance/test_secret_storage.py::test_credential_manager_round_trip`
(master `:128-148`) constructs the **production** secret store and then writes
to, and finally deletes, the **product's own** Windows Credential Manager entry:

- `:139` `store = secrets_module.CredentialManagerStore()` - the production
  backend, not the in-memory one.
- `:140` `store.set(SECRET_NAME, "sk-roundtrip-zz")` - `CredentialManagerStore.set`
  (`backend/core/secrets.py:66-76`) calls `win32cred.CredWrite` with
  `TargetName = _cm_target(name)` (`backend/core/secrets.py:32-33`) =
  **`Sythion (Synth)/ollama_api_key`** - the exact target the product itself
  writes (`backend/core/secrets.py:143-147` `set_secret` -> `_get_store().set(...)`).
- `:141-146` the `finally` calls `store.delete(SECRET_NAME)` -
  `CredentialManagerStore.delete` (`backend/core/secrets.py:78-87`) calls
  `win32cred.CredDelete` on **that same target**.

The test never requests the `memory_secret_store` fixture (`:27-33`), and
`win32cred` **is** importable on this machine, so `_default_store()`
(`backend/core/secrets.py:112-121`) hands back the real vault whenever the
module-level `_store` has been reset to `None`. The file's only skip is the
`win32cred` `ImportError` (`:134-137`), so **every** full-suite run executes
this test. The exposure is "every run", not "the rare run".

This contradicts the repository's own contract at `docs/ARCHITECTURE.md:358`
("A non-persistent in-memory backend is used for tests so the real vault is
never touched") - a contract that is currently false. A read-only enumeration
(`win32cred.CredEnumerate('Sythion (Synth)/ollama_api_key', 0)`) reports
winerror **1168, "Element not found"**: the entry does not exist right now, and
the `backend/.env` fallback is intact. Whether the entry ever existed - or
whether an earlier full-suite run in this session deleted it - cannot be
determined from the repository. **That is precisely why the fix must not depend
on the entry's presence.**

The fix shape is already known: `_cm_target()` reads the module global
`_CM_TARGET_PREFIX` **at call time** (`backend/core/secrets.py:32-33`), so a test
can pin a test-only prefix and still drive the **real** `win32cred` store. The
acceptance test therefore keeps proving a real Credential Manager round trip
against the real API, while writing to a target the product never uses.

Two things this item must deliver, and they pull in opposite directions:

1. the suite must never write to or delete a product-prefixed target; and
2. the suite must still prove the real round trip - not a mock, not a memory
   store, and not "the test was deleted".

The second requirement is what makes the proof subtle: **a test that merely
asserts "the credential was deleted" passes both before and after the fix**,
because on master the entry is written and then deleted, leaving the vault in
the state it started in. The proof has to observe *which target was written*,
not *whether the vault ended up empty*.

## How it will be proven

### Reproduction (fails on master, passes on the branch)

The reproduction is run with a **throwaway fake-vault recorder** that replaces
the three `win32cred` mutation/read calls with an in-process dictionary. It
therefore performs **no vault operation at all** - it cannot damage anything -
while recording exactly which target names the test wrote and deleted.

**Harness (NOT committed - write it outside the repository, e.g. under the
session temp dir, and put that dir on `PYTHONPATH`):**

`vault_probe.py`, loaded with `pytest -p vault_probe`:

- `pytest_configure`: import `win32cred`; save `CredWrite`, `CredRead`,
  `CredDelete`, `CredEnumerate`; replace all four with fakes backed by one
  in-process dict `target -> blob`:
  - `CredWrite(cred, flags)` - record `("write", cred["TargetName"])`; store
    `cred["CredentialBlob"]` under that target; return `None`.
  - `CredRead(target, type)` - if the target is in the dict, return a dict with
    at least `{"TargetName": target, "CredentialBlob": blob}`; otherwise raise
    `pywintypes.error` (the production `get()` catches `pywintypes.error` and
    returns `""`, which is what the test asserts).
  - `CredDelete(target, type, flags)` - record `("delete", target)`; remove the
    entry, or raise `pywintypes.error` if it was absent.
  - `CredEnumerate(prefix, flags)` - return one dict per stored target whose
    name starts with `prefix` (with `TargetName` and `CredentialBlob`); raise
    `pywintypes.error` when nothing matches, mimicking the real API.
  - The fake blob must be `value.encode("utf-16-le")`, because
    `CredentialManagerStore.get` decodes with `utf-16-le`
    (`backend/core/secrets.py:60-64`).
- `pytest_sessionfinish(session, exitstatus)` - print every recorded operation
  and then decide:
  - **FAIL (exit 1)** if any recorded target starts with `Sythion (Synth)/`
    (a product-prefixed target was written or deleted);
  - **FAIL (exit 1)** if **no** vault mutation was recorded at all (the round
    trip is no longer exercised - the anti-mock tripwire);
  - **FAIL (exit 1)** unless the recorded operations contain a `write` to some
    non-product target followed by a `delete` of the same target (a
    write-then-delete round trip, not a one-sided poke);
  - otherwise **PASS (exit 0)**.

**The command (identical on both trees):**

```
# from the repository root, with the harness directory on PYTHONPATH
python -m pytest backend/tests/acceptance/test_secret_storage.py -q -p vault_probe
```

* On **master**: the harness prints
  `write Sythion (Synth)/ollama_api_key` and `delete Sythion (Synth)/ollama_api_key`
  and exits **1** with `PRODUCT TARGET WRITE DETECTED`. Note that pytest itself
  reports `10 passed` in this mode - the fake vault makes the round trip work in
  memory - so the **harness's exit status and its printed record are the
  verdict**, not pytest's summary. This is the whole point: on master the
  vault ends in exactly the state it started in, so any check that only looks
  at the end state passes on master too.
* On the **branch**: the harness prints
  `write Sythion (Synth) [TEST]/ollama_api_key` and
  `delete Sythion (Synth) [TEST]/ollama_api_key` and exits **0**.

**Secondary reproduction - the committed guard fires against master's own
offending test (this is the guard's teeth against the real defect):**

```

# 2. git show master:backend/tests/acceptance/test_secret_storage.py > backend/tests/acceptance/test_secret_storage.py
# 3. python -m pytest backend/tests/acceptance/test_secret_storage.py -q     -> MUST FAIL (exit 1)
# 4. restore the branch's copy and confirm it is byte-identical again
```

**Safety precondition for steps 2-3 (read it, do not skip it):** the guard
described below must **check the target BEFORE delegating to the original
`win32cred.CredWrite` / `CredDelete`**. If the check came after the call, step 3
would really write - and on a machine where the product credential exists,
really overwrite - the developer's key. Before running this reproduction, read
the guard's implementation and confirm the ordering. On this machine the
product entry does not exist, so the worst case would be a transient bogus
entry that master's `finally` deletes - but the plan does not rely on that.

**Third reproduction - the read-only enumeration of the product target,
before and after (corroborating, NOT the proof):**

A read-only helper (run by hand, never committed) that calls
`win32cred.CredEnumerate(prefix, 0)` and reports **only** the match count and
the `TargetName` values - the `CredentialBlob` is never read, logged or
asserted on:

* before the run: enumerate the exact target `Sythion (Synth)/ollama_api_key`
  and the product prefix `Sythion (Synth)/`;
* run `python -m pytest backend/tests/acceptance/test_secret_storage.py -q`;
* after the run: enumerate the same two things again, plus the test prefix
  `Sythion (Synth) [TEST]/` (expected: empty - the test cleans up after itself).

The before and after results must be **identical** (on this machine: the
product target is absent - winerror 1168 - and the product prefix enumerates
empty, before and after).

**State this honestly in the report:** this enumeration check is *corroborating
only*. It is trivially satisfied when the product credential does not exist
(which is the case here), **and it is also satisfied on master**, because
master writes the entry and then deletes it, leaving the vault as it was. The
proof is the harness record (which target was written) plus the committed
guard (which fails the run if any product-prefixed target is attempted). The
enumeration is what makes the *absent* state non-vacuous - see the self-check
below, which proves the enumerator is capable of seeing an entry.

### Test that pins the invariant

**1. The committed guard - `backend/tests/acceptance/conftest.py`.**

An **autouse, function-scoped** fixture (using pytest's `monkeypatch`, so it is
undone automatically after every test) that:

- imports `win32cred`; if the import fails, the fixture is a **no-op** (the
  guard must never turn a non-Windows machine into a failing suite);
- snapshots the production prefix **at conftest import time**, e.g. as a
  module-level constant assigned from `backend.core.secrets._CM_TARGET_PREFIX`
  - **not** read at call time. This matters: the round-trip test pins that same
  module attribute to a test-only prefix, and a guard that read the attribute
  dynamically would be **disarmed by the very fix it is meant to police**. The
  guard must compare against the snapshot taken before any test can patch it;
- wraps `win32cred.CredWrite` and `win32cred.CredDelete` so that the
  `TargetName` (for `CredWrite`, `cred["TargetName"]`; for `CredDelete`, the
  first positional argument) is checked against that snapshot;
- if the target starts with `Sythion (Synth)/`, it raises **before** delegating
  to the original function, with a message that names the offending target and
  the test that attempted it (`request.node.nodeid`);
- otherwise it delegates to the original function unchanged.

The exception it raises must **not** be a `pywintypes.error`:
`CredentialManagerStore.delete` swallows those
(`backend/core/secrets.py:84-86`, `except pywintypes.error: pass`), so a
`pywintypes.error` would make the delete path look like it had no teeth. Use a
dedicated class derived from `AssertionError` (or `pytest.fail`), which pytest
reports as a failure.

The guard must **not** touch `secrets_module._store` and must **not** intercept
`CredRead` - reads are non-destructive, and blocking them would change what
other acceptance tests observe.

**2. The round-trip test - `backend/tests/acceptance/test_secret_storage.py`.**

`test_credential_manager_round_trip` keeps its shape and keeps driving the
**real** `win32cred` store; only the target changes and the proof gets
stronger. Concretely:

- add a module-level constant `_PRODUCT_TARGET_PREFIX`, a **snapshot** of
  `secrets_module._CM_TARGET_PREFIX` taken at import time (same reason as the
  guard: the test itself patches that attribute), and a module-level constant
  `_TEST_TARGET_PREFIX = "Sythion (Synth) [TEST]/"`. That prefix is chosen so
  that it is (a) **not** under the product prefix - the character after
  `Sythion (Synth)` is a space, not a `/` - and (b) visibly test-scoped to a
  human browsing the Credential Manager, so a leftover is identifiable;
- inside the test, pin the prefix with
  `monkeypatch.setattr(secrets_module, "_CM_TARGET_PREFIX", _TEST_TARGET_PREFIX)`;
  this works because `_cm_target()` reads the global at call time
  (`backend/core/secrets.py:32-33`);
- inside the test, pin the active store with
  `monkeypatch.setattr(secrets_module, "_store", store)` where `store` is the
  production `secrets_module.CredentialManagerStore()`. This makes the
  module-level helpers (`has_secret`, `list_secret_names`) resolve to the real
  store instead of a `MemoryStore` that another test may have left behind, and
  `monkeypatch` restores the previous `_store` value afterwards;
- assert the target the test is about to write, **against the snapshot**:
  the composed target (`_cm_target(SECRET_NAME)`) equals
  `Sythion (Synth) [TEST]/ollama_api_key` **and** does not start with
  `_PRODUCT_TARGET_PREFIX`. (Comparing against the *patched* attribute would
  be a tautology - it would always be true.)
- keep every existing assertion unchanged: after `set`, `store.get(...)`
  returns the value, `has_secret(...)` is `True`, `SECRET_NAME` is in
  `list_secret_names()`; after the `finally` delete, `store.get(...)` is `""`
  and `has_secret(...)` is `False`. The `finally` must still delete - now the
  **test-scoped** target.
- add one **read-only self-check inside the test**, while the credential still
  exists: enumerate `win32cred.CredEnumerate(_TEST_TARGET_PREFIX, 0)` and
  assert that the test target is among the enumerated `TargetName`s, reading
  **no blob**. This is the anti-mock tripwire for the normal (uninstrumented)
  suite run: a `MemoryStore`, a mocked `win32cred`, or a test that stopped
  touching the vault would make this assertion fail. It also proves that the
  enumerator used by the before/after check above is capable of seeing an
  entry - which is what makes "the product target is absent" a real
  observation rather than a broken enumerator.
- update the docstring: it currently says "then cleans up"; it must say the
  test writes and deletes a **test-scoped** target and never the product's.

## Risk

### What is most likely to break

1. **The defining risk: the fix stops the real-vault write and also stops the
   test proving anything, while the suite stays green.** "The Credential
   Manager round trip is no longer tested" is exactly what a lazy fix looks
   like - swap in `MemoryStore`, or delete the test, or skip it on Windows, and
   the suite is green and the vault is untouched. **How the plan makes it
   detectable:**
   - the committed test still constructs the production
     `CredentialManagerStore()` and calls the real `win32cred` API - visible in
     the diff;
   - the **in-test read-only enumeration self-check** fails if the credential
     is not really in the vault (a memory store, a mock, or a skipped write
     all make it fail);
   - the **harness's tripwires** fail if no vault mutation was recorded at all,
     or if the recorded operations are not a write followed by a delete of the
     same non-product target - so "the test no longer touches `win32cred`" is a
     hard failure of the reproduction, not a green run;
   - the acceptance suite's per-test outcome set is unchanged (JUnit
     comparison), so the round-trip test cannot have quietly become a skip.
   A reviewer should treat "the round-trip test no longer asserts a write and
   a delete" as a criterion failure, not as a simplification.
2. **The guard disarms itself.** If the guard read
   `secrets_module._CM_TARGET_PREFIX` at *call* time, the round-trip test's own
   monkeypatch would move the prefix the guard checks against, and the guard
   would never fire. The plan requires the **import-time snapshot**; a reviewer
   must check it.
3. **The guard's delete path looks toothless.** `CredentialManagerStore.delete`
   swallows `pywintypes.error` (`backend/core/secrets.py:84-86`). If the guard
   raised a `pywintypes.error`, the delete attempt would be swallowed and the
   guard would appear to pass. The guard must raise something that is **not** a
   `pywintypes.error`.
4. **Pinning the secret store to a memory store for the WHOLE acceptance
   suite.** This is the quiet way to "fix" the item, and it would change what
   other acceptance tests observe: `has_secret()` / `list_secret_names()` /
   `resolve_ollama_api_key()` would answer from a `MemoryStore` instead of the
   real vault in every acceptance test, silently changing the answers that
   `backend/api/routes.py:2007` and `:2261` (the R-023 sites) compute. The
   plan forbids it explicitly: **no autouse fixture may call
   `set_secret_store_for_testing(...)`**, and the guard must not touch
   `secrets_module._store`. The only store pinning is the per-test
   `monkeypatch.setattr(secrets_module, "_store", store)` inside
   `test_credential_manager_round_trip`, which `monkeypatch` undoes
   automatically. The JUnit per-test outcome comparison is the check that
   nothing else moved.
5. **A legitimate future test needs a product-target write** and the guard
   turns it red. That is the guard working as intended, but the failure must
   be actionable - the message names the offending target and the test's node
   id, and the report notes that such a test needs an explicit, reviewed
   exemption rather than a silent prefix change.
6. **A stray test-scoped credential survives a crashed run** (see "new public
   surface"). Mitigation: the `finally` delete, the post-delete assertions
   (`get(...) == ""`, `has_secret(...) is False`), and a visibly test-scoped
   name. The operator check for strays belongs in the follow-up entry.
7. **The guard is acceptance-scoped only.** A future test *outside*
   `backend/tests/acceptance/` that writes to the vault would not be caught.
   Moving the guard to the root `backend/tests/conftest.py` is the right
   follow-up, but that file is contended by items 002 and 006 - this item must
   not create that conflict. Recorded as a deferred follow-up, not done here.
8. **Residual doc debt (honest-debt reporting, no change here):**
   `docs/ARCHITECTURE.md:358` ("A non-persistent in-memory backend is used for
   tests so the real vault is never touched") is currently **false**. After
   this fix the suite still performs a real `win32cred` write/delete - at a
   test-scoped target - so the sentence becomes "nearly true" rather than
   exactly true. `docs/ACCEPTANCE_TESTS.md:199` ("Secrets in Credential
   Manager mock") is also inaccurate: the test uses the **real** vault, before
   and after this change. Both wording fixes belong to the documentation item
   (003) or to a follow-up; criterion 4 forbids touching them here, and this
   plan does not try to.

### Rollback

- `git revert` the merge commit, or restore the two files from `master`
  (`git checkout master -- backend/tests/acceptance/conftest.py
  backend/tests/acceptance/test_secret_storage.py`). The rollback reinstates
  the defect - it is not a safe state - so it is a revert of a fix, not a
  forward step.
- Residue to clean up by hand afterwards: a stray
  `Sythion (Synth) [TEST]/ollama_api_key` entry, if a run was interrupted

- Nothing outside the repository is touched by the rollback: no schema, no
  API, no published artefact, no credential value is read or written by this
  item at the product target.

## Sensitivity

### Tier

**`sensitive`** - and the reason is substantive, not only lexical: the change
sits directly on the Windows Credential Manager path and installs a fixture
that intercepts credential writes and deletes. A mistake here either destroys
a real credential or hides that it did. The change is **test-only** and does
not modify any production module, so it does not reach `sensitive+external`.

**Agreement with the orchestrator's classifier, stated honestly:** the
classifier is a keyword screen, and this item's changed files, title and
acceptance criteria all contain the words *secret*, *credential* and *delete*,
so the classifier will flag SENSITIVE **regardless of substance** - a change
that merely renamed a fixture would be flagged the same way. My prediction
therefore agrees with the classifier, and it agrees for a reason the
classifier cannot see: the change really is in the credential-storage area,
and the invariant it protects is "the product's credential is never written or
deleted by a test". The Scout's prediction (tier `sensitive`, domain
`security`) is correct.

The nearest argument for `external` is that the defect's effect lands outside
the repository, in the OS credential vault. That effect is precisely what this
item eliminates, and the change itself touches no external service, no CI, no
published artefact and no network - so `sensitive` is the right tier.

### Domain

**`security`** - the protected subject is a secret (the Ollama API key) held
in an OS credential store, and the property being pinned is a
credential-integrity / least-privilege property (tests may not write to the
product's credential target). `data` would describe a defect about stored
records; `access` would describe an authentication or authorisation defect;
neither fits. `security` is correct.
