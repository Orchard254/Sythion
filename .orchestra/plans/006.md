# Plan for 006

## The problem

`backend/core/config.py:173-176` points pydantic-settings at `<repo>/backend/.env`
with `env_prefix="SYTHION_"`, and `:179` builds the `settings` singleton **once, at
import**. `backend/.env` is gitignored (`.gitignore:16`), so it exists in a developer's
working tree and in NO clean checkout and on NO GitHub Actions runner. The
Researcher's 2x2 matrix (R-019) proved that the file and the `SYTHION_OLLAMA_API_KEY`
environment variable are **alternatives** - either one alone satisfies the consumer at
`backend/api/routes.py:2261` (`key_ok = has_secret(OLLAMA_API_KEY) or
bool(settings.ollama_api_key)`), and only the complete absence of both fails.

Exactly **ONE** test in the suite depends on that ambient state:
`backend/tests/test_setup_readiness.py::test_readiness_states` (`:144-177`). It builds
a fully healthy world - fake provider healthy (`:147`), `resolve_selected_model`
pinned to `"m1"` (`:49`), a real inference persisted (`:151`), safe settings applied
(`:152`), voice assets monkeypatched (`:153-156`) - and pins **nine of the ten**
readiness checks; the tenth, `ollama_api_key_ok`, is the one it leaves to the ambient
state, because it never calls the isolation helper its own two sibling tests use
(`_clear_local_env_key` at `:195-204`, called at `:215` and `:237`). In the test the
secret store is a fresh empty `MemoryStore()` (`:63`, `:145`), so `has_secret` is
False and the tenth check depends entirely on `settings.ollama_api_key`.

The consequence is the asymmetry that makes this a release-confidence defect, not a
style nit: **in the orchestrator's main tree the test passes today, and in a clean
checkout it fails** (`1 failed, 7 passed`). The pipeline item 001 repaired would go
RED on its first real run (`goal.md` budget note; `.orchestra/follow-ups.md:16`
tells the human to EXPECT that red). The no-credential answer is the CORRECT
first-run answer and is asserted on purpose at `:207-227`; a packaged install never
has a `.env` at all (`scripts/verify_release_payload.py:53-59`). This is therefore a
**test-isolation** defect. It is fixed in the tests, and only in the tests.

## How it will be proven

### The proof environment (this is the part that must be right)

The proof is meaningless in the developer's tree, because there `backend/.env` exists
and the test passes for the wrong reason. The proof MUST be run in a tree where that
file is **absent**.

**Chosen method: a detached git worktree (a clean checkout of the tracked files).**
It is used for two reasons and not for convenience:

* it is byte-for-byte the situation a GitHub Actions runner is in - the tracked files
  and nothing else. `git ls-files -- backend/.env` is EMPTY (R-019), so the worktree
  physically cannot contain the developer's `.env`;
* the working tree is 5.7 GB (the `backend/` package alone is 31 MB), so a full
  "scratch copy of the tree" is impractical; a worktree is a checkout, ~40 MB, seconds
  to create. (A selective copy of `backend/` + `scripts/` + `pytest.ini` is the
  documented fallback if a worktree is not permitted - it must copy TRACKED files
  only, so the `.env` cannot come along.)

**The developer's `backend/.env` is never read, copied, moved, renamed or deleted by
any step of this plan.** The only `.env` any step ever writes is a DUMMY one, written
inside a scratch worktree, containing only non-secret placeholders.

Worktree layout (the run already uses this location for item 002's worktree):

```
C:\Users\orcha\AppData\Local\Temp\opencode\wt-006-before   <- the "before" code
C:\Users\orcha\AppData\Local\Temp\opencode\wt-006-after    <- the branch code
```

```powershell
$repo = "C:\Sythion\sythion"
$tmp  = "C:\Users\orcha\AppData\Local\Temp\opencode"

# "before" = the commit the branch was cut from (record it in the item report at
# branch time; it is master's tip at that moment). Using the recorded base SHA
# keeps the comparison valid even after the Committer merges the branch.
git -C $repo worktree add --detach "$tmp\wt-006-before" <BASE_SHA>
# "after"  = the branch tip (or master, if the Committer has already merged)
git -C $repo worktree add --detach "$tmp\wt-006-after" orchestra/006-readiness-test-isolation

# The precondition that makes the proof meaningful: NO .env in either worktree.
foreach ($wt in @("$tmp\wt-006-before", "$tmp\wt-006-after")) {
    if (Test-Path "$wt\backend\.env") { throw "WORKTREE IS NOT CLEAN: $wt" }
}
```

`git worktree add --detach` creates NO branch and NO commit, and the worktrees are
scratch copies: remove them when the verification is done
(`git -C $repo worktree remove --force <path>`; `--force` is needed only because the
test run leaves `__pycache__`/`.pytest_cache`/a dummy `.env` behind, all of which are
gitignored - `.gitignore:2,8,16`).

**The environment variable must also be cleared.** The 2x2 matrix says the env var is
an ALTERNATIVE to the file, so a run that leaves `SYTHION_OLLAMA_API_KEY` exported
proves nothing (it would make the "before" tree pass). Every verification run
therefore executes in a child process with no `SYTHION_*` variable:

```powershell
Get-ChildItem Env: | Where-Object { $_.Name -like "SYTHION_*" } |
    ForEach-Object { Remove-Item -Path "Env:$($_.Name)" }
if (Get-ChildItem Env: | Where-Object { $_.Name -like "SYTHION_*" }) { throw "SYTHION_* is still set" }
```

Run this in the Verifier's own PowerShell session. It removes variables from that
session only; it never touches `backend/.env`. (The Researcher's equivalent helper
was a `run_env.py` outside the repo that scrubbed the child environment; either form
is acceptable as long as the scrub is demonstrated to have happened.)

**Never set `SYTHION_RUN_PROVIDER_E2E=1` during verification.** It would make the two
provider-e2e modules attempt live provider calls (network, cost, a real credential).
They must stay skipped, exactly as they are in every normal run.

the readiness endpoint only asks whether the key is non-empty.

### Test that pins the invariant

Three layers, and they pin different things:

1. **`test_readiness_states` (strengthened, `backend/tests/test_setup_readiness.py:144-177`).**
   It now states the tenth check instead of inheriting it. In the healthy block it
   asserts `body["checks"]["ollama_api_key_ok"] is True` next to
   `body["full_ready"] is True`; in the incomplete block it asserts
   `body["checks"]["ollama_api_key_ok"] is True` **and**
   `body["checks"]["selected_model_ok"] is False` **and**
   `body["full_ready"] is False`. The credential is pinned for the whole test, so the
   two blocks differ ONLY in what the test is about (model selected, inference
   verified, safe settings applied) - the credential is a constant, not a variable.
   The incomplete block is what makes the test meaningful rather than merely green: a
   configured credential must NOT be enough for readiness, so a hard-coded `True` in
   the endpoint would fail it.
2. **A new test in the same file: the readiness credential check follows the
   effective configuration.** With the credential cleared it must report
   `ollama_api_key_ok is False`; with the credential pinned it must report
   `ollama_api_key_ok is True`; and the response body must never contain the pinned
   value. This is non-vacuous in EVERY environment (it exercises the check in both
   directions) and it fails if anyone hard-codes the answer.
3. **A new test in the same file: the suite does not inherit the local `.env`.** It
   asserts that the three effective settings values equal the values a `Settings`
   instance has when the env file is disabled (`Settings(_env_file=None)`). It fails
   if the conftest neutralisation is removed or a field is dropped from the list. It
   is a discriminator in a tree that HAS a `backend/.env` and a tautology in a clean
   checkout - state that honestly in the item report rather than overselling it.

The environment-level invariant is the fourth layer and the only one that is
meaningful in the "both states of the world" sense: the suite's outcome set must be
the same with and without a `backend/.env` (criterion 3's check above).

## Risk

### What is most likely to break

**R1 - the global-PIN mistake (the obvious way to get this wrong).** A fix that
pins a credential GLOBALLY - an autouse fixture in `backend/tests/conftest.py` that
sets `settings.ollama_api_key` to a non-empty value - changes what EVERY other test
observes. The suite's own sibling test `test_a_clean_installation_without_credentials_is_not_ready`
(`:207-227`) asserts the NO-credential behaviour, and the tests that assert a
CONFIGURED key would see a key that no test configured. Note honestly: that sibling
test calls `_clear_local_env_key` itself, so it would NOT by itself catch a global
pin - the reliable detectors are the diff and the new isolation test.

How this plan avoids it, and how a reviewer can tell the difference:

* the conftest fixture assigns ONLY clean values (empty by default). A global pin
  would show up in `git diff master -- backend/tests/conftest.py` as a non-empty
  literal; this plan's diff contains none, and the values it assigns come from a
  snapshot built with the env file disabled;
* the credential is introduced ONLY inside `test_readiness_states`, by the file's own
  helper, function-scoped and undone by `monkeypatch` at teardown;
* the new test "the suite does not inherit the local `.env`" FAILS if the conftest
  assigns anything other than the clean values - it is the teeth of the isolation;
* the four-file outcome-set equality (criterion 3) breaks if the fixture changes a
  value some test depends on;
* the two sibling tests must still pass in BOTH the developer's tree and the
  worktree (`ollama_api_key_ok is False` before, `is True` after the key is stored).

**R2 - the WRONG-REASON risk (the test goes green without testing anything).** "The
credential is pinned" is not "the readiness endpoint correctly reports ready when a
credential is configured". This plan keeps the test meaningful in three ways: the
healthy block asserts the tenth check EXPLICITLY instead of inheriting it; the
incomplete block reports a CONFIGURED credential and still `full_ready is False`
(a hard-coded `True` would fail it, and so would a key check that ignores the rest
of the world); and the new test exercises the check in BOTH directions (cleared ->
False, pinned -> True) and asserts the response never echoes the credential. The
other nine checks are already pinned by the test's own monkeypatches and by the
inference / safe-settings POSTs, so the tenth is the only thing the pin changes.

**R3 - the neutralising fixture changes what every test observes (the benign form
of R1).** It is bounded to three fields and always moves TOWARD "what a clean
checkout has", so it can only align the local tree with CI - it can never make a
test depend on something CI does not have. The established fact is that exactly ONE
test depends on the missing `.env`; the criterion-3 and criterion-5 checks are
designed to catch any other, and the delta comparison in the full-suite proof makes
a silent change impossible to miss.

**R4 - the `provider_e2e` carve-out.** Without it, a developer whose ONLY credential
lives in `backend/.env` would find the opt-in live-provider run failing with a
confusing 401 (the import-time gate passes, the runtime key is gone). With the
carve-out those two modules keep the ambient value and behave exactly as they do
today. The cost of the carve-out is that the neutralisation is not literally
"for every test"; the carve-out is confined to the two modules that are explicitly
opt-in (`SYTHION_RUN_PROVIDER_E2E=1`) and that declare in their own docstrings that
they need a real provider credential. The criterion-3 proof set contains none of
them. This deviation is recorded in the item report.

**R5 - the merge with item 002.** Both items edit `backend/tests/conftest.py`.
Sequence: build 006 AFTER item 002 merges (the backlog's build order). The new code
is appended at the end of the file and the existing `_guarded_autonomy_default`
fixture is left untouched, so a textual conflict is unlikely; if there is one,
resolve by keeping BOTH item 002's classification rules and item 006's neutralising
fixture. If item 002 has NOT merged when 006 is built, the plan still holds - the
verification steps do not depend on 002's content - but `pytest.ini` will not exist
yet, so the suite runs with `inifile: None` and item 002's selection-contract guard
is absent; note that in the item report.

**R6 - the known native crashes (R-007).** The full suite is not deterministic on
this machine (a COM burst and a native sqlite3 access violation). A truncated run is
a known baseline condition: re-run it and compare outcome SETS, never raw output.

**R7 - a malformed dummy `.env`.** A bad `SYTHION_FILE_ROOTS` value would make
every import of `backend.core.config` fail and would look like a product defect.
The import guard (`python -c "import backend.core.config"`) runs before any pytest
invocation in the "with .env" steps.

**R8 - the full-suite run triggers item 007's known defect** (the acceptance suite
writes and deletes the product's credential target in the real Windows Credential
Manager). It is item 007's subject; do not report it as a failure of this item and
do not fix it here.

`git checkout master -- backend/tests/conftest.py backend/tests/test_setup_readiness.py`.
No production code, no schema, no data, no configuration outside the repository and
no state on the machine is touched by this item, so there is nothing else to undo.
The `.orchestra/follow-ups.md` note is a text edit and is reverted by editing the
text. The scratch worktrees are removed with `git worktree remove --force <path>`;
they contain only generated artifacts and the dummy `.env`.

## Sensitivity

**Tier: `sensitive`.**
The change writes a value into the field the product reads as the API key
(`settings.ollama_api_key`) and it deliberately changes what every test in the
process observes about the presence of a credential. A mistake - a real value
instead of a placeholder, a pinned credential that leaks into a report, a fixture
that leaks across tests - would put a credential into a test artifact or hide a
credential-dependent behaviour. It is not `external`: no network, no third-party
system, no credential is used to reach anything, and the live-provider path is left
exactly as it is. It is more than `none` because the credential path is the subject
and the change is process-global inside the test run. The mitigations are in the
plan: the only literal introduced is the repository's existing placeholder
`"test-key"`, the conftest fixture assigns only clean values, and no credential
value is ever read, printed or written by any step of the implementation or the
verification.

**Domain: `security`.**
The subject is secret/credential handling - the readiness endpoint's credential
check, the secret store interaction, and the boundary between a developer's local
credential and a test's own fixture. This is the same domain item 007 (the
acceptance suite writing to the product's credential target) was assigned. It is
not `api` (the HTTP contract is untouched - `backend/api/routes.py` is not
modified), not `data` (no schema, no migration, no stored data), not `access` (no
authentication, token issuance or origin checking) and not `infra` (no CI, release
or packaging change).

## Open questions

Nothing here needs a human decision to execute the plan. The following are recorded
deviations and assumptions, to be stated in the item report rather than resolved by
guesswork:

1. The `provider_e2e` carve-out is a deliberate, documented deviation from criterion
   3's "for every test" (Risk R4). The criterion's proof set is unaffected.
2. In the criterion-3 comparison, "the copy with `.env` present" is a scratch
   worktree carrying a DUMMY `.env` with placeholder values. The developer's real
   `.env` is never copied, read or printed.
3. The `.orchestra/follow-ups.md` update (criterion 6) is an orchestration state
   commit, not part of the branch, so that criterion 4's `git diff --name-only` check
   lists only files under `backend/tests/`.
4. The clean snapshot is computed once at conftest import. If a future test mutates
   `SYTHION_OLLAMA_API_KEY` / `SYTHION_SELECTED_MODEL` / `SYTHION_FILE_ROOTS` in the
   process environment, the snapshot must move to a session-scoped fixture; no test
   does this today (the only `SYTHION_*` variables the suite sets are
   `SYTHION_AUTONOMY_LEVEL`, `SYTHION_DATA_DIR` and `SYTHION_HANDSHAKE_TOKEN_FILE`).
5. The full-suite acceptance check is a DELTA against the base in the same
   environment, not an absolute count, because this item intentionally changes what
   the developer's tree observes; the absolute numbers (expected 1564 passed /
   45 skipped) are still recorded.
6. The full-suite verification run also executes item 007's known credential-vault
   defect. It is not this item's failure and is not fixed here.
