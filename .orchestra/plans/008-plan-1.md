## 1. Goal and rationale

Close the concurrency defect that turns `DbEventLedger.append_event` into a read-modify-write race:

- Invariant for the phase-2 verification: **`100` threads × `10` events per task** (one pre-created task) produces **exactly `1000` unique, gapless, monotonic sequence numbers per task** (`set(1..1000)` with no duplicates and no gaps), with **worker exceptions propagated** out of thread targets rather than swallowed by `threading`, and `count(task_events WHERE task_id=tid) == 1000`.
- Preserve the protected-runtime contract: `append_event` still participates in the caller's state-transition transaction (event + state commit atomically); `autoflush=False` sessions are still supported; SQL-level event-history replay and `GET /api/v1/tasks/{task_id}/events` stay byte-compatible (no HTTP schema change); `EventLedger.append_event` keeps the `(task_id, event_type, event_data) -> int` signature.
- The fix must not rely on in-process serialisation only: cross-session and cross-`DatabaseManager` contention over the same file must be handled by the database transaction, because routes/specialist agents create their own managers.

Root cause in one sentence: `backend/runtime/events.py:47-52` reads the committed per-task maximum, `events.py:56-64` computes `sequence = max(committed_max, pending_max) + 1` over data whose concurrency isolation is SQLite's deferred reader, then adds a row (`events.py:72`) carrying that number; a second session that reached step 3 before the first commits commits its row with the *same* number and hits `uq_task_events_task_sequence` (`backend/core/db_manager.py:129-130`), failing the whole transaction (up to 50% event loss, memory id 1270 + 010-research-1).

## 2. Threat surface (what mutates state and what must happen, in what order)

`DbEventLedger.append_event` is not a pure audit append in two senses that a fix must respect:

1. **Transactional participation.** Every one of the 179-ish call sites (88 non-test call sites, 28 construction sites per 010-research-1 §5) expects the event row to be *lawfully present iff* the caller's state transition lands. If `append_event` moves sequence allocation into an isolated transaction, a rolled-back state change would still have consumed a sequence number and, worse, an uncommitted event row would survive — both violate "history is the authoritative execution record" (docs/PROTECTED_RUNTIME_CONTRACT.md §5). Allocation must happen on the caller's transaction and roll back with it.
2. **Caller ordering.** In the common runner shape the sequence is:
   ```
   task_runner.transition_state(tid, new_state, event_type, data)   # Python
       -> validates ALLOWED_TRANSITIONS
       -> appends the state-change event via ledger.append_event(...)   # same session
       -> session.commit()                                             # one atomic commit
   ```
   So `append_event` always runs **inside** an already-open (possibly reader-pinned) transaction and must upgrade that transaction to a writer at allocation time without restarting or arming a read snapshot. Around 88 call sites mean the upgrade behaviour must be transparent to callers — no API change.
3. **Cross-task interleaving is fine; same-task is not.** `test_kernel_concurrency.py:224-249` demonstrates two ledgers in one session on `task-a` / `task-b` concurrently via `asyncio.sleep(0)`; that passes today because sequence spaces are disjoint. Any fix must keep `task-a` advancing one sequence at a time, independently of `task-b`, and must not force a process-wide/global sequence.
4. **The unique guard is non-negotiable.** `uq_task_events_task_sequence` is the backstop that has been making the failure visible as `IntegrityError` instead of silent data corruption (010-research-1 §4). It must remain (or be strengthened), not removed.
5. **What must not happen.** Allocating a sequence in a separate connection; re-reading the max and retrying **alone** (approach (a)) — with SQLite deferred isolation the retry reads the same stale committed value plus only this session's pending rows, so collisions remain on closed systems; serialising the whole database (global lock) instead of the per-task write transaction (would starve unrelated tasks and kill throughput across the 88 call sites); silently truncating failed allocations (the defect being fixed).

## 4. Chosen approach

**Hybrid of (b) DB-managed per-task counter + transactional write serialisation, generalised slightly, with no primary reliance on (a) or (c).**

Concretely:

- Add a small first-class counter table `task_event_sequences (task_id PRIMARY KEY, next_seq INTEGER NOT NULL)` — approach (b). Allocation becomes a **single atomic UPSERT that reserves the next number while incrementing the counter**, executed on `self._session` so the counter participates in the caller's transaction and rolls back with it.
- This makes the UPSERT itself the serialisation boundary — approach (d) at statement level: SQLite serialises writers at the database file, so two sessions cannot both increment-and-return the same `next_seq`; the second blocks on the writer lock with the configured busy-timeout rather than reading a stale value. No retry is needed on the happy path and the deferred-isolation "stale reader" window disappears because there is no separate read step.
- Keep (a) **bounded N=8 optimistic retry per append** only as a defensive backstop for allocation-level `IntegrityError` (e.g. a row inserted out-of-band into `task_events` with a sequence the counter does not know about). The test harness that pins the count must *not* mask these: a retry exhausted must surface as a deterministic error, not a green run.
- Do **not** add an in-process per-task `threading`/`asyncio` lock (approach (c)) as a correctness dependency. Two reasons: (i) 100 test threads over the same file already form a cross-connection test of correctness and the DB lock handles it; (ii) an in-process lock adds re-entrancy/lookup state and only covers same-process callers, which the routes/agents that create their own `DatabaseManager` per request would still fail. Rationale is recorded so the reviewer does not ask "why no c?".
- Cross-process reader visibility is inherited from the busy timeout plus SQLite's commit publication. We also harden connection setup so the wait budget applies to *every* connection, not just the bootstrap connection (`backend/core/db_manager.py` currently sets `PRAGMA busy_timeout=5000` once at bootstrap only).

### 4.1 Allocation statement (to be placed verbatim in `DbEventLedger.append_event`)

```sql
INSERT INTO task_event_sequences (task_id, next_seq)
VALUES (
    :task_id,
    COALESCE(
        (SELECT MAX(sequence_num) + 1 FROM task_events WHERE task_id = :task_id),
        1
    )
)
ON CONFLICT(task_id) DO UPDATE SET
    next_seq = CASE
        WHEN task_event_sequences.next_seq >= COALESCE(
            (SELECT MAX(sequence_num) FROM task_events WHERE task_id = :task_id), 0
        )
        THEN task_event_sequences.next_seq + 1
        ELSE COALESCE(
            (SELECT MAX(sequence_num) FROM task_events WHERE task_id = :task_id), 0
        ) + 1
    END
RETURNING next_seq
```

Semantics:
- If there is no counter row yet, seed from `MAX(sequence_num)+1` of existing `task_events` rows (handles pre-existing/imported tasks without creating a one-per-task manual sequence scan on every call).
- If the counter is ahead of the table, increment the counter — keeps contention repair-proof when a row was added manually or earlier rollbacks left the counter lagging/leading correctly.
- If a row was inserted out-of-band at a higher sequence, lift `next_seq` to `MAX(sequence_num)+1` instead of reusing the lower counter — gaplessness is preserved across "import then append".
- `RETURNING` hands back the allocated number, which becomes the new event's `sequence_num` and the method's return value.
- Everything runs inside the session's current transaction: if the caller rolls back, the counter update rolls back too, so no phantom gaps from dead transactions.
- The subquery sees **this** session's own uncommitted `task_events` rows because SQLite's intra-transaction reads are self-consistent, so per-transaction multiple appends allocate strictly increasing integers.

### 4.3 Why (a) alone is rejected (for the record)

Under a fresh `fresh_db()`-style deferred session, approach (a) re-runs `SELECT MAX(sequence_num)` and sees only committed values plus this session's pending rows, re-allocating the same number; the winning commit succeeds and the losing commit races again. With a 100-thread test this converges only probabilistically and still produces 50% loss. The retry is retained *only* to cover out-of-band inserts and lock-timing edge cases, not as the primary fix (research hint acknowledged).

## 5. Migration, schema version, and compatibility

- This **is** a schema change. There is no `schema_version` table or `PRAGMA user_version` in this codebase (searched — no version sentinel anywhere; migrations are additive `IF NOT EXISTS` guards in `DatabaseManager._apply_migrations`). We therefore follow the existing convention rather than introducing one: add one more conditional DDL block and backfill, idempotent; `Base.metadata.create_all` ensures the table appears on fresh databases (necessary because `backend/tests/conftest.py:test_db` uses `Base.metadata.create_all` directly and does not call `_apply_migrations`).
- **New object:** `task_event_sequences` (surface: `backend/models/database.py::TaskEventSequence`, PK `task_id`, non-null `next_seq`).
- **Existing-object changes:** none to `TaskEvent` shape or to the unique index; `uq_task_events_task_sequence` is retained as a backstop.
- **Column/index changes in `tasks`/`skills`/etc.**: none.
- **Forward migration cost on an existing DB:** one `GROUP BY` over `task_events` to backfill, run on every boot (idempotent, `ON CONFLICT` keeps it bounded; under ~thousands of event rows this is sub-second).
- **Backwards compatibility with pre-change DBs:** pre-008 databases gain the new table on first boot via `_apply_migrations`; historical `sequence_num` values seed the counter, so semantics are continuous and the next allocation is `max(existing)+1` (no reuse of an already-used generation that could collide). No data loss, no change to queryable history.
- **No version bump** of the application data contract, and no HTTP schema change (`/tasks/{task_id}/events` only reflects longer contiguous sequences). A reader that tracks the last seen `sequence_num` continues to work; the only observable difference is that counts rise to the full attempted number.
- **Offline/DB-replayed testing:** `Base.metadata.create_all` in-memory DBs now include `task_event_sequences`, so event allocation works exactly there too. Tests that insert `TaskEvent` rows directly and then call `append_event` (e.g. `test_phase105_concurrency.py`, `test_skill_proposals_*`) will allocate above the existing seeded max because of the `MAX(sequence_num)` branch — no stale-zero collision.

## 6. Durability decisions (recorded for the implementer and reviewer)

- **Retry cap: 8 per append, not 8 per task.** (`(task_id, sequence_num)` collision is per append's own transaction; once a winning commit has landed, the next attempt reads the new value via the counter table and does not loop.)
- **Error type: `EventSequenceAllocationError(RuntimeError)`**, defined `@dataclass?`-free in `backend/runtime/events.py` and exported. It is raised only after the 8th attempt fails and always chains the underlying exception (`raise ... from exc`). Worker threads in the invariant test must collect and re-raise it (so the new test fails loudly), and DB transactions roll back through the normal `session`/`get_session` machinery rather than special-casing.
- **Ordering semantics.** Sequence numbers remain **per-task**, strictly increasing, gapless within the committed projection. `created_at` is not the replay key; `sequence_num` is (`_query` at :75-79 sorts `asc`). Two threads interleaving the same task always end up with exactly one owner per number because writers block on the database lock while they hold uncommitted transactions, and the UPSERT returns one row per unique `(task, allocated)` reservation (the row's own PK on `task_id` manufactured one-at-a-time).
- **Commit policy unchanged.** `append_event` still does not commit; `self._session.add(event)` followed by the caller's commit is the narrow contract (`EventLedger` Protocol at `interfaces.py:33-34`). The counter increments and rolls back in lockstep.
- **Gaplessness on partial rollback.** If a caller rolls back after `N` appends, both the `task_events` rows and the `task_event_sequences` updates revert, so a replaying reader cannot see a hole produced by an aborted transaction. Only committed history is measured against the invariant.
- **Lock-wait budget.** SQLite busy-timeout is raised to 30 000 ms for every connection (`connect_args` already exposes `timeout=30` at `db_manager.py:59-63`); a holder that keeps the database locked longer than that in a single transaction makes the whole attach fail with an explicit `OperationalError`, which is preferable to silent loss. 100 threads × 10 increments per transaction terminate in tens of milliseconds on this machine.
- **No retries swallowed.** No `try/except` hides worker returns: the new invariant test collects exceptions with a shared queue and re-raises. Production callers propagate normally through `get_session` (rollback + re-raise at `db_manager.py:242-246`).

## 9. Risk and assumptions

1. **The defining risk:** a simplistic fix seductively pins `max(existing, pending_new)+1` in a retry loop and survives cross-thread by luck — the suite goes green *and the defect stays*. The counter-UPSERT + writer serialisation chosen here has no such read window; the new test pins the exact count, and the rejection (§4.3) is written down so reviewers attack the same misconception.
2. **SQLite lock contention under 100 threads.** 100 concurrent `DatabaseManager` constructors each run `Base.metadata.create_all` + `_apply_migrations`. On this machine that has been stable for small tests, but at this scale schema DDL can become a bottleneck. Assumption: the invariant test pre-creates/seeds the task (schema) before launching threads, and every connection inherits `PRAGMA busy_timeout=30000` + Python `timeout=30`; if a run exhibits a lock timeout, fix it by increasing **both** (one-sided) rather than by serialising in-process (which only hides cross-connection behaviour).
3. **Timestamps and event metadata carry no ordering authority.** Two different threads' `created_at` values can tie or even skew slightly behind a smaller sequence number. Any UI that sorts by `created_at` rather than `sequence_num` can look wrong. The ordering authority is `sequence_num` already and this does not change; the verifier should confirm no test in the touched set sorts events by `created_at`.
4. **False starts from relying on `session.new`.** The old compensation (*Phase 8.75* memory ids 198/206) covered same-transaction pending rows only. The new design does not remove that contract; it removes the *cross-session* blindness. Hunch that "pending-row view plus a retry is enough" is rejected above.
5. **Size of the new table.** One row per task. Scale is bounded by the task table (~tens of thousands), so budget is negligible. Archival behaviour is out of scope but safe — deleting a task's counter row re-seeds at `MAX(task_events.sequence_num)+1` on the next append (see the `MAX` branch in the statement).
6. **Unknown SQLite versions.** `ON CONFLICT ... DO UPDATE ... RETURNING` requires SQLite ≥3.35 (RETURNING). Sythion already depends on `CREATE INDEX ... WHERE` and partial unique indexes, so partial/upsert features are baked into the supported minimum. If a future supported environment were below this floor, implementer must substitute an unconditional `INSERT OR IGNORE` + locked `SELECT ... FOR UPDATE`-equivalent (`UPDATE task_event_sequences SET next_seq = next_seq + 1` with a `changes()` check), and the plan's error class still applies.
