# Plan for 020

## The problem

Item 006 made the backend suite independent of the developer's gitignored
`backend/.env`, and its follow-up F2 (`ba69cc2`, an ancestor of HEAD) extended the
isolation to the process environment. The 006 verifier
(`.orchestra/verifications/006-v1.md`) then measured the thing that was still
missing, and measured it three ways:

* **Control 1** - the autouse isolation deleted, clean tree, no `.env`:
  the whole readiness file is **11 passed, exit 0**. A CI runner therefore
  **cannot detect a deleted isolation**. The isolation is currently *assumed*,
  not *measured*.
* **Control 2** - the isolation deleted, tree **has** a `.env`:
  `test_the_suite_does_not_inherit_the_local_env_file` fails
  (`1 failed, 10 passed`). The existing test only has teeth in a tree that
  happens to have a `.env`, and CI never has one.
* **Finding 2** - the isolation covered the `.env` *file* but not the process
  environment. **This finding is now STALE**: `ba69cc2` landed after the
  verifier's tree (`f144557`) and the current conftest clears every `SYTHION_*`
  variable both while snapshotting (`conftest.py:544-560`) and for the
  duration of every test (`conftest.py:602-612`). The current tree must be
  re-measured, not re-planned.

So the genuinely open part is a **measurement**: a check that goes RED when the
isolation is removed, on a machine that has no `backend/.env` - i.e. on CI.
Criterion 1 asks for exactly that, and the second half of it ("removing the
isolation makes that subprocess run fail") is the whole point.

The plan below was validated by measurement before it was written: a scratch
copy of the tree, a generated sentinel `.env`, a generated probe, three nested
pytest subprocesses. Every number quoted in this plan is a measurement from
this machine (CPython 3.14.7 / pytest 8.4.2 / Windows), not an estimate.

## How it will be proven

### The mechanism in one paragraph

The check is a **nested pytest run against a scratch copy of the tree**. The
scratch copy contains a byte-for-byte copy of the repository's `backend/`
package (including the repository's own `backend/tests/conftest.py`, i.e. the
isolation under test) and a **generated** `backend/.env` holding a sentinel
`SYTHION_OLLAMA_API_KEY`. Because `backend/core/config.py` computes the env
file path from `__file__` (`config.py:175`), the settings singleton in the
child process reads **the scratch tree's** `.env` - and only that. A
**generated probe module** is copied into the scratch tree's `backend/tests/`
directory, so the scratch tree's own conftest (the isolation under test)
applies to it. The probe writes ONE machine-readable line stating what it
observed; the outer test compares that line to an **exact expected string**.
Because the scratch tree inherits the repository's isolation verbatim, deleting
the isolation in the repository turns the new test RED on a CI runner - which
is exactly what the 006 verifier could not achieve.

### The scratch tree

* **Where**: `tempfile.mkdtemp(prefix="sythion-020-")` under the system temp
  (`%TEMP%`, e.g. `C:\Users\<user>\AppData\Local\Temp\sythion-020-xxxx`), i.e.
  **outside the repository**, on the same volume. A short root keeps every
  path far below the 260-character limit (the longest relative path under
  `backend/` is 57 characters: `migrations/migrate_conversation_turns_nullable_task_id.py`).
  `pytest`'s `tmp_path` is an acceptable alternative; `mkdtemp` is preferred
  because the removal is then entirely under the test's control.
* **What is copied** (the minimum that makes the subprocess meaningful):
  * `backend/` - the whole package, via `shutil.copytree`, with
    `shutil.ignore_patterns("__pycache__", "*.pyc", ".pytest_cache", ".env",
    ".env.*", "*.db", "*.sqlite*")`.
    * **Why the whole package and not a subset**: the nested run collects
      `backend/tests/test_setup_readiness.py`, which imports `backend.main`
      (the entire FastAPI app). A minimal subset (`core/config.py` +
      `core/secrets.py`) would be enough for the probe alone but NOT for the
      readiness file, and criterion 1 requires the readiness file's outcome
      set. The whole package is cheap: **238 files / 3.13 MB / 0.4 s**
      (measured), and it removes any doubt that the run is "the tree".
    * **`.env` is EXCLUDED on purpose**: the developer's real
      `backend/.env` holds a real credential. It must never be copied, read,
      printed or diffed. The scratch tree gets a **generated** `.env` and
      nothing else.
  * `pytest.ini` - copied from the repository root. It carries the marker
    vocabulary and `asyncio_mode`, and the selection-contract guard's rule 5
    requires the configuration in use to live at the tree root (in the scratch
    tree, that is the scratch root).
  * `backend/tests/test_env_isolation_probe.py` - the **generated probe**,
    copied at run time from the committed template (see "The change"). It is
    collected ONLY in the scratch tree.
  * `profile/` and `localappdata/` - empty directories, the redirect targets
    for the data dir and for `%LOCALAPPDATA%`.
* **The generated `.env`**: written at `<scratch>/backend/.env`, only for
  runs 2 and 3, containing exactly one line:
  `SYTHION_OLLAMA_API_KEY=SENTINEL-FILE-020-DO-NOT-PRINT`
  It is a fake, it is a constant of the test, and it never appears in any
  captured output (asserted).
* **Removal**: `shutil.rmtree(scratch, onerror=...)` in a `finally`, where the
  error handler clears the read-only bit and retries once. A removal that
  still fails **fails the test** (debris must not accumulate silently). The
  scratch tree holds nothing but fakes, so a leftover is not a credential
  risk - it is untidiness, and untidiness is visible.

### The subprocess invocation

All three runs use the **identical** command, cwd and environment; only the
presence of the `.env` and the state of the scratch conftest differ.

```
[sys.executable, "-m", "pytest",
 "tests/test_env_isolation_probe.py",
 "tests/test_setup_readiness.py",
 "-q", "--disable-warnings",
 "--junitxml=<scratch>/report-<n>.xml"]
cwd = <scratch>/backend
```

* `sys.executable` - **the same interpreter that runs the outer test**, so
  `fastapi`, `sqlalchemy`, `pydantic-settings`, `httpx`, `pytest` and
  `pytest-asyncio` are importable with no install step. In CI
  (`.github/workflows/ci.yml:29-39`) the runner installs
  `backend/requirements.txt` into the very interpreter that runs
  `python -m pytest tests -q`, so `sys.executable` is that interpreter.
* cwd `<scratch>/backend` - the CI shape (`working-directory: backend`).
  `python -m pytest` puts the cwd on `sys.path[0]`; pytest's *prepend* import
  mode then inserts the package root at `sys.path[0]`. Because both `backend/`
  and `backend/tests/` have `__init__.py`, that root is `<scratch>` - so
  `import backend` resolves to the **scratch copy**, and the repository root
  is not on the child's path at all. `PYTHONPATH` is removed from the child
  environment so nothing can shadow the scratch tree.
* Two explicit paths = a **partial** collection, so the selection-contract
  guard (which only guards a full-tree collection) does not run; rule 5 would
  hold anyway, because the copied `pytest.ini` sits at the scratch root.
* The child environment is built **explicitly**, never inherited wholesale:
  * every `SYTHION_*` variable removed (case-insensitive) - the developer's
    shell can contribute nothing;
  * `PYTHONPATH` removed;
  * `SYTHION_SELECTED_MODEL=SENTINEL-ENV-020-DO-NOT-PRINT` **added** - the
    process-environment sentinel;
  * `SYTHION_DATA_DIR=<scratch>/profile` and
    `LOCALAPPDATA=<scratch>/localappdata` **added**;
  * `PROBE_SCRATCH_ROOT`, `PROBE_SIGNAL_PATH`, `PROBE_NETWORK_ATTEMPTS`,
    `PROBE_FILE_SENTINEL`, `PROBE_ENV_SENTINEL` **added** - deliberately NOT
    `SYTHION_*`-prefixed, because the isolation deletes every `SYTHION_*`
    variable for the duration of a test and the probe's own plumbing must
    survive it;
  * `SYTHION_RUN_PROVIDER_E2E` is absent by construction (it is a
    `SYTHION_*` variable).

### The exact expected signal

The generated probe writes exactly ONE line to `<scratch>/probe-signal.txt`
*before* it asserts, so the line is produced even when the probe fails:

```
SENTINEL-PROBE file_neutralised=True env_neutralised=True env_cleared=True profile_isolated=True network_attempts=0
```

* **Runs 1 and 2 (isolation present) must produce EXACTLY that line.**
* **Run 3 (isolation removed) must produce EXACTLY:**

```
SENTINEL-PROBE file_neutralised=False env_neutralised=False env_cleared=False profile_isolated=True network_attempts=0
```

The five fields are computed by the probe as:

| field | expression | meaning |
|---|---|---|
| `file_neutralised` | `settings.ollama_api_key != FILE_SENTINEL` | the generated `.env` sentinel did not reach the effective settings |
| `env_neutralised` | `settings.selected_model != ENV_SENTINEL` | the exported process-environment sentinel did not reach the effective settings |
| `env_cleared` | `"SYTHION_SELECTED_MODEL" not in os.environ` | the `SYTHION_*` process environment really was cleared for the test |
| `profile_isolated` | `data_dir().startswith(scratch) and database_path().startswith(scratch)` | the profile dir and the DB path resolve inside the scratch tree |
| `network_attempts` | count of blocked outbound connects | no outbound connection was attempted |

The probe additionally drives its sentinel checks from the imported
`_LOCAL_ENV_FIELDS` (`from backend.tests.conftest import _LOCAL_ENV_FIELDS`),
so a field added to the isolation's field list is covered automatically -
criterion 4 applied to the probe as well.

All comparisons are **boolean**: the probe's failure messages name the
property that broke and never render a value (the 006 idiom), so a sentinel
can never reach a terminal or a JUnit XML. The outer test additionally
asserts that **neither sentinel string occurs anywhere in the captured
stdout/stderr of any of the three runs**.

Together with the JUnit XML, the expected signal is therefore:

| run | tree state | exit | probe testcase | readiness file | signal line |
|---|---|---|---|---|---|
| 1 | no `.env`, isolation present | 0 | passed | **11 passed** | the `True` line above |
| 2 | sentinel `.env`, isolation present | 0 | passed | **11 passed**, outcome set **identical to run 1** | the `True` line above |
| 3 | sentinel `.env`, isolation **removed in the scratch copy** | **!= 0** | **failed** | **1 failed** (`test_the_suite_does_not_inherit_the_local_env_file`), 10 passed | the `False` line above |

"Outcome set" = the set of `(classname, name) -> verdict` pairs parsed out of
the JUnit XML for `backend.tests.test_setup_readiness`. Run 2's set must equal
run 1's set, item by item - that is criterion 1's "the readiness file stays
green with the same pass/fail set as the `.env`-absent tree".

### Reproduction (the isolation deleted -> the check fails)

The negative control is the proof that the check has teeth. Two levels, and
**both must be demonstrated**:

**(a) Inside the check (the automated control, run by every execution of the
new test).** The isolation is deleted **in the scratch copy only**, with a
single anchored text edit of `<scratch>/backend/tests/conftest.py`:

```
"@pytest.fixture(autouse=True)\ndef _isolate_local_env_settings("
   ->
"@pytest.fixture\ndef _isolate_local_env_settings("
```

* The **repository's** `backend/tests/conftest.py` is never touched. The edit
  is applied to the disposable copy inside the scratch tree, which is removed
  afterwards.
* The anchor includes the fixture's **name**, so exactly one of the two
  autouse fixtures in the conftest is affected
  (`_guarded_autonomy_default`, `conftest.py:385`, is untouched).
* Turning `autouse` off disables **both halves** of the isolation: the
  settings assignment and the `SYTHION_*` environment clearing.
* **If the anchor text is not found** (the fixture was renamed or
  restructured), the test **FAILS immediately** with a message saying the
  control could not be built. A control that cannot be built is a control
  that cannot detect anything, so it must never be skipped silently.

The outer test then asserts, for run 3: exit code != 0; the probe's JUnit
testcase carries a `<failure>`; the readiness file's OWN
`test_the_suite_does_not_inherit_the_local_env_file` also carries a
`<failure>` (006's Control 2, reproduced by the repository's own test, not
only by the generated probe); and the signal line is the `False` line above.
**If run 3 had passed, the outer test fails** with "the negative control did
not fail - the check is vacuous".

Why the control is what makes the positive signal meaningful: the positive
assertion is "the sentinel is NOT in effect", which a broken scratch tree
would satisfy trivially (if the `.env` were never read, the sentinel would
simply be absent). The control closes that hole - with the isolation off and
the sentinel `.env` present, the probe MUST go red. If the scratch `.env`
were not being read, run 3 would pass and the outer test would go red. That
is the anti-vacuity mechanism, and it is why the negative control is not
optional.

**(b) In the repository (the human reproduction).** Delete the isolation from
the **repository's** `backend/tests/conftest.py` (e.g. in a throw-away
worktree) and run the new test:

* the scratch copy inherits the deleted isolation, so run 2's signal line
  becomes the `False` line, the exact-signal assertion fails, and the new
  test **goes RED**;
* independently, run 2's readiness outcome set no longer equals run 1's
  (the readiness file's own isolation test fails there too, 006's Control 2),
  so the outcome-set assertion fails as well.

That is the property the 006 verifier could not demonstrate: **on a machine
with no `backend/.env`, a deleted isolation now turns the suite red.**

### Test that pins the invariant

`backend/tests/test_env_isolation.py` (new) - one test,
`test_the_local_env_isolation_is_measured_not_assumed`, which:

1. builds the scratch tree (and asserts the developer's `.env` was **not**
   copied: `<scratch>/backend/.env` does not exist before the test writes
   its own);
2. runs the three nested pytest subprocesses, each with a **120 s timeout**;
3. asserts, for every run: exit code, the exact signal line, the JUnit
   outcome set, no sentinel in stdout/stderr, no blocked network attempt;
4. asserts run 2's readiness outcome set == run 1's;
5. asserts run 3's failure is the probe's failure and the readiness file's
   own isolation failure;
6. removes the scratch tree in a `finally`.

**Timeout behaviour**: each nested run is `subprocess.run(..., timeout=120)`.
On `subprocess.TimeoutExpired` the child is killed and the exception is
caught and re-raised as a test failure with the message "the nested isolation
run exceeded 120 s" - the test **fails, it never hangs**. The whole test is
therefore bounded by 3 x 120 s + copy, worst case ~6 minutes, and by
~30 s in practice.

## Risk

* **Slow.** A subprocess-based test costs real time. **Measured** on this
  machine: copy 0.4 s; run 1 **8.1 s** wall (pytest 5.2 s); run 2 **9.0 s**
  (5.2 s); run 3 **9.9 s** (5.9 s); **total nested ~27 s**, plus ~1 s of
  parsing. That is ~5 % of the ~8-9 minute full suite. Mitigation: the copy
  is 3.13 MB and takes 0.4 s; the nested run collects **two files**, not the
  tree; the per-run timeout bounds the worst case at 120 s.
* **Flaky.** A subprocess test can hang or be slow. Mitigation: the
  120 s per-run timeout with kill-on-timeout (the test fails, it never
  hangs); the scratch tree is unique per test, so parallel runs cannot
  collide; the child environment is fully explicit, so nothing ambient leaks
  in; there is no network (the socket guard both prevents a hang on an
  outbound call and records the attempt); there is no real profile dir and
  no real DB, so the developer's running application cannot interfere.
  Note for the budget: the machine was under load while this plan was
  written (a full-tree collection took **134 s** here, against the 21-34 s
  the 006 verifier measured), so the nested runs' absolute timings can
  inflate on a busy machine - which is exactly why the timeout is 12x the
  measured cost rather than a tight bound.
* **Windows file locks on removal.** `shutil.rmtree` can fail on a locked
  file. Mitigation: the `onerror` handler clears the read-only bit and
  retries; a persistent failure fails the test rather than leaving debris
  silently. (No DB file is created, so there is nothing to lock in practice.)
* **Self-fulfilling.** The check could prove only that "the scratch copy
  behaves like the repository". Mitigations: (a) the scratch tree is a
  byte-for-byte `copytree` of the repository's `backend/` - the isolation
  under test is the repository's own conftest, not a re-implementation;
  (b) the **negative control mutates that copy and must turn the run red**,
  which is only possible if the copy really is the repository's isolation -
  and it also breaks the repository's own readiness test; (c) the probe is
  generated from a committed template and contains no copy of the isolation
  logic, so it cannot agree with a broken isolation by construction.
* **The probe is not a repository test.** It is a committed template copied
  into the scratch tree, so it IS reviewable in the diff (that is why it is a
  file and not a string constant). It is never collected in the repository,
  so it cannot silently become a skipped test (which would violate
  criterion 6).
* **The 019 tautology guard scans every `*.py` under `backend/tests/`.** The
  two new files are therefore written in the guard's legal shape
  (`assert value is True`, `assert value == []` - a comparison is an opaque
  leaf and is never a guard position), and the guard will scan and accept
  them. No `or True` / `and False` / bare `assert True` may appear.
* **The isolation could be "fixed" in a way the check cannot see** (e.g. the
  fixture is renamed and the probe's import of `_LOCAL_ENV_FIELDS` breaks).
  The nested run would then fail loudly (collection error), and the negative
  control's anchor check fails loudly as well. Both are red, not green.

## Sensitivity

**none.** The diff is confined to `backend/tests/` (criterion 5). It adds no
credential-shaped literal other than two invented sentinels
(`SENTINEL-FILE-020-DO-NOT-PRINT`, `SENTINEL-ENV-020-DO-NOT-PRINT`), touches
no secret store, writes no credential, and reads no credential: the
developer's real `backend/.env` is excluded from the copy and never opened.
The nested run reads only the scratch tree's generated `.env`.

**Domain: none.** No product behaviour changes.

## Open questions

1. **Criterion 6's wording vs. criterion 1.** Read literally, "the full suite
   keeps the pre-change passed/skipped counts" would forbid the new test that
   criterion 1 demands. The reading this plan uses, which the implementer
   must state in the item report: the **skipped** count is unchanged, the
   **passed** count grows by exactly the number of new tests (1), the
   collected count moves 1628 -> 1629, and **no existing test's verdict
   changes**. The pre-change baseline must be measured by the implementer
   (the 006 verifier's numbers are stale: it measured 1614 collected, 45
   skipped, on a tree that predates items 017-019; this tree collects
   **1628**). If the board reads criterion 6 as "no existing test may change
   verdict, and the new tests must pass", the plan is unchanged.
2. **Should the new test carry the `slow` marker?** The plan says **no**:
   the default suite must include it, otherwise the isolation check becomes
   optional and CI would not run it. `pytest.ini`'s `slow` description does
   not forbid it, and the selection-contract guard does not police the
   `slow` population, but marking it would create the first `slow` test in
   the tree.
3. **Should the negative control also run the readiness file?** The plan says
   **yes**: it costs ~4 s and it demonstrates 006's Control 2 with the
   repository's own test, which is the most convincing part of the
   reproduction. Dropping it (probe only) would save ~4 s and weaken the
   evidence.
4. **The per-run timeout of 120 s** is ~12x the measured 8-10 s on this
   machine. On a heavily loaded CI runner the margin is smaller than it
   looks; if the implementer sees the nested run exceed ~30 s on CI, the
   timeout should be raised (not the budget cut) rather than the check
   weakened.
5. **006's finding 2 is stale**, and the item report must say so explicitly
   (the process-environment coverage landed in `ba69cc2`, after the tree the
   verifier measured). The item VERIFIES that coverage with the nested run;
   it does not re-deliver it. If the board expects a code change for
   criterion 2, the plan would have to change - but the criterion's own
   wording ("either ... or ...") and the "preferred" branch are already
   implemented.
6. **Not measured here**: the nested run on the CI runner (GitHub Actions,
   Windows, Python 3.11) - this plan's numbers come from CPython 3.14.7 /
   pytest 8.4.2 on the developer's machine. The shape (same interpreter, same
   cwd, same command) is CI-identical, but the absolute timings are not.
