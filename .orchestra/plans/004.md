> Item: **004 - Four tautological assertions replaced by the assertions they stood in for**
> (candidate R-016). Branch: `orchestra/004-real-assertions`, branched from `master`

## The problem

Four `assert` statements under `backend/tests/` end in a disjunction with the
boolean literal `True`, which makes the whole expression unconditionally true:
the assertion can never fail, so it verifies nothing, while the suite that
contains it advertises exactly the property it does not check.

| # | Site (master) | Verbatim | Suite that promises the property |
|---|---|---|---|
| 1 | `backend/tests/test_phase105_concurrency.py:530` | `assert len(tids_in_hist) == 1 or True  # history per tid already isolated` | `TestEventLedgerConcurrency::test_no_duplicate_sequence_and_no_cross_contamination` - "No cross contamination: each tid's events isolated" |
| 2 | `backend/tests/test_phase105_concurrency.py:746` | `assert not fail_res.get("fallback") is False or True  # fallback handled` | `TestModelCallConcurrency::test_provider_calls_isolated` - "One failure doesn't corrupt another" |
| 3 | `backend/tests/test_phase1075_hardening.py:765` | `assert analysis.get("delegation_id") is None or True  # reasoner returns findings` | `TestProviderE2EGated::test_two_reasoning_real_provider_isolated` - "Attribute correctly" |
| 4 | `backend/tests/test_phase125_planning_validation.py:230` | `assert "actual_policy" in d and "shadow_policy" in d and "actual_outcome" in d or True` | `test_shadow_quality_agreement_divergence` - "must store actual and shadow policy + supporting evidence" |

`grep -rn "or True" backend/tests` matches **exactly these four lines and
nothing else** in the tree today (verified).

Three further facts, all verified by the planner on this machine, shape the
plan:

* **Site 1 was doubly broken.** The expression it guarded,
  `tids_in_hist = set(tid for _ in hist)`, iterates the *loop variable* `tid`,
  not the task id of each returned event - so even without `or True` it could
  never detect cross-contamination. It is not a weakened check, it is a check
  of nothing.
* **The event projection cannot carry the task id.**
  `DbEventLedger._to_dict` (`backend/runtime/events.py:82-88`) returns
  `id, event_type, event_data, sequence_num, created_at` - **no `task_id`** -
  so the isolation property cannot be asserted from `event_history()` alone.
* **A genuine defect hides behind this test** (see `## Risk` and
  `## Open questions`): `DbEventLedger.append_event` is not safe for
  concurrent appends to the same task id, and the test's own assertions are
  count-relative, so the loss is invisible. This is the item's defining risk
  and the plan states the rule for it in advance.

A fifth, separate defect is in scope by accident: `test_phase105_concurrency.py:730`
evaluates `fake_chat([{"role":"user","content":"x"}], model_id="model-b")` to
build a `side_effect` list that is never used (the test switches to
`provider2` on the next line). The un-awaited coroutine makes every run emit
`RuntimeWarning: coroutine 'TestModelCallConcurrency.test_provider_calls_isolated.<locals>.fake_chat' was never awaited`.

### Test that pins the invariant

**New file `backend/tests/test_no_tautological_asserts.py`** - self-contained,
two test functions, no dependency on `backend/tests/conftest.py`, no
dependency on a repo-root pytest configuration file, no dependency on the
Makefile.

1. `test_no_assert_statement_disjoins_with_the_literal_true`
   Scans every `*.py` file under `backend/tests/` (recursively, so
   `backend/tests/acceptance/` is included) and fails if any `assert`
   statement's **top-level** expression is a disjunction (`ast.BoolOp` with
   `ast.Or`) that has the boolean literal `True` as one of its operands.
   Detection rule, exactly:
   * the `assert` node's `test` is an `ast.BoolOp`;
   * that `BoolOp`'s `op` is `ast.Or`;
   * at least one of `BoolOp.values` is an `ast.Constant` whose value is `True`.
   This rule is a superset of the literal `... or True` text pattern (it also
   catches `True or ...`), it flags nothing else, and it deliberately does
   **not** look inside calls or comparisons - `assert f(x or y)` and
   `assert (x or y) is not None` are legitimate and must not be flagged.
   The failure message lists every offending `file:line` plus the offending
   expression, so one run shows all of them.
   Non-vacuity is part of the same test: it asserts that the scan covered a
   plausible number of files (a floor of 50; there are 113 `*.py` files under
   `backend/tests/` today) and that the guard's own file was among them, so a
   broken path/glob can never make the guard silently pass.

2. `test_detector_flags_a_tautological_disjunction_and_ignores_legitimate_ones`
   Feeds the detector two synthetic sources and asserts both directions:
   * a source whose assert ends in a disjunction with the literal `True` **is**
     flagged (the detector has teeth);
   * a source containing `assert value == 1 or value == 2`,
     `assert any(v or w for v in vs)` and `assert (v or w) is not None` is
     **not** flagged (no false positives on legitimate assertions).
   This is what makes the guard a check rather than a hope: if someone later
   weakens the detection rule, this test fails.

**Implementation constraints for the guard module (they are not optional -
each one was found by the planner and each one breaks a criterion):**

* **Read the files BOM-safely.** Eight test files under `backend/tests/`
  start with a UTF-8 BOM (`backend/tests/acceptance/test_model_failure.py`,
  `backend/tests/acceptance/test_target_validation.py`,
  `backend/tests/test_goal_planning.py`, `backend/tests/test_kernel_concurrency.py`,
  `backend/tests/test_main_agent.py`, `backend/tests/test_phase45_hardening.py`,
  `backend/tests/test_work_orchestration.py`, `backend/tests/test_work_state.py`).
  `Path.read_text(encoding="utf-8")` + `ast.parse` raises `SyntaxError:
  invalid non-printable character U+FEFF` on those files and the guard would
  error out. Use `tokenize.open(path)` (encoding detection per PEP 263, BOM
  stripped) - with it, all 113 files parse cleanly and the detector finds
  exactly the four known sites.
* **Never spell the pattern out in the guard's own source.** Criterion 1 is a
  literal text check over the whole `backend/tests/` tree, so the module must
  not contain the two-word sequence "or True" anywhere - not in a comment, not
  in a docstring, not in a failure message. Build the synthetic snippet from
  parts (for example a tuple `("or", "True")` joined at runtime) and phrase
  messages as "the top-level disjunction includes the boolean literal True".
  The detector needs no literal at all: it matches `ast.Constant(value=True)`.
* **Locate the tree from `__file__`**, not from the CWD:
  `Path(__file__).resolve().parent` is `backend/tests/` both for
  `python -m pytest backend/tests -q` from the repo root and for CI's
  `cd backend && python -m pytest tests -q`.
* A file that cannot be parsed must be reported as a violation ("cannot
  verify"), not silently skipped. Today every file parses (checked on
  CPython 3.14.7), and no file under `backend/tests/` uses 3.12+ syntax
  (`ast.TypeAlias` / `ast.TypeVar` scan: zero hits), so CI on 3.11 parses the
  same tree.

## The change

### Files to change, and how

Everything below is **tests only**. No file under `backend/` outside
`backend/tests/` is touched.

#### A. `backend/tests/test_phase105_concurrency.py` - site 1 (master line 530)

**What the correct assertion is.** The property the surrounding test claims is
"no cross contamination: each tid's events isolated", i.e. *every event
returned by `DbEventLedger.event_history(tid)` belongs to `tid`*. The current
expression cannot express that: `set(tid for _ in hist)` yields the loop
variable, and the ledger's event dicts carry no `task_id`
(`backend/runtime/events.py:82-88`).

**The replacement** re-reads the owning rows by their primary key (the event
dict does carry the row `id`) and asserts ownership:

* assert the history is non-empty (a task that was written to must have
  events);
* fetch `TaskEvent` rows whose `id` is in the history's `id` list
  (`TaskEvent` is already imported at master line 35);
* assert that the set of `task_id` values of those rows is exactly `{tid}` -
  i.e. no event from another task appears in this task's history.

Keep the two existing real assertions above it unchanged
(`len(seqs) == len(set(seqs))` and `sorted(seqs) == list(range(1, len(seqs)+1))`),
and drop the now-meaningless local `tids_in_hist`.

**What must NOT be added:** `assert len(hist) == 10`. The concurrent-append
race (see `## Risk`) means the number of surviving events is timing-dependent
(5 or 10 in the planner's measurements); such an assertion would make the
suite intermittently red and would violate criterion 6. The isolation
property above is deterministic and is the property the test name promises.

#### B. `backend/tests/test_phase105_concurrency.py` - site 2 (master line 746) and the dead assignment (master line 730)

**What the correct assertion is.** `fail_res` is the artifact returned by
`SpecialistReasoner.analyze()` when the provider raises. The production code
path is `backend/agents/reasoner.py:271-273` -> `_fallback_artifact()`
(`:298-308`), which returns `findings: []`, `analysis: ""`,
`limitations: [reason, "fallback: no substantive model findings available"]`,
`confidence: None`, `fallback: True`. The planner reproduced the exact test
scenario and measured:

```
OK_RES:   {'findings': ['ok'], 'fallback': False, 'confidence': 0.7, 'limitations': ['n']}
FAIL_RES: {'findings': [],   'fallback': True,  'confidence': None, 'limitations': ['model failure: provider down', 'fallback: no substantive model findings available']}
```

So the intended property - "fallback handled", "one failure doesn't corrupt
another" - is exactly the **fallback contract**: a failing provider must
produce the fallback artifact (never a fake success), and it must not affect
the sibling call.

**The replacement** asserts that contract concretely:

* `fail_res.get("fallback") is True` (it is a fallback, not a silent success);
* `fail_res.get("findings") == []` (a fallback carries no findings);
* `fail_res.get("confidence") is None` (a fallback marks confidence unknown);
* `ok_res.get("fallback") is False` (the sibling call was not corrupted) -
  the existing `assert ok_res.get("findings")` on the next line already pins
  the sibling's success and stays.

Note the original left-hand side (`not fail_res.get("fallback") is False`) was
*also* true under the fallback contract; the new assertions say the same
thing concretely instead of leaving it to a `or True`.

**Dead assignment (master line 730).** Delete the whole line
`provider.chat.side_effect = [RuntimeError("fail"), fake_chat([{"role":"user","content":"x"}], model_id="model-b")]`.
It is dead: `provider` is not used again after it (the following block uses
the separate `provider2` mock), and the coroutine it creates is never awaited,
which is the source of the `RuntimeWarning`. Keep the intent comment
("One failure doesn't corrupt another") with the `provider2` block it
describes. Do not "fix" it by awaiting the coroutine - there is nothing to
await it for.

#### C. `backend/tests/test_phase1075_hardening.py` - site 3 (master line 765)

**What the correct assertion is.** This test is gated
(`SYTHION_RUN_PROVIDER_E2E=1`; it is skipped in every normal run and in CI),
so the replacement must state a property the production code *guarantees*,
not one that depends on a live model answering well.

`SpecialistReasoner.analyze()` returns either `_normalize(...)`
(`backend/agents/reasoner.py:334-390`: `findings` = list of strings,
`confidence` = float or `None`, `fallback` = `False`) or `_fallback_artifact(...)`
(`:298-308`: `findings` = `[]`, `confidence` = `None`, `fallback` = `True`).
**Neither ever puts a `delegation_id` key in the artifact** - the planner
confirmed the key sets directly: the fallback artifact carries
`{_raw, analysis, confidence, fallback, findings, limitations, proposed_actions, repaired}`
and the normalized artifact the same plus `recommended_next_action`.
Delegation attribution is the caller's job (`backend/agents/coordination.py:378-387`
attaches `delegation_id` when it builds the evidence bundle; the context
packet `SpecialistContextPacket` has no delegation field at all -
`backend/agents/specialist.py:44-56`).

So the correct assertion has two honest parts:

* **the artifact shape the reasoner guarantees** - `analysis` is a dict;
  `analysis.get("findings")` is a list; `analysis.get("fallback")` is a bool;
  `analysis.get("confidence") is None or isinstance(..., float)`;
* **the explicit negative the original left-hand side was reaching for** -
  `analysis.get("delegation_id") is None`, i.e. the reasoner does not embed
  delegation attribution; the caller owns it. This is the "explicit negative
  assertion" branch of criterion 1, and it pins the current contract.

**Do not** assert `analysis.get("findings")` is non-empty: with a real
provider the model may fail or return malformed JSON, in which case the
reasoner legitimately returns the fallback artifact with empty findings, and
the assertion would make a gated test flaky for a reason that has nothing to
do with the property under test.

#### D. `backend/tests/test_phase125_planning_validation.py` - site 4 (master line 230)

**What the correct assertion is.** `PlanningOutcomeStore.shadow_quality_report()`
(`backend/learning/planning_store.py:731-790`) builds `details` **only from
rows where `would_diverge` is true** (`:744-780`) and each detail dict
contains `actual_policy` (`:767`), `shadow_policy` (`:768`) and
`actual_outcome` (`:771`). The planner ran the test's exact scenario:

```
shadow1: actual=DEPENDENCY_AWARE_PLAN shadow=DEPENDENCY_AWARE_PLAN would_diverge=False
shadow2: actual=DIRECT_PLAN          shadow=DEPENDENCY_AWARE_PLAN would_diverge=True
details count: 1
  actual_policy: DIRECT_PLAN  shadow_policy: DEPENDENCY_AWARE_PLAN  actual_outcome: None  would_diverge: True
```

So the key-presence property is true, but the original `for d in q["details"]`
loop is **vacuous when `details` is empty** - the shape check would then
verify nothing at all, which is the same class of defect as the tautology.

**The replacement**:

* assert `q["details"]` is non-empty (this scenario is constructed to produce
  one divergent shadow, so the loop that follows is not vacuous) - this is the
  part the original was missing;
* inside the loop, assert `"actual_policy" in d`, `"shadow_policy" in d` and
  `"actual_outcome" in d` (the literal property the tautology stood in for);
* recommended extra, because the production code guarantees it and it is the
  point of Phase 12 §15/§16 (a shadow comparison must never carry a claimed
  outcome): `d["actual_outcome"] is None` and `d["would_diverge"] is True`.

## Risk

**What is most likely to break.**

1. **The concurrency test's new isolation assertion (site 1).** It depends on
   two production details: the ledger's event dict carries the row `id`
   (`backend/runtime/events.py:82-88` - true today) and `TaskEvent.id` is a
   stable primary key (true). If either changed, the new assertion would
   error, not silently pass - that is the desired direction. The assertion is
   deterministic: the planner's reproduction showed the surviving event count
   for a task varies (5 or 10) but the *owner* of every surviving event is
   always the task itself.
2. **The guard's file reading (site E).** This is the single most likely way
   to turn a green branch red for the wrong reason: reading the files with
   `read_text(encoding="utf-8")` makes 8 of 113 files fail to parse (UTF-8
   BOM) and the guard errors out. Use `tokenize.open`. The planner verified
   that with `tokenize.open` all 113 files parse and the detector reports
   exactly the four known sites and nothing else.
3. **The guard flagging the tree on the branch.** If the implementer writes
   the four replacements in a way that leaves a top-level disjunction with a
   literal `True` anywhere under `backend/tests/` (including in a helper
   function or a docstring example), the guard fails. That is the guard
   working. Fix the code, not the guard.
4. **The suite's known non-determinism.** One run on this machine aborted with
   `Windows fatal exception: code 0x80040155` (a COM fault in the
   `sythion-uia-mta` worker thread, R-007, observed twice). It is unrelated
   to this change; it is why criterion 6 is stated against a *measured*
   pre-change baseline rather than against the reference numbers.
5. **The count reconciliation in criterion 6.** The guard adds two tests, so
   the literal wording "the same passed/skipped counts" cannot hold while
   criterion 5 also holds. See `## Open questions` - the resolution is
   stated there and in the restated criterion 6.

**The defining risk of this item, and the rule for it.**

The tautology was hiding a real defect, and the planner has already found it:
`DbEventLedger.append_event` (`backend/runtime/events.py:41-73`) allocates a
sequence number by *reading* the committed maximum
(`sequence = max(last.sequence_num if last else 0, pending_max) + 1`) and
then writing. Two sessions appending to the same `task_id` concurrently
compute the same sequence number; the unique index
`uq_task_events_task_sequence` (`backend/core/db_manager.py:128-131`) then
rejects the second commit.

**Reproduced on this machine.** Running the very test this item touches:

```
python -m pytest "backend/tests/test_phase105_concurrency.py::TestEventLedgerConcurrency::test_no_duplicate_sequence_and_no_cross_contamination" -q
```

emits, from a worker thread,

```
sqlalchemy.exc.IntegrityError: (sqlite3.IntegrityError) UNIQUE constraint failed: task_events.task_id, task_events.sequence_num
```

and still reports **`1 passed`**. `threading` swallows the worker exception
(the test's `write_events` has no error propagation), and the test's own
assertions are count-relative - `sorted(seqs) == list(range(1, len(seqs)+1))`
holds for 5 surviving events just as well as for 10 - so half of a task's
events can be lost while the test is green. In the planner's standalone
reproduction, one task ended with 5 of its 10 events.

**The rule, stated in advance:**

* The real assertion wins. If the concrete assertion fails, the Implementer
  **must not** restore `or True`, must not weaken the assertion to something
  vacuous, must not delete or skip it, and must not mark it `xfail`.
* The outcome is exactly one of: (a) a fix in the production code, or (b) a
  **reported defect** in the item's report - the failing command, the failing
  output, the root cause and the blast radius.
* For this item the expected outcome is (b): the concurrent-append race in
  `DbEventLedger.append_event` is a production defect and this item is
  tests-only by contract, so it is **reported**, not fixed here, and not
  papered over with a weaker assertion. The narrowest honest replacement at
  site 1 (ownership isolation) is deterministic and passes; the racy property
  (no events lost) is reported and raised as a follow-up item that may touch
  `backend/runtime/events.py`.
* If the Implementer believes a production fix is required to make one of the
  four replacements pass, that is a scope change: it must be raised to the
  orchestrator with the evidence, not taken unilaterally.
