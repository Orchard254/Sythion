- Evidence: `DbEventLedger.append_event` (`backend/runtime/events.py:41-73`) allocates the per-task sequence number by **reading** the committed maximum (`:47-52`, `order_by(TaskEvent.sequence_num.desc()).first()`), then computing `:64` `sequence = max(last.sequence_num if last else 0, pending_max) + 1`, and finally adding the row (`:72`) with that number. The read and the write are not serialised, so two sessions appending to the same `task_id` concurrently compute the **same** sequence number. The unique index `uq_task_events_task_sequence` on `task_events (task_id, sequence_num)` (`backend/core/db_manager.py:128-131`, the `CREATE UNIQUE INDEX IF NOT EXISTS` statement at `:129-130`) then rejects the second commit. The blast radius was quantified with `scratch-004/measure_event_loss.py` (8 rounds, 10 events attempted per task, 2 tasks, 2 threads each) - `survived [10, 5]`, `[10, 10]`, `[10, 5]`, `[5, 5]`, `[10, 10]`, `[10, 5]`, `[10, 10]`, `[10, 5]` - i.e. **up to 50% of a task's event history can be silently lost while every test in the suite stays green** (`reports/004-implement-1.md:341-358`). The surviving rows' ownership was always correct, which is why item 004 could pin the deterministic ownership property rather than the racy count. The old tautology hid it because it iterated the loop variable, and the surviving count-relative assertions (`len(seqs) == len(set(seqs))`, `sorted(seqs) == list(range(1, len(seqs)+1))`) hold just as well for 5 surviving events as for 10. It is already queued for the human as `[required]` in `.orchestra/follow-ups.md:24`; this candidate is the repo-side work item. It was deliberately left out of item 004, which was tests-only by contract.
- Files: `backend/runtime/events.py`, `backend/core/db_manager.py`, `backend/tests/test_phase105_concurrency.py`
- Severity: high
- Direction: Allocate the sequence atomically rather than by read-then-write - either re-read and retry inside the write transaction when the unique index rejects the commit, or serialise appends per `task_id` (a per-task lock, or a database-assigned monotonic value) - and then add the test that asserts the **expected event count** under concurrent appends. - Status: adopted -> 008
